# run-worker-contract-executor.mjs

Test file: [test/browser/run-worker-contract-executor.mjs](../../../../../../test/browser/run-worker-contract-executor.mjs)

## Overview

The browser job in the CI workflow runs this gate inside the distributed runner image, under the environment's container limits (read-only root, no capabilities, a 256 MB `/tmp`), after installing and compiling in that same container, and reports the peak `/tmp` use. Local runs remain available through the package script. CI execution itself is established only after the workflow runs on a pull request.

Twenty-three named Node test declarations drive the browser page in Chromium. The gate is one task of the runner's browser tier, so these declarations also run on a distributed worker, launched through the `browser-test` Hardhat task. Contract, clock, detached-error and WebRTC fixtures use full SDK setup. Each page or worker realm deploys the stack once, and every SDK setup in that realm reuses the deployment with its own provider and clock, so no scenario pays for more than one deployment. The main-thread WebRTC case reaches the actual SDK service's local factory; dedicated-worker and proxy cases run full SDK setup in an application worker and forward its supplied bridge port to an SDK-owned main-thread broker. Each asserts one real data payload in each direction. Reconnect, pending teardown and native transfer-failure cases use the real provider and shared RPC. The crash-log cases use the real receiver. The nested case requires new main, SDK and VM streams under its own channel after a genuine executor error, then checks the local report reason. Shared setup and browser-error checks remain common; the fixtures do not supply fake managers or implement service routing.

The clock case brackets its asynchronous read with wall-time samples. It checks that the host Clock's adjustment falls within that interval, allowing the existing one-second sampling boundary; reply latency does not count as clock drift. The host adjustment is the value the Clock settled on after the requested 600-second shift, because the Clock sync keeps any offset within one average block time; the case also checks that it is within 60 seconds of 600, so the shift took effect.

The thread-label case renders one info line per thread name (absent, `main`, `sdk`, `vm`, `prover`) through a real `BrowserLogger`, captures the console group label for that write only, removes the `%c` style markers and matches the whole line against the shared expectation: time, level, peer, exactly one thread label, component and the unchanged message. The worker-root case sets a marker value in the page's config and creates a parentless browser worker root through the shared [BootstrapConfigRootEntry](../../../../../../test/fixtures/workerRoot/BootstrapConfigRootEntry.ts), whose root class throws before the root is built unless the worker already holds the marker; it then creates the named and unnamed logger-probe entries and reads each worker logger's thread name (`prover`, then `main`).

The detached-error fixture selects its scripted executor by the built-in worker asset URL, not the removed rpc-root name prefix. The focused browser run verifies watchdog, throw and rejection reporting while the executor remains usable.

The load-failure case creates parentless browser worker roots from a script URL the page server answers with 404, from a URL whose requests the page aborts (the diagnostic fetch included), from a URL the page answers with a 16-byte script that fails to parse, from a URL the page answers with that script first and a 28-byte valid script on the diagnostic fetch, and from a blob script that throws at top level. Each creation must reject with the exact summary for its cause and the absolute script URL, and each must log exactly one error-level line. The load and parse failures must log a plain `Event` with the URL, `received` and the `fetched` result: for the 404 and the aborted script `received` is `null` and `fetched` is the 404 or only the fetch error; for the unparsable script `received` holds status 200 and 16 bytes and `fetched` holds 200, `text/javascript` and 16 bytes; for the changed script `received` holds 16 bytes and `fetched` 28. Only the 404 case also checks the root name and a numeric `msSinceSpawn`. The throw must log an `ErrorEvent` with its message, file and line 1, and no `fetched`. The gate ignores only the 404 and aborted requests and their console lines. The failure-log case makes the owner's log write throw for that one line and expects the same throw summary plus the write error reported as uncaught.

The drain case points the page's config at the real receiver with a pinned upload jitter, creates the logger-probe worker root, writes one error-level line in it and disposes it at once. The disposal must end before the flush bound, and right after it returns, with no wait, the receiver must hold a `prover` chunk under the case's channel that contains the line. The not-ready case disposes a parent whose worker child runs an empty script that never starts: the child's creation rejects with `Runtime child closed before ready` and the disposal ends before the flush bound. The drain-timeout cases set the parent's flush bound to 500 ms while the child's upload waits 10 s. The disposal must end no earlier than the bound plus 1 s and before the upload wait, with one warning that carries the worker URL, `LoggerProbeExecutorRoot` and `drainTimeoutMs`; when the warning write throws, no warning is stored, the write error is reported as uncaught, and the disposal ends the same way.
