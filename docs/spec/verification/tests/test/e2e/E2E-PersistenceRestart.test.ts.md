# E2E-PersistenceRestart.test.ts

Test file: [test/e2e/E2E-PersistenceRestart.test.ts](../../../../../../../test/e2e/E2E-PersistenceRestart.test.ts)

## Overview

Each case runs the math harness with the persistent peers in their own temporary partitions (`persistentPeers`). `LifecycleActions.restartPeer` disposes a peer's runtime through its one disposal and starts it again with the same key and the channel id, so it resumes from its partition. Assertions read the restarted peer's head, status, turn notifications, local mirror and dispute marker through the harness-control queries before any connection, check that it refuses to author while held, then that it reaches the height the others reached while it was down and the channel's progress. The deadline case disposes the only other participant and waits for the restarted peer's abort; it never reports `PARTICIPATING`. The failed-answer case stubs the only other participant to answer the restart sync with an undecodable payload and checks the same abort. The join case restarts a founder, holds its restart sync at the application step after the answer arrived, and has a synced spectator join: the collection fails naming that founder with the restart-sync refusal and the spectator stays `SYNCED`; after the release the founder participates and the same join lands, leaving the spectator `PENDING_PARTICIPANT`. The marker case writes and flushes a dispute marker host-side with no dispute on chain, restarts and connects the peer, advances three blocks, and checks its own copy of each carries its signature and that another peer holds one of them authored by it. One case sets and clears another channel id on a persistent runtime first, as a failed negotiation attempt does, then opens the real channel, checks both partitions are on disk and restarts the peer. One case has the persistent peer dispute a double-signed block through `DisputeOrchestrator.openOrdinaryDisputeWindow`, then restarts it. One case authors a block off the wire with its gossip and calldata post cut, restarts the author, and waits for the calldata on another peer; a second keeps the author down for the agreement time plus one second first, so the re-armed post has no delay left. The held-dispute case suppresses the timeout checks of the two live participants, restarts the third without connecting it and records its dispute uploads and audits, keeps participant 0 from disputing (its kill of an invalid dispute still lands alone), and has participant 1 upload a dispute stripped of every reason. Participant 0's kill empties the window, and every peer that sees that kill tries to dispute the fork; after the held peer saw it and a 500 ms absence window, it has recorded no upload and no audit (only a committed participant audits), holds no dispute marker and is still `SYNCED`. The sync-joiner case adds a synced spectator, lands its join, waits until it participates, restarts it and checks its restored height and that the channel continues past it. The reduction cases dispute an invalid state transition of one of four participants and reduce the fork without it (`startAndReduce`): one restarts the persistent peer before the reduced fork's first block and checks it holds that fork's genesis, participates after its restart sync and co-signs the next blocks; the other first authors two blocks on the reduced fork, checks the replaced fork holds more, restarts the peer and checks it resumes on the reduced fork at its height, co-signs the next three blocks, all honest peers agree on them, and none blacklisted it. The no-persistence case checks only that the restart comes back fresh, not that nothing reached disk, so `REQ-STOR-10-XY96KG.T1.P1` stays unassigned.
