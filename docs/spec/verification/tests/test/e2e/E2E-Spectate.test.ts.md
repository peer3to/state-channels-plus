# E2E-Spectate.test.ts — Test Report

## Overview

The suite drives the full spectator lifecycle end to end through the `MathTestSession` harness:
real multi-peer channels, harness control RPC into each peer's host-side `StateManager`, and
`execOnHost` bodies where an interleaving has to be staged in-process (mutex-guarded persistence,
captured pre-handshake transports). The guard case sends a request on an incomplete-handshake
transport, asserts the exact guard error and zero endpoint admission, then completes a valid
spectate request over a separate authenticated session. Other covered flows include same-fork
spectating with atomic persistence and the already-ahead no-op,
proof reconstruction from synced storage,
fork-traversal and post-dispute spectating, spectator promotion to participant (`forceInboundJoin`
and `joinChannel`, including concurrent promotion races — the losing joiner's static call is
decoded and matched against the widened threshold set and the set its pre-signed signatures
recover to, which is what identifies the pending participant as the missing signer; the losing
joiner's client-side cleanup is read as the status-hook transition back to `SYNCED` immediately
followed by the abort transition to `OPENED`, plus a cleared force-join submission height, because
the abort sets `OPENED` itself and would otherwise hide both cleanup effects), genesis and
block-0 joins, concurrent
sync dedup, mutual blacklisting on an unprovable target, minimum-height payload proving (heights 0/1
and requests at or below a leave), and dispute-window recovery inside `generateSyncPayload`. Oracles are peer
status and sync/block-height assertions, storage and blacklist queries through control RPC, event
spies, and direct decode of generated sync payloads against the responder's latest height. Three tests are
currently blocked or flaky on known product bugs (#351–#353) and carry no IDs. Out of scope: the
forged-payload element matrix, balance-invariant checks, and chain-level no-transaction
observation ([`INV-SYNC-4-Z6HER7` (Read-only trust establishment)](../../../../specification/peer-communication/synchronization.md#inv-sync-4-z6her7)). The former bundled permutations have been atomized into
one-scenario IDs, so the latest/pinned successes, refusals, no-op skips, and abort cases here
now carry their own assignments.
Spectator spawns in this suite go through the shared `addSpectatorAuthoring` helper (`test/harness/JoinActions.test.ts.md`): the spawn runs unawaited while the named participants keep authoring, bounded by literal minimum and maximum block counts, so no spawn or promotion sits inside an idle authoring window.

The finalized-window joiner scenario selects surviving honest responders. Recovery after accepting a genesis-only proof from a removed peer remains unverified: [`REQ-SYNC-1-T2589H.T1.P16`](../../../../specification/peer-communication/synchronization.md#req-sync-1-t2589h.t1.p16), tracked by [`FIND-SYNC-1-JWY1C8` (Recovery from a removed sync responder lacks verification)](../../../../audit/open-findings.md#find-sync-1-jwy1c8).

The proof-reconstruction cases sync a spectator on a three-participant channel and then build a state proof from the spectator's own storage with `constructProof` (`AgreementManager.buildStateProof`, then the chain's `verifyMilestones`). The first case posts a snapshot before the spectator joins and asserts the built proof is chain-valid. The second case builds a chain-valid proof after more finalized blocks, then has peer 0 post a snapshot and one more block finalize, and asserts the proof is still chain-valid and ends at a greater height.

The `Sync verification and completion` cases use the staging helpers in `test/fixtures/SyncVerificationStaging.ts` and `test/fixtures/SyncCompletionStaging.ts`. In the read-failure case the spectator's next local `verifyMilestones` read fails with a transport fault during its initial sync: its connect fails with `connectToChannel failed`, `onAbort` fires once, and no participant blacklists it; a fresh spectator added afterwards syncs to the latest height and no peer blacklists another. The lagging-spectator cases isolate a synced spectator at its final point while one more block finalizes. A kept early payload whose history ends below that point, and a payload whose served state is an earlier threshold-final block whose tail would replay past that point, are both rejected as `served state below the proof start` with the responder blacklisted, the head at the final point and the state unchanged. An honest head payload from another participant then completes the sync and matches that participant's state. A payload with a forged adopted snapshot is rejected as `milestones invalid` with no stored snapshot and an unchanged state. A placeholder milestone below the final point is ignored: the stored honest block stays and the planted snapshot is not stored. The compact case syncs a spectator after a snapshot at height 2 and four more blocks: only the head block is stored, and the proof (start 2, one milestone) is chain-valid and goes into a dispute. The repeated-run case serves the last run twice: with a forged tail block every participant serves, a fresh spectator's runtime closes; with the honest tail the spectator's blocks and state match the responder's after replay. The unposted-leave case syncs after a signed leave whose exit snapshot is not posted: the spectator stores the change height and only the change and head blocks, and builds chain-valid proofs [change], [head] from genesis, after one more block, and after the exit snapshot lands (then starting at that snapshot).

The dispute-window-gap case waits until the window's kill period has expired on the responder before it asks for the payload, because a responder serves a disputed window only after its kill period.

The kill-period case runs the real `sync` RPC, parks the requester at its window persistence after the proof arrived, commits a dispute on the pinned fork, and releases: the sync resolves `true`, neither peer blacklists the other, the requester stays on the fork, and the dispute still resolves with no host error.
