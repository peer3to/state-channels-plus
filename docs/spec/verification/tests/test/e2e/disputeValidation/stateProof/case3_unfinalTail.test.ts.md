## Overview

The suite audits a state proof that is only an unfinal tail. `preDisputeSetupDisconnectedPeer`
prepares a channel where peer 2 is disconnected and never signs, so no block is threshold-final: the
proof is one milestone run from genesis block 0, and the whole run is the unfinal tail.
`stubConstructDispute` rewrites peer 3's honestly built dispute just before submission, and
`submitDoubleSignBlock(1)` gives peer 3 a real reason to dispute. The tampers break the genesis link
of block 0 (the later blocks are relinked, so only the genesis link is wrong), inject a forged inbound
message into the last block's `messageBlocks`, break the `previousBlockHash` link of tail block 1,
copy another block's author signature onto the last block, and make the last block's author an
outsider. Oracles: the dispute initiates with auditing data, peer 0 observes `onDisputeKilled`, the
honest peers store the expected proof type — `DisputeInvalidStateProof` for the broken genesis link,
`DisputeInvalidBlockInStateProofApplyFraudProof` for the forged message,
`DisputeInvalidBlockStructure` for the linkage and signature breaks, `DisputeBlockAuthorNotParticipant`
for the outsider — and the dispute window then resolves. The outsider case also asserts that peers 0,
1 and 3 each store exactly that one proof type. The last case sets a zero `stateSnapshotHash` on the
last block and drops the auditing data: the honest peers store
`DisputeLastMilestoneNotFinalAndNoAuditingData`, so the missing auditing data is judged before the
tail content. `latestStateSnapshotHash` tampers live in
`disputeInputFields/latestStateSnapshotHash.test.ts`; upload-gate reverts are out of scope.
