## Overview

The suite verifies the shared first-join and top-up owner used by direct signer calls and targeted connect.
It verifies that transaction submission establishes local pending protection before the receipt. A failed
receipt restores `SYNCED`; failures observed while the transaction is pending do not abort the runtime.
Later block inclusion remains separate from transaction submission and receipt handling.

Pending or participating callers with no balance send no transaction. Top-ups send once and wait for the
receipt. Force-join cases check the fired flag at the triggering block, then wait for detached dispute
construction to reach its recorded submission. The trigger case sets the counting start height directly: one
block early starts nothing, and at `counting start height + participants + 1` the dispute starts and exactly
one submission is recorded. The grace case records a join submitted at height 0 whose `agreementTime` grace
has not ended: the latest block starts no dispute and records no counting start height. After the grace ends,
the same block becomes the counting start height and still starts no dispute, and no submission is recorded.
The Clock case waits, with no fixed sleep, until the observer's own Clock is more than one second past its
latest block's timestamp (the author stamps a block one second past its own Clock), then sets
the counting start one second after that block's timestamp: block timestamps play no part, so the block
counts by the observer's clock at commit. It becomes the counting start height, fires nothing, and nothing is
submitted.

The deferral case holds the join submission, makes the block bound due, and shows the absent signer defers
(no fired bound, marker kept, no submission). After the join lands and the chain lists the signer, it answers
"no dispute window" for the local window read and runs the due check twice: exactly one submission is
recorded. The refusal case lets the joiner observe its join (the deadline is armed), answers an expired
evidence window for the local window read, and makes the block bound due: the bound is fired, the deadline is
cancelled, the marker stays, nothing is submitted, a later due check with the window restored starts nothing,
and the runtime stays `PENDING_PARTICIPANT`.

The deadline case suppresses and records the joiner's `force join deadline` task, completes a first join,
waits until the joiner observes its join and the task is armed, and asserts a grace start within one second of
observation time plus `agreementTime` and exactly one task whose delay is
`(participants + 1) × (p2pTime + agreementTime + chainFallbackTime) × 1000` ms; the deadline firing itself is
the force-join E2E subject. The unobserved case holds the join submission so the join stays off chain while
the founders author four blocks, and asserts no `force join deadline` task, no grace start and no started
dispute. The re-arm case lets all founders omit the join and fails the joiner's local dispute-window read, so
every force-join start defers. The founders keep authoring until a second `force join deadline` task is
recorded, and the case asserts that no force-join dispute started. The seated case records the stored
authorization deadline (equal to the confirmation's `deadlineTimestamp`) and then authors until the joiner is
`PARTICIPATING`: every join field reads absent, the fired flag is false, and no deadline task is armed.

The uncertain-outcome case also asserts that no grace was recorded, because the join was never observed. Two
landed-join cases share one staging body: the join lands, then the submission reports an uncertain outcome or
an "already a participant" outcome. `joinChannel` returns `true`, the grace start is recorded once the joiner
observes its join, and the runtime stays `PENDING_PARTICIPANT`.

The `getOwnJoinState` cases read through the public signer: `none` for a synced spectator; for an uncertain
join that never lands, `open` with `secondsUntilExpiry` at least 1 and at most the chain deadline minus the clock read before
the state (the chain time can lead the local clock), then `expired` once a
chain block is past the deadline, while the runtime stays pending; `landed` for a join that landed before an
uncertain outcome; and `none` with `SYNCED` after a failed receipt.

The two repeat-join cases reject a second `joinChannel` on a pending or participating runtime and prove the
runtime keeps its status and stays undisposed; the later-sync-failure angle of the same requirement is owned by
the targeted-join E2E suite. The unopened-refresh case maps to its own refresh permutation.

These cases contribute to [`REQ-TJOIN-2-MFWADG` (Separated matching and handoff)](../../../../specification/peer-communication/targeted-channel-join.md#req-tjoin-2-mfwadg) and [`REQ-TJOIN-5-Q795M7` (Phase-specific failure)](../../../../specification/peer-communication/targeted-channel-join.md#req-tjoin-5-q795m7).

Cached source checks are optimistic. Misses refresh once, including concurrent misses. Tests also cover failed reads, reset, committed off-chain additions and observed slashes during a refresh.
