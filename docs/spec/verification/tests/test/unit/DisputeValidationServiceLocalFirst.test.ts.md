## Overview

Each case builds a real dispute on a running math channel (`fetchConstructedDispute`), optionally
edits its input or auditing data, and audits it on another peer through the harness
`auditDispute`, which returns the verdict (or the thrown message) and the stored proof. The
harness mirror service observes one local-first read on that peer record-only: every local and
chain call still reaches the real local diamond and the real manager, and the oracle reads the
answers and failures of each side. Divergence is staged with real state, never with a stubbed
answer: the chain view is served from the block just before an event (`serveChainReadsBefore`), the
auditor's mirror misses a consumed top-up, or the auditor's store and mirror miss or trail the
previous block's calldata post. `failNextLocalRead`/`failNextChainRead` make one read fail through
the real contract and connection: `revert` calls the same function with its ABI arguments cut
off, so the EVM reverts; `transport` sends corrupted params to the local executor ("Malformed RPC
request") or sends the chain read to an endpoint that refuses the connection. A fault or chain
refusal case asserts the thrown audit and no proof; a case about avoiding the chain asserts zero
chain reads.

The header-check cases observe that neither answer reads the chain. The finality cases cover a
local final answer kept without a chain read, a local not-final answer confirmed by one chain read,
a lagging chain view, a local revert and a local executor failure (each throws out of the audit
with no chain read and no proof), and a chain read refused for transport (the audit throws and
stores no proof). The latest-state, balance-invariant and
timeout-calldata cases cover a local answer kept, a chain-confirmed adverse answer, and a mirror
or store that misses or trails real state. Each of these three checks also covers a local executor
failure (the audit throws it with no chain read) and a local answer whose chain read is refused for
transport (the audit throws and stores no proof). The timeout-calldata preflight stores no
`TimeoutCalldataPosted` proof the chain rejects, so the auditor never submits a proof that would
slash it. The forged-`totalDeposits` balance case judges the dispute's latest
state once: one local answer and one chain answer, both invalid.

The local-false/chain-true split of the latest-state check is staged with a stale genesis dispute
(`stageStaleGenesisDispute`): the dispute claims genesis as the latest state after a snapshot was
posted. The chain view of both `isCorrectLatestState` and `getAnchorSnapshot` is served from
the block before that `StateSnapshotUpdated` post, so the chain still answers "correct" while the
auditor's up-to-date mirror answers "incorrect". The case asserts one local `false`, one chain
`true`, and that the stored proof is `DisputeNotLatestState` from the later latest-state check, not
`DisputeInvalidStateProof`.

The `state-proof verification` cases observe the two verification paths. Without posted data the
linkage and the latest state decide: the local `isStateProofLinked` answers true with no chain read,
and no walk runs (`verifyMilestonesFromTrustedStart` and `verifyMilestones` are not read). Posted
data is judged by the chain's `verifyStateProof` alone: a forged block above the tip
(`postedForgedSingleton`) gets the chain's `false` with no local `verifyStateProof` read and no walk,
and the audit stores `DisputeInvalidStateProof`; a chain read refused for transport throws with no
proof. When the chain's start (9) is ahead of the mirror's (5, `stageChainAnchorAheadOfMirror`), a
run from the chain's start is accepted by the chain; the persistence walk's local tiers answer
invalid, the chain walk answers valid, and the replay alleges the forged tail block at block index 1.
A run over the auditor's final point whose start snapshot is a re-timed copy gets the chain's
`false` and `DisputeInvalidStateProof` with no walk; the same run on another fork stops at the
header check.

The `chain anchor races` cases check that a block allegation keeps its position in the submitted
proof whatever start the mirror or the chain has: with the chain at 9 and the mirror at 5, with the
chain at 5 and the mirror at the genesis, and before and after a delayed snapshot event, the
stored allegation is block index 6, the last `isBlockChallengeEligible` chain answer (after the
replay's tail-start search) is true, and `commitAndKillAsAuditor` applies it: the disputer is
slashed, the auditor is not. A run whose block 6 is a bad transition from the mirror's start 5 but
whose block 9 does not commit the chain's start 9 is rejected by the chain's `verifyStateProof`
(`DisputeInvalidStateProof`) with no eligibility read. Each audit reads the chain's start
(`getAnchorSnapshot`) once, honest or with an allegation, and a valid local walk adds no chain walk.
A failed eligibility read throws with no stored allegation, and an explicit repeat audit reads the
chain again and submits the allegation.
