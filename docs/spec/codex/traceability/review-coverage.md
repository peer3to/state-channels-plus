# Specification review coverage

## Purpose

This map shows where each note in `temp/SPECIFICATION-REVIEW.md` is represented in the new specification tree. It prevents accepted design detail from disappearing during the split from one file into subsystem chapters.

`Accepted` means the design is stated as normative. `Decision` means the review itself left a choice open. `Gap exposed` means the intended direction is clear but current code does not satisfy it. One row may have more than one status.

## Coverage audit rules

When the specification changes:

1. keep the review row linked to the chapter that owns the behavior;
2. move accepted behavior out of the decision register and into the owning normative algorithm;
3. mark code contradictions in both the owning chapter and [Verification](../verification.md);
4. add test evidence only when the test asserts the exact requirement;
5. do not mark a review note complete only because terminology appears somewhere in the tree.

## Current result

All 41 review notes have an owning location. The map also shows where documentation is complete but implementation, evidence, or engineer decisions are still missing. Those gaps are retained because the review asks the specification to expose conflicts instead of copying current code as intended behavior.

## Future work

Non-normative tooling may generate this map from stable review and requirement IDs. Until then, changes to an owning chapter must update this file in the same review.
