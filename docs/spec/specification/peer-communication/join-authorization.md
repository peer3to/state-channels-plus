## Purpose and observable contract

Admission expands the on-chain participant set and requires unanimous authorization: the joiner
signs the join, and every member of the current eligibility set (snapshot participants plus
pending joiners, minus on-chain-slashed — the slash-excluding rule of
[cross-layer-messages.md §4](../settlement/cross-layer-messages.md)) must countersign before the
joiner submits on-chain with its deposit. This service is
exactly the collect-signatures hop: the joiner fans out one request per threshold member and
assembles the confirmation, or the collection fails as a whole. Deciding _whether_ to admit is not
part of this service's current contract — a structurally and contextually valid request is signed —
and the admission-policy filter is an open decision ([`OQ-10-04YNC4` (Spectate/join failure-point details)](../open-questions.md#oq-10-04ync4)).

## Collector algorithm

Run by the joiner, locally:

1. **Self-scope.** Collect only for the local identity's own join; collecting for a third party is
   refused.
2. **Pin the chain state.** Read the current on-chain snapshot; record its hash and fork id. The
   collection is valid only against this exact state — the same values enforcement re-checks at
   submission, so a stale collection fails on-chain rather than admitting against a moved state.
3. **Derive the threshold set** from the pinned state: snapshot participants ∪ pending joiners,
   minus on-chain-slashed participants.
4. **Self-sign** the join and produce its canonical encoding — the exact bytes every counterparty
   signs.
5. **Preflight reachability.** Every remote threshold member must be reachable before any request
   is sent; a missing member fails the collection immediately (unanimity cannot be reached).
6. **Bound each request** by the smaller of the agreement window and the time remaining until the
   join's deadline. Collection requires a positive remaining window; a deadline at or before the
   current protocol time fails before self-signing or sending any request.
7. **Fan out in parallel**; verify every returned signature recovers, over the exact encoded join,
   to the addressed member. Any timeout, error, or wrong-signer response fails the whole
   collection.
8. **Assemble** the confirmation: the signed join plus one verified countersignature per threshold
   member, with the pinned snapshot hash and fork id for submission.

## Responder algorithm

Run by each threshold member on request; the adversarial ingress side:

1. **Authenticated sender required** ([rpc.md](./rpc.md)).
2. **Decode** the signed join through the canonical encoding; decode failure is a request error.
3. **Bind three identities.** The signature over the encoded join must recover to the join's
   declared participant, and that participant must equal the authenticated sender. No relaying or
   collecting on behalf of others.
4. **Context checks.** The join's channel must be this node's channel; the deadline must not have
   passed in protocol time (equality is still valid for a responder). The responder does not compare
   the joiner's snapshot and fork pins with its own chain view: the countersignature covers only the
   encoded join, the pins are the joiner's guard against joining a state it did not verify, and
   enforcement checks them at submission.
5. **Authority check.** The local identity must itself be in the current threshold set; a
   non-member has no authority to countersign.
6. **Countersign** the exact encoded join and return the signature. Every validation failure is a
   penalty-free declared error — refusing is a normal outcome, not misbehavior.

## Failure outcomes

First joins and top-ups construct `deadlineTimestamp` from chain time plus the standard 120-second join
deadline at execution. No public lobby, connect, worker, or harness option supplies it. A supplied full
balance preserves `amount` and `data`; omitted requested membership uses the simple default. Participants
validate remote balances with the state machine's neutral zero value and existing lesser-than operation
before signing.

After exact-channel sync, a first join waits up to two agreement windows for every threshold participant to
be directly reachable, then uses the normal per-request signature deadline. Missing reachability or a failed
signature leaves the caller uncommitted, so it aborts and disposes. Receipt-confirmed
`PENDING_PARTICIPANT` is already a successful membership result; later cooperative block inclusion or forced
inclusion is separate. A pending or participating call with no balance sends no transaction. A supplied
balance sends one top-up and waits for its receipt. A first join or a top-up whose proven failure follows a
move of the on-chain snapshot to one the runtime stores is collected again once against that snapshot, with
the same balance and a fresh deadline, and submitted once more; a failure of that retry is final
([`REQ-JOINSIG-1-8X1A4V`](join-authorization.md#req-joinsig-1-8x1a4v)).

| Failure                                                                                    | Outcome                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Collector: unreachable member, timeout, error, wrong-signer response                       | Whole collection fails (unanimity is all-or-nothing); no penalty assigned by this service.                                                                                                                                                                                                                                            |
| Responder: any validation failure (decode, identity binding, channel, deadline, authority) | Penalty-free declared request error; session kept.                                                                                                                                                                                                                                                                                    |
| Stale pins at submission                                                                   | Enforcement rejects. A first join or top-up whose pinned snapshot moved to one the runtime stores collects once more against that snapshot ([`REQ-TJOIN-5-Q795M7`](targeted-channel-join.md#req-tjoin-5-q795m7)); otherwise, and after that one retry, a first join aborts and its runtime is disposed, and a top-up returns `false`. |

## Requirements and invariants

**<a id="inv-joinsig-1-jx5ec4"></a>`INV-JOINSIG-1-JX5EC4` — Identity triple-binding.** A countersignature is produced only when the join's
embedded signature, its declared participant, and the authenticated requesting peer all bind to the
same identity.

**<a id="inv-membership-pending-1-2h1t75"></a>`INV-MEMBERSHIP-PENDING-1-2H1T75` — Submitted joins are locally
pending before acknowledgement.** A first join MUST move the local runtime from `SYNCED` to
`PENDING_PARTICIPANT` before invoking transaction submission or crossing any asynchronous boundary that may
send it. This protects a potentially funded in-flight transaction from cleanup that applies only to an
uncommitted observer. A final failure ends the logical join and restores `SYNCED` only when the outcome proves that no
commitment exists. An intermediate refusal eligible for the one snapshot-race retry does not end it. An uncertain submission keeps local pending protection while chain state is reconciled; a
join the chain has not shown when its active authorization expires on chain, and that the chain does not list, ends
and restores `SYNCED`. Each such end is reported as `onLeftChannel`. Force-join escalation MUST wait until the
signer is present in the authoritative on-chain participant union and the ordinary dispute window is usable;
an expired window defers the check to a later relevant trigger without a duplicate submission. An observed
join that the chain no longer lists was dropped without a seat: it ends and restores `SYNCED`, reported as
`onLeftChannel`. A failed authoritative read is an internal failure, not a deferral.
Both escalation bounds start at the observation of the joiner's own on-chain JOIN, never at submission. The
height bound starts at the first block committed one agreementTime after that observation and MUST NOT
trigger before current participant count + 1 further heights; that exact height is the first eligible block.
The time bound arms at observation for (current participant count + 1) full author-timeout windows.

**<a id="req-joinsig-1-8x1a4v"></a>`REQ-JOINSIG-1-8X1A4V` — Pinned-state authorization.** The collector pins its collection to the exact
on-chain snapshot and fork it read, and the collection's pins MUST be carried to submission, where enforcement
checks them. A countersigner MUST NOT refuse because the pins differ from its own chain view: its
countersignature covers only the encoded join, so such a refusal protects no one and only fails a join that
races a snapshot post. A collection rejected for stale pins is never
resubmitted; any retry is a fresh collection pinned to the current chain state. A first join or a top-up whose
proven failure (a decoded revert or a mined failed receipt) follows a move of the on-chain snapshot away from
its pin, with both the pinned and the new snapshot stored by the runtime, is collected again once with the same
balance and submitted once more; a failure of that retry is final. When the fresh collection for that retry fails, the call ends as a failure with no second submission: a first join becomes `SYNCED` and does not abort, and a top-up keeps the participation. An unchanged snapshot, an unstored pinned or
new snapshot (a pin that was never a real snapshot is not a race) gives no retry. A first join or a top-up
refused because its confirmation's signers no longer cover the threshold set (another join landed first and
its pending participant widened the set) is the same race and gets the same one retry: a fresh collection
from the current threshold set, which the new pending participant countersigns, submitted once more; a
failure of that retry is final. Two first joins prepared concurrently on one table therefore both land:
the second costs one more collection and submission, never more.
A failed snapshot read rejects the call under the [SDK-wide RPC availability assumption](../runtime/sdk.md#assumptions-and-constraints);
it is an infrastructure error, not a normal no-retry outcome, and does not require refusal cleanup before
propagation.

The automatic snapshot-race retry is part of one logical join operation owned by the join component.
During fresh collection and the internal retry, the public call MUST remain pending: the intermediate
refused attempt does not resolve or reject it, expose a transient `SYNCED`, emit `onLeftChannel`, or
report a final join failure. Local pending protection remains in place until the operation reaches
its final specified outcome. Retire the refused attempt's deadline and invalidate its stale checks
before fresh collection so they cannot end the logical operation. A completion after the operation
has ended or the runtime is disposed MUST NOT submit another funded join. This preserves the one-retry
limit and existing final success, refusal, collection-failure, uncertain-submission and error handling;
it adds neither infinite retries nor RPC-outage recovery.

**<a id="req-joinsig-2-rr2g4q"></a>`REQ-JOINSIG-2-RR2G4Q` — All-or-nothing unanimity.** The collection succeeds only with a verified
countersignature from every threshold member over the exact encoded join; any member's failure
fails the collection.

**<a id="req-joinsig-3-vagfvd"></a>`REQ-JOINSIG-3-VAGFVD` — Refusal is penalty-free.** A responder's validation failure is a declared error
without session or identity consequences; countersigning is voluntary cooperation, not an
obligation whose refusal is slashable.

## Assumptions and constraints

- Requires authenticated sessions. The joiner needs a current chain view for its pins; a countersigner's
  view of the snapshot does not affect its answer.
- Deadline arithmetic uses protocol time ([time.md](../protocol-model/time.md)).
- A collector needs time to contact remote members, so it requires a deadline strictly after its
  current protocol time. A responder may sign at the exact deadline; enforcement applies the same
  inclusive deadline boundary at submission.
- The service is stateless across calls: every decision derives from the request plus live reads,
  so replay of a still-valid request yields another signature over the same bytes — idempotent by
  content.
- Admission policy (who _should_ be admitted, beyond structural validity) is deliberately outside
  this contract and open ([`OQ-10-04YNC4` (Spectate/join failure-point details)](../open-questions.md#oq-10-04ync4)).

## Security considerations

The unanimity rule makes this service safety-relevant: a signature harvested here becomes part of a
membership change. Defenses: triple identity binding stops relayed or third-party collection;
byte-exact signing over the canonical encoding stops substitution between what was validated and
what was signed; the joiner's state pins stop a submission against a moved or forked state; threshold
membership stops non-members from manufacturing authority. Residual: unconditional signing of valid
requests means membership control is purely structural until the admission filter is decided
([`OQ-10-04YNC4` (Spectate/join failure-point details)](../open-questions.md#oq-10-04ync4)); a malicious joiner can burn responder attention (rate bounds per [`REQ-RPC-5-CV1R1Y` (Resource bounds)](rpc.md#req-rpc-5-cv1r1y)). The one retry after a
move to a stored snapshot adds no authority: every threshold member countersigns again, and enforcement checks the new
pins and the current threshold set. It costs one more countersignature round and one more funded
submission per join or top-up; it keys on the snapshot move, not on the revert reason, so any proven failure that
coincides with such a move gets the one retry.
