## Purpose and observable contract

Admission expands the on-chain participant set and requires unanimous authorization: the joiner
signs the join, and every member of the current eligibility set (snapshot participants plus
pending joiners, minus on-chain-slashed — the slash-excluding rule of
[cross-layer-messages.md §4](../settlement/cross-layer-messages.md)) must countersign before the
joiner submits on-chain with its deposit. This service is
exactly the collect-signatures hop: the joiner fans out one request per threshold member and
assembles the confirmation, or the collection fails as a whole. Deciding _whether_ to admit is not
part of this service's current contract — a structurally and contextually valid request is signed —
and the admission-policy filter is an open decision ([`OQ-10-04YNC4` (Spectate/join failure-point details)](../open-questions.md#oq-10-04ync4)).

## Collector algorithm

Run by the joiner, locally:

1. **Self-scope.** Collect only for the local identity's own join; collecting for a third party is
   refused.
2. **Pin the chain state.** Read the current on-chain snapshot; record its hash and fork id. The
   collection is valid only against this exact state — the same values enforcement re-checks at
   submission, so a stale collection fails on-chain rather than admitting against a moved state.
3. **Derive the threshold set** from the pinned state: snapshot participants ∪ pending joiners,
   minus on-chain-slashed participants.
4. **Self-sign** the join and produce its canonical encoding — the exact bytes every counterparty
   signs.
5. **Preflight reachability.** Every remote threshold member must be reachable before any request
   is sent; a missing member fails the collection immediately (unanimity cannot be reached).
6. **Bound each request** by the smaller of the agreement window and the time remaining until the
   join's deadline. Collection requires a positive remaining window; a deadline at or before the
   current protocol time fails before self-signing or sending any request.
7. **Fan out in parallel**; verify every returned signature recovers, over the exact encoded join,
   to the addressed member. Any timeout, error, or wrong-signer response fails the whole
   collection.
8. **Assemble** the confirmation: the signed join plus one verified countersignature per threshold
   member, with the pinned snapshot hash and fork id for submission.

## Responder algorithm

Run by each threshold member on request; the adversarial ingress side:

1. **Authenticated sender required** ([rpc.md](./rpc.md)).
2. **Decode** the signed join through the canonical encoding; decode failure is a request error.
3. **Bind three identities.** The signature over the encoded join must recover to the join's
   declared participant, and that participant must equal the authenticated sender. No relaying or
   collecting on behalf of others.
4. **Context checks.** The join's channel must be this node's channel; the deadline must not have
   passed in protocol time (equality is still valid for a responder); the current on-chain
   snapshot's fork and hash must equal the request's pinned values — the countersigner authorizes
   only against the chain state it currently observes.
5. **Authority check.** The local identity must itself be in the current threshold set; a
   non-member has no authority to countersign.
6. **Countersign** the exact encoded join and return the signature. Every validation failure is a
   penalty-free declared error — refusing is a normal outcome, not misbehavior.

## Failure outcomes

First joins and top-ups construct `deadlineTimestamp` from chain time plus the runtime's configured join
authorization lifetime (120 seconds by default) at execution. The lifetime is runtime configuration; no public
lobby, connect, or worker call option supplies it. The joiner records the deadline of the join it submits:
it bounds how long the join can still land ([`INV-MEMBERSHIP-PENDING-1-2H1T75`](join-authorization.md#inv-membership-pending-1-2h1t75)). A supplied full
balance preserves `amount` and `data`; omitted requested membership uses the simple default. Participants
validate remote balances with the state machine's neutral zero value and existing lesser-than operation
before signing.

After exact-channel sync, a first join waits up to two agreement windows for every threshold participant to
be directly reachable, then uses the normal per-request signature deadline. Missing reachability or a failed
signature leaves the caller uncommitted, so it aborts and disposes. Receipt-confirmed
`PENDING_PARTICIPANT` is already a successful membership result; later cooperative block inclusion or forced
inclusion is separate. A pending or participating call with no balance sends no transaction. A supplied
balance sends exactly one top-up and waits for its receipt.

| Failure                                                                                                       | Outcome                                                                                    |
| ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Collector: unreachable member, timeout, error, wrong-signer response                                          | Whole collection fails (unanimity is all-or-nothing); no penalty assigned by this service. |
| Responder: any validation failure (decode, identity binding, channel, deadline, fork/snapshot pin, authority) | Penalty-free declared request error; session kept.                                         |
| Stale pins at submission                                                                                      | Enforcement rejects; the joiner re-collects against fresh state.                           |

## Requirements and invariants

**<a id="inv-joinsig-1-jx5ec4"></a>`INV-JOINSIG-1-JX5EC4` — Identity triple-binding.** A countersignature is produced only when the join's
embedded signature, its declared participant, and the authenticated requesting peer all bind to the
same identity.

**<a id="inv-membership-pending-1-2h1t75"></a>`INV-MEMBERSHIP-PENDING-1-2H1T75` — Submitted joins are locally
pending before acknowledgement.** A first join MUST move the local runtime from `SYNCED` to
`PENDING_PARTICIPANT` before invoking transaction submission or crossing any asynchronous boundary that may
send it. This protects a potentially funded in-flight transaction from cleanup that applies only to an
uncommitted observer. A failure restores `SYNCED` and clears force-join state only when the outcome proves
that no commitment exists. An uncertain submission keeps local pending protection while chain state is
reconciled. The joiner records the join authorization deadline (the `deadlineTimestamp` of the join it
submitted). The chain admits a join only in a block whose timestamp is at most that deadline, so the join
can still land while the latest chain block is not past it. While it can still land, a pending joiner whose
join neither the installed state nor the chain lists MUST stay `PENDING_PARTICIPANT`, so that observing the
join still starts the escalation triggers. Once the latest chain block is past the deadline and the chain
does not list the signer, the join never landed and never can: the next state installation, or the join wait
of a terminal leave ([`REQ-TJOIN-7-NNGTAY` (Terminal channel leave)](targeted-channel-join.md#req-tjoin-7-nngtay)), returns the runtime to `SYNCED`.
Force-join escalation MUST wait until the signer is present in the authoritative on-chain participant union;
an absent signer or an unavailable authoritative read defers the check to a later relevant trigger without a
duplicate submission. A fork whose dispute window exists and whose evidence period has ended accepts no
new dispute: the joiner logs the refusal, both triggers end, and neither trigger retries. The pending join
is not lost. The chain admits a dispute only when it carries the latest on-chain inbound head, no join lands
on a disputed fork, and a reduction consumes the on-chain inbound queue up to its window's expiry. So the
next reduction of the fork seats the pending joiner, and the joiner needs no dispute of its own for that
(its more-evidence comparison finds nothing to add for the join).
Escalation has two triggers, and whichever comes first starts the one dispute. Both triggers start only
when the joiner observes its own join as an inbound message on chain, while it is still pending for that
submission; a transaction receipt or an "already a participant" refusal does not start them, because
the writers that must include the join cannot have seen it before it appears in the inbound stream. A
join that is never observed starts neither trigger. The block trigger counts blocks only after a grace:
counting starts `agreementTime` after the observation, measured on the joiner's own clock. A block counts
only when the joiner commits it once its own clock is at or after that time; block timestamps play no part,
so a block authored earlier counts when the joiner commits it after that time. The first
counted block is the counting start height, and escalation MUST NOT start before
`counting start height + current participant count + 1`; that exact height is the first eligible block.
The grace exists because the table's writers observe the join on chain only within `agreementTime`; a
fast table can author the `N + 1` blocks before its writers could include the join, and counting
those blocks would dispute honest writers. The time trigger: when the joiner observes its own join it
arms a local deadline of `N` full turn windows, where `N` is the current
participant count plus one (the same `N` turns as the block trigger) and one turn window is the full time a
scheduled author has before it can be timed out (`p2pTime + agreementTime + chainFallbackTime`, plus any
first-block grace, evaluated at `joinSubmissionHeight + 1`). When the deadline passes while the runtime is
still pending for the same submission and no trigger has fired, the joiner applies the same gates; only a
gate that defers re-arms the deadline for another full period. A trigger fires when it starts the dispute or
when the chain's expired evidence period refuses it. Either outcome cancels the deadline, and a fired
trigger never fires again for the same submission: a started dispute is never submitted a second time, and a
refused one is not retried.

**<a id="req-joinsig-1-8x1a4v"></a>`REQ-JOINSIG-1-8X1A4V` — Pinned-state authorization.** Both sides bind the authorization to an exact
on-chain snapshot and fork; a countersigner MUST refuse when its own current view differs from the
pin, and the collection's pins MUST be carried to submission.

**<a id="req-joinsig-2-rr2g4q"></a>`REQ-JOINSIG-2-RR2G4Q` — All-or-nothing unanimity.** The collection succeeds only with a verified
countersignature from every threshold member over the exact encoded join; any member's failure
fails the collection.

**<a id="req-joinsig-3-vagfvd"></a>`REQ-JOINSIG-3-VAGFVD` — Refusal is penalty-free.** A responder's validation failure is a declared error
without session or identity consequences; countersigning is voluntary cooperation, not an
obligation whose refusal is slashable.

## Assumptions and constraints

- Requires authenticated sessions and a current chain view on both sides; a lagging countersigner
  refuses honestly (pin mismatch) rather than authorizing blind.
- Deadline arithmetic uses protocol time ([time.md](../protocol-model/time.md)).
- A collector needs time to contact remote members, so it requires a deadline strictly after its
  current protocol time. A responder may sign at the exact deadline; enforcement applies the same
  inclusive deadline boundary at submission.
- The service is stateless across calls: every decision derives from the request plus live reads,
  so replay of a still-valid request yields another signature over the same bytes — idempotent by
  content.
- Admission policy (who _should_ be admitted, beyond structural validity) is deliberately outside
  this contract and open ([`OQ-10-04YNC4` (Spectate/join failure-point details)](../open-questions.md#oq-10-04ync4)).
- Force-join escalation under [`INV-MEMBERSHIP-PENDING-1-2H1T75`](join-authorization.md#inv-membership-pending-1-2h1t75) has
  a block trigger and a time trigger, so it does not depend on blocks arriving. Both start when the
  joiner observes its own inbound join; a joiner whose join never reaches the chain has no escalation. Such a
  join stays pending only while its authorization can still admit it, judged by the latest chain block's
  timestamp, not the local clock; after that, a terminal leave or the next state installation drops it
  ([`REQ-TJOIN-7-NNGTAY` (Terminal channel leave)](targeted-channel-join.md#req-tjoin-7-nngtay)). The block trigger's
  `agreementTime` grace assumes that an honest writer observes an on-chain join within one
  `agreementTime`, the same bound the protocol uses for every chain observation
  ([`OQ-SPEC-FORCE-JOIN-1-J4QZ2V` (Force-join trigger when no blocks arrive)](../open-questions.md#oq-spec-force-join-1-j4qz2v), decided 2026-10-02). The time trigger
  is a local timer: it measures the joiner's own elapsed time, not chain time, and it is not adjudicated.
  It lasts `N` full turn windows so that an honest but slow table, in which each scheduled author uses its
  whole window, still includes the join before the joiner escalates.

## Security considerations

The unanimity rule makes this service safety-relevant: a signature harvested here becomes part of a
membership change. Defenses: triple identity binding stops relayed or third-party collection;
byte-exact signing over the canonical encoding stops substitution between what was validated and
what was signed; state pinning stops authorization against a moved or forked state; threshold
membership stops non-members from manufacturing authority. Residual: unconditional signing of valid
requests means membership control is purely structural until the admission filter is decided
([`OQ-10-04YNC4` (Spectate/join failure-point details)](../open-questions.md#oq-10-04ync4)); a malicious joiner can burn responder attention (rate bounds per [`REQ-RPC-5-CV1R1Y` (Resource bounds)](rpc.md#req-rpc-5-cv1r1y)).

The force-join time trigger protects the joiner's deposit from being held pending forever by a table that
stops authoring blocks. Its threat is the reverse race: a joiner whose clock runs fast, or that ignores the
deadline, escalates while an honest table would still include the join. The deadline length (`N` full turn
windows) makes this rare for honest joiners. The trigger changes only when the joiner asks for the
dispute, not what the chain accepts: the dispute is adjudicated on chain like any other dispute input.
Residual: an early escalation costs the table one dispute pause on its fork.

The block trigger's grace protects honest writers from the same race on the block side. Without it, a
table that authors faster than its writers observe the chain reaches the trigger height before any
writer could include the join, and the joiner disputes a table that did nothing wrong. The grace is
measured on the joiner's local clock from the moment it observes its own inbound join, and a block counts by
the joiner's own clock when it commits the block, regardless of how it perceives block time; a fast clock
shortens it and can again cause one early dispute pause. The time
trigger is unchanged by the grace.

A refused escalation is not retried. This is safe for the joiner's deposit because the refusal means the
fork already has a dispute window: that window reduces, and its reduction consumes the joiner's inbound join
(a join cannot land on a disputed fork, and every admitted dispute carries the latest inbound head).
Residual: the joiner depends on someone completing that reduction; the escalation does not resume on its own
after a restart of the joiner, because the triggers are local, in-memory state.

Dropping an expired, unlisted join cannot strand a deposit: the chain refuses the join in every block after
the authorization deadline, so a join the chain does not list once a block past the deadline exists never
lands later.
