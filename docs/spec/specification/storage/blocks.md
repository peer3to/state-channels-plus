## Purpose and data model

The block store holds every committed block the node has accepted, addressable two ways that MUST
stay consistent: by block hash, and by coordinates (fork id, height). It tracks the highest stored
height per fork (the local tip) and each block's growing confirmation-signature set and optional
on-chain publication timestamp.

## Requirements and invariants

**<a id="inv-blkstore-1-mk4w8d"></a>`INV-BLKSTORE-1-MK4W8D` — Index consistency.** The hash index and the coordinate index always refer to the
same block objects: a store, signature merge, timestamp update, or delete through either key is
observable through both, and a delete removes the entry from both.

**<a id="req-blkstore-1-kyhtwt"></a>`REQ-BLKSTORE-1-KYHTWT` — Same-coordinate conflict is not resolved here.** Storing a block whose
coordinates are occupied by a _different_ block MUST be refused, not silently replaced; resolving
which block is canonical belongs to the validation and evidence rules of
[block-processing.md](../block-progression/block-processing.md) ([`REQ-BLOCK-PIPE-6-XQ0RTT` (Total-order application)](../block-progression/block-processing.md#req-block-pipe-6-xq0rtt)). Storing the
_same_ block again merges its signature set and, when present, its on-chain posting timestamp.

**<a id="req-blkstore-2-vwxp2c"></a>`REQ-BLKSTORE-2-VWXP2C` — Monotone signature merge.** Signature insertion only grows the set, is
idempotent, and never alters block identity. Which values it adds is bounded by
[`REQ-BLKSTORE-4-RQTR2Y`](blocks.md#req-blkstore-4-rqtr2y); a held signature is never removed. A known on-chain posting timestamp is never
discarded; no preference rule between conflicting values is needed, because such values cannot
legitimately coexist — the on-chain calldata commitment is author-bound, first-post-wins, and
non-overwritable ([data-availability.md](../security/data-availability.md)), and the annotation is
populated only from chain observation, never from gossiped payloads.

**<a id="req-blkstore-3-s9v2kc"></a>`REQ-BLKSTORE-3-S9V2KC` — Tip tracking and bounded traversal.** The per-fork maximum height advances only
on stores that extend the fork (a persistence-only store MAY opt out of tip advancement, e.g. when
backfilling proof data). Range and latest-block reads MUST clamp any caller-supplied bound to the
fork's known tip so a remote-supplied absurd height cannot force iteration over an empty range. Deleting the block at the fork's maximum height lowers the maximum to the height below (deletes
below the tip leave it unchanged); the store does not search for the next held block — history
contiguity makes the two equivalent.

**<a id="req-blkstore-4-rqtr2y"></a>`REQ-BLKSTORE-4-RQTR2Y` — One confirmation signature per signer.** A stored block
holds at most one confirmation signature per recovered signer. The first store keeps the first
confirmation signature offered for each signer. A later store or insertion adds a signature only
when its signer has none on the stored block yet; the signature already held is kept, never
replaced. A confirmation signature that recovers to the block author is not added, because the
author's original signature already counts for that signer. A value that recovers to no signer MUST
NOT be stored, on any store path. Recovery here means on-chain recovery: a re-encoding that the
chain rejects (a recovery byte other than 27 or 28, a 64-byte compact form, or a high `s`) recovers
to no signer even where a looser library recovers it, so it can never take the place of the
genuine signature. A value that is not a byte string is malformed
without any recovery attempt. Every store path classifies values this way before it stores them; a
sync payload is classified in full before its first write, so a failure cannot leave it half-applied.
A supplier of such a value on a gossip path gets the malformed-signature consequence. An author signature that recovers to no signer holds no signer
and MUST NOT make the store fail. A confirmation for an already-stored block that brings no new
signer changes nothing and is not relayed. One that brings new signers stores their first
signatures, and its relay MUST carry only those new-signer signatures, not the signatures the store
already held. Dropping a repeated signer's signature is silent: it is not treated as a fault of
its signer or its supplier. A value whose signer is outside the participant union stays a fault of
every source that supplied it, including a later value of the same outsider signer.

## Assumptions and constraints

- Callers store only blocks that passed their pipeline stage; the store checks keys and identity,
  not protocol validity.
- Deletion is a pipeline decision (e.g. fork replacement); the store only guarantees consistency.
- ECDSA allows one signer to produce many distinct valid signatures for one block hash, so byte
  equality cannot bound a signature set; the per-signer bound of
  [`REQ-BLKSTORE-4-RQTR2Y`](blocks.md#req-blkstore-4-rqtr2y) relies on signer recovery instead.
- Shared durability, retention, and integrity rules: [durability.md](./durability.md).

## Security considerations

The store defends read-path availability, not validity: clamped traversal prevents a
remote-supplied height from stalling the node; refusal of same-coordinate substitution prevents a
late duplicate from silently replacing accepted history; monotone merge prevents signature loss.
Equivocation evidence handling lives with block processing, not here.

The per-signer bound ([`REQ-BLKSTORE-4-RQTR2Y`](blocks.md#req-blkstore-4-rqtr2y)) defends memory,
gossip and on-chain proof cost. Without it a participant could resend fresh self-signatures for a
block honest peers already store: each batch would grow the stored set, be relayed to every peer,
and be copied into threshold evidence whose on-chain verification cost grows with every signature.
With the bound a stored block carries at most one confirmation signature per participant, and a
batch without a new signer produces no relay. Residual risk: each batch still costs the receiver
one signer recovery per value before it is dropped; the per-copy admission bound of the queue
limits that work per message. Dispute confirmations are not covered by this requirement.
