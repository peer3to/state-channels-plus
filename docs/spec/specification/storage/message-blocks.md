## Purpose and data model

Each store holds one hash-linked message-block chain: blocks keyed by their canonical-encoding hash,
plus a latest-tip pointer (hash and height). One instance holds the inbound stream (base layer →
channel), one the outbound (channel → base layer); the module contract is identical for both.

## Requirements and invariants

**<a id="req-msgstore-1-6me9d7"></a>`REQ-MSGSTORE-1-6ME9D7` — Content-addressed store with tip tracking.** A block is stored under the hash of
its canonical encoding. A store that does not opt out of tip advancement moves the latest-tip
pointer when no tip is held or the block's height is at least the tip height: an equal-height block replaces the tip,
a lower block leaves it, and linkage to the current tip is not required, so the tip MAY sit above a
gap in held history. A store operation MAY explicitly opt out of tip advancement: blocks persisted
only as proof material, and the blocks of a non-extending chain-verified run, use that opt-out and
never move the tip. Blocks recovered later from base-layer logs, and the inbound list of a window
this node reduced itself, use the tip-moving store and follow the height rule above. A store of a chain-verified run moves the tip only when
the run extends the current tip exactly — the run's predecessor hash equals the current tip's hash,
or the zero hash when no tip is held; otherwise its blocks are persisted and the tip stays. A read
from a tip above a gap follows [`REQ-MSGSTORE-2-8RDXPZ`](message-blocks.md#req-msgstore-2-8rdxpz) and reports the first missing block. A tip read against a snapshot returns the snapshot's head while the
store holds no tip or a lower one, so a reader never starts below the snapshot it works against. A
consumer never treats a truncated range as complete: it recovers the missing blocks first, skips
the range, or fails the operation. A consumer MAY use the linked part of a truncated range for an
additive observation whose missing part is recovered on demand (membership JOIN eligibility).

**<a id="req-msgstore-2-8rdxpz"></a>`REQ-MSGSTORE-2-8RDXPZ` — Linked backward range reads.** A range read walks the chain backward by
`previousBlockHash` from an upper bound (inclusive) to a lower bound (exclusive), returning the
linked blocks in between. A break in linkage or an absent block ends the walk with exactly the
blocks proven linked so far and an explicit incomplete result. A requested range is complete only
when the walk reaches its lower bound. Reaching the zero hash first does not satisfy a nonzero
lower bound, and a zero upper bound is an empty complete range only when the lower bound is also
zero. The store never bridges gaps or substitutes blocks by height. An
implementation MAY additionally expose an all-or-nothing read that fails on any gap, for callers
whose precondition is a complete run; the truncating read remains the range-read contract.

## Assumptions and constraints

- Chain validity (height increments, cumulative totals) is verified by settlement and enforcement;
  the store keeps and returns what was committed.
- The inbound and outbound instances share no state; a block stored in one is invisible to the
  other.
- Inbound blocks reach a tip-moving store from three sources: the base-layer event feed (trusted;
  this includes logs re-read from the base layer to recover a missed delivery), a chain-verified run carried by a committed block, and the inbound list of a window this node
  reduced itself during synchronization. The verified run and the self-reduced window's list are
  checked before they are stored; the event feed is stored without a check because the base-layer
  feed is a trust boundary. A wrong block from the feed is a base-layer reorg or a forged event; the
  store does not arbitrate it.
- The height tip is deliberate. A node that missed an inbound block still tracks the latest
  delivered inbound head. Block production carries no inbound blocks until the run is linked;
  dispute construction names that head and recovers the run from the base layer.
- Shared durability/retention rules: [durability.md](./durability.md).

## Security considerations

Range reads feed settlement proofs and sync payloads; returning a gap-bridged or height-substituted
range would turn a storage convenience into a forged linkage claim, which is why
[`REQ-MSGSTORE-2-8RDXPZ`](message-blocks.md#req-msgstore-2-8rdxpz) forbids it. The tip is a height pointer, not a linkage claim: it grants no validity to the chain
itself, and only a range read proves linkage. The store does not judge between two blocks at the
tip height; the later one becomes the tip.
