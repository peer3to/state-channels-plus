## Purpose and data model

Proof construction ([`REQ-SP-8-9ZCCEJ`](../disputes/state-proofs.md#req-sp-8-9zccej)) derives a state proof from the mirrored chain anchor and the
node's block history. Each reader that needs a proof repeats that derivation, and each derivation
walks every membership hop above the anchor again. This module keeps one **stored proof** per active fork
instead. The node extends it as finality is reached, rebuilds only its newest milestone on demand,
re-roots it when the chain anchor advances, and starts a new one when the active fork changes.
Blocks that only support the proof live inside it, not in block history. Because the kept part of
the proof does not depend on the blocks between its runs, ordinary blocks that no kept run needs can
later be pruned.

The aim is direct access to the stored proof. It does not make proof size, encoding, verification,
or update cost constant.

Terms used in this document:

- **Construction anchor.** The start of the stored proof: the mirrored same-fork chain anchor, or
  the fork genesis when the chain holds no snapshot on the active fork ([`REQ-SP-4-NCSEX4`](../disputes/state-proofs.md#req-sp-4-ncsex4),
  [`REQ-SP-8-9ZCCEJ`](../disputes/state-proofs.md#req-sp-8-9zccej)).
- **Kept milestone.** A milestone of the stored proof whose run proves the first block of a
  membership hop after the anchor final. That run is the hop's evidence.
- **Stored prefix.** The anchor and the kept milestones, in order.
- **Final point record.** The latest proved final point: its block, its snapshot commitment, and
  the full application state at it.
- **Newest milestone.** The milestone that proves the latest final point, together with the
  unfinalized tail above it. It is rebuilt on demand from the final point record, the support the
  stored proof holds for it, and the block history above the record.
- **Projection.** A proof built from the stored proof that ends at a final point below the final
  point record. It keeps the kept milestones that start at or below that point unchanged and leaves
  the stored proof unchanged ([`REQ-PROOFSTORE-4-ZFCWNB`](proof-store.md#req-proofstore-4-zfcwnb)).
- **Proven history and support.** A checked block of a verified proof is proven history when the
  proof proves it final — a threshold-final milestone first block, a matching anchor block, or a
  hash ancestor of one of them inside the proof — or when it has executed through tail replay.
  Every other checked block is support.

The module is keyed by channel and fork ([`REQ-STOR-5-T6EQSA` (Isolation, integrity, and versioned encoding)](durability.md#req-stor-5-t6eqsa)). It holds the stored prefix with one
supporting snapshot per milestone, the support blocks of the kept runs and of the newest milestone,
and the final point record. A tail block that has executed is block history; a tail block that has
not executed, for example after a failed tail replay, is support. The blocks, snapshots, full state
and support that prove the recorded final point stay readable while the record names it, so the
node can still prove that point when tail replay fails or is interrupted
([`REQ-PROOFSTORE-1-G11DH7`](proof-store.md#req-proofstore-1-g11dh7)).

For example, the chain anchor is 50 with participants A, B, C, D and E. F joins at block 60. Block
60 carries signatures from A to E, and its successor 61 carries F's signature, so [60, 61] proves
the hop final. Later, block 75 carries all six signatures. The stored proof is anchor 50, the kept
milestone [60, 61], and a final point record for 75; the newest milestone [75] is rebuilt on
demand. In phase 1, nothing above the anchor is pruned. In phase 2, blocks 62–74 could be pruned,
because neither the kept run nor the newest milestone needs them. Whether blocks 51–59, between the
anchor and the first kept run, could also go is
[`OQ-SPEC-PROOFSTORE-2-V4N7VH` (Pruning above the anchor and lost exact-height checks)](../open-questions.md#oq-spec-proofstore-2-v4n7vh). When the chain adopts 75, the
stored proof re-roots at 75 and keeps only the anchor claim [75].

## Requirements and invariants

**<a id="req-proofstore-1-g11dh7"></a>`REQ-PROOFSTORE-1-G11DH7` — One stored proof per active fork.** Phase 1. A node MUST hold at most one
stored proof per channel, and only for its active fork. The stored proof starts at the construction anchor of
[`REQ-SP-8-9ZCCEJ`](../disputes/state-proofs.md#req-sp-8-9zccej): the mirrored same-fork chain anchor, which may lag the chain but must not lead it,
or the fork genesis when there is none. A peer's newer private final point is never its anchor. The
stored proof holds the kept milestones after the anchor in order, one supporting snapshot per
milestone ([`REQ-SP-7-70EMAT`](../disputes/state-proofs.md#req-sp-7-70emat)), and the final point record. When the anchor is itself the latest
final point, it holds the anchor claim: the anchor block in a milestone, matched by its exact
snapshot commitment, with its snapshot and full state ([`REQ-SP-4-NCSEX4`](../disputes/state-proofs.md#req-sp-4-ncsex4), [`REQ-SP-10-JMVHTB`](../disputes/state-proofs.md#req-sp-10-jmvhtb)). Only
data that the proof rules of [state-proofs.md](../disputes/state-proofs.md) verified enters the
stored proof. Storage grants no validity: whatever the node reads back re-enters verification
([`REQ-STOR-3-4RJGER` (Restart recovery without trust)](durability.md#req-stor-3-4rjger)). Every proof the node yields from the stored proof MUST verify from its
anchor.

**<a id="inv-proofstore-1-5kg1nx"></a>`INV-PROOFSTORE-1-5KG1NX` — Proof support stays evidence.** Phase 1. Support is kept only inside the
stored proof. It keeps its signatures for proof reconstruction, but it never occupies block
history, never moves the installed head, and never grounds a history conflict, a persistence
abort, or an invalid-transition accusation. The installed head never rises above the proven
endpoint, the proof's latest proved final point, before the tail replay. For example, a proof whose
earlier milestone holds an honest run 60–70 and a forged 71′ by another author, and whose later
milestone starts at the real final 71, keeps 71′ as support only; it never displaces the real 71.

**<a id="req-proofstore-2-99rrxk"></a>`REQ-PROOFSTORE-2-99RRXK` — Seeding from a verified proof.** Phase 1. After a received proof verifies in
synchronization ([`REQ-SP-10-JMVHTB`](../disputes/state-proofs.md#req-sp-10-jmvhtb)), the node MUST write into the stored proof of that fork the
verified start, the kept milestones that reconstruction needs with their supporting snapshots, and
the final point record. It writes only changed data and never unchecked skipped history. Support
from the received proof stays in the stored proof ([`INV-PROOFSTORE-1-5KG1NX`](proof-store.md#inv-proofstore-1-5kg1nx)), including the support of the
newest milestone, which proves the installed final point until the tail has executed. Seeding is
part of the atomic persist step of synchronization
([synchronization.md](../peer-communication/synchronization.md#requester-algorithm-verification-before-effect),
step 12): it becomes visible together with the installed state, an install that aborts publishes
none of it, and a later failure of tail replay does not undo it. Applying the same verified proof
again changes nothing. How a received proof combines with an existing stored proof
of the same fork, and whether a proof verified in dispute audit also seeds it, is
[`OQ-SPEC-PROOFSTORE-4-DZSGJP` (Merging a received or longer proof into the stored proof)](../open-questions.md#oq-spec-proofstore-4-dzsgjp).

**<a id="req-proofstore-3-qdxnh9"></a>`REQ-PROOFSTORE-3-QDXNH9` — Extension keeps earlier evidence.** Phase 1. When a membership hop above the
stored prefix is proved final under [`REQ-SP-3-SP1JG4`](../disputes/state-proofs.md#req-sp-3-sp1jg4), the node MUST append it to the stored proof
as a kept milestone whose evidence alone proves its first block final. When a later point is proved
final, the node MUST advance the final point record; the record never moves down on the same fork.
A newer final point never authorizes removing an older kept milestone or the support that proves
it. A kept run may be replaced or shortened only by evidence that by itself proves the same first
block final. Missing signatures are not missing data: an unfinalized hop stays in the tail and is
not appended ([`REQ-SP-8-9ZCCEJ`](../disputes/state-proofs.md#req-sp-8-9zccej)). For example, if the hop at 60 needs the run 60–65 for its votes,
that run stays after 75 becomes final; [60, 61] may replace it only if those two blocks carry the
whole required union. Which hops are kept is [`OQ-SPEC-PROOFSTORE-3-F9HWYC` (Which membership hops the stored proof keeps)](../open-questions.md#oq-spec-proofstore-3-f9hwyc). Whether extension
happens during a build or through incremental vote counting is [`OQ-SPEC-PROOFSTORE-7-TJW3H8` (Extending the stored proof on demand or by vote tracking)](../open-questions.md#oq-spec-proofstore-7-tjw3h8).

**<a id="req-proofstore-4-zfcwnb"></a>`REQ-PROOFSTORE-4-ZFCWNB` — Construction above the stored prefix.** Phase 1. Construction of the latest proof under
[`REQ-SP-8-9ZCCEJ`](../disputes/state-proofs.md#req-sp-8-9zccej), at a requested head at or above the final point record, MUST reuse the stored
prefix unchanged and search only above it: backward from the requested head, no lower than the
final point record, for the latest point that can be proved final, its milestone, and the linked
tail. It MUST NOT re-walk or rebuild kept milestones. The result MUST prove the same latest final
point and latest claimed state that construction from complete history would prove from the same
evidence, and it MUST verify from the anchor. A proof that must end at a lower final point is a
projection. It keeps unchanged only the kept milestones whose first block lies at or below that
point. When none of them starts at that point, it adds one last milestone that proves the point
from the evidence the node holds at and above it: block history, and the runs and support of the
stored proof, including virtual votes from later blocks. A projection never changes the stored
proof and MUST verify from the anchor. When that evidence is absent, the outcome is
[`OQ-SPEC-PROOFSTORE-11-J7D4H1` (Missing-evidence policy with pruned storage)](../open-questions.md#oq-spec-proofstore-11-j7d4h1); the absence is never evidence ([`INV-PROOFSTORE-2-NT5FD6`](proof-store.md#inv-proofstore-2-nt5fd6)). For
example, with kept hops at 60 and 80 and a final point record at 100, a proof ending exactly at 70
keeps the hop at 60, leaves out the hop at 80, and proves 70 from blocks 70 and above. Whether the
final point record can lie above the active head, and what a read at a requested head below the
record returns, is [`OQ-SPEC-PROOFSTORE-4-DZSGJP` (Merging a received or longer proof into the stored proof)](../open-questions.md#oq-spec-proofstore-4-dzsgjp).

**<a id="req-proofstore-5-vnqgdg"></a>`REQ-PROOFSTORE-5-VNQGDG` — One proof source for every reader.** Phase 1. Every reader that needs a proof from
the construction anchor MUST obtain it from the stored proof through [`REQ-PROOFSTORE-4-ZFCWNB`](proof-store.md#req-proofstore-4-zfcwnb): the
synchronization responder
([synchronization.md](../peer-communication/synchronization.md#responder-algorithm-proving-the-latest-state),
step 4), the node's own dispute construction, dispute audit and its local final-state tier
([`REQ-SP-9-RNXP56`](../disputes/state-proofs.md#req-sp-9-rnxp56)), the same-fork snapshot update ([`REQ-SP-8-9ZCCEJ`](../disputes/state-proofs.md#req-sp-8-9zccej)), and the counters that need a
proved final point ([fraud-proofs.md](../disputes/fraud-proofs.md)). A read yields its proof from
these inputs: the anchor, the stored proof, the evidence above the final point it proves, the
requested head, and the mode, either with the unfinalized tail or with the final point only, as a
snapshot update needs. Two reads with the same inputs yield the same proof. A late signature can let
a later point be proved final without moving the head, so a read after it can prove a newer final
point or use a shorter run; a result is not reused once any of its inputs has changed. A reader that
needs a proved final point at an exact height, such as the final-state conflict counter, obtains the
projection of [`REQ-PROOFSTORE-4-ZFCWNB`](proof-store.md#req-proofstore-4-zfcwnb) that ends at that height. On a node that never held, or no longer
holds, the history at that height, the outcome is
[`OQ-SPEC-PROOFSTORE-11-J7D4H1` (Missing-evidence policy with pruned storage)](../open-questions.md#oq-spec-proofstore-11-j7d4h1).

**<a id="req-proofstore-6-38g1kc"></a>`REQ-PROOFSTORE-6-38G1KC` — Re-rooting on anchor advance.** Phase 1. When the mirrored chain anchor
advances on the active fork, the node MUST re-root the stored proof at the new anchor. Kept
milestones wholly below the new anchor are dropped. A run that contains the anchor keeps its suffix
from the anchor ([`REQ-SP-4-NCSEX4`](../disputes/state-proofs.md#req-sp-4-ncsex4)). A run contains the anchor only when its block at the anchor
height matches the anchor's exact snapshot commitment. A kept run that reaches the anchor height
with a different block there, such as support that conflicts with the adopted block, is dropped
like a run wholly below the anchor, and the milestones above it stay unchanged. For example, with a
kept run 60–70 followed by a forged 71′ and a final point record at 75, adoption of the real 71
drops that run and keeps the milestone that proves 75. When the new anchor is the latest final point, the stored proof
keeps the anchor claim: the anchor block in a milestone, matched by its exact snapshot commitment,
with its snapshot and full state. An empty milestone list is never used for a non-genesis anchor,
because it would claim fork genesis. Only a chain anchor advance re-roots the proof; a newer local
final point alone never does. Whether re-rooting waits for base-layer finality of the adoption is
[`OQ-SPEC-PROOFSTORE-8-QR7WWQ` (Re-rooting and base-layer finality of the adoption)](../open-questions.md#oq-spec-proofstore-8-qr7wwq). For example, with the kept milestone [60, 61] and final point 75
above anchor 50, adoption of 75 re-roots the stored proof to the anchor claim [75]; the hop at 60 is
dropped because the chain anchor moved past it, not because 75 became final.

**<a id="req-proofstore-7-t0ebmx"></a>`REQ-PROOFSTORE-7-T0EBMX` — Reset on fork change.** Phase 1. When the active fork changes, the node MUST
discard the old fork's stored proof and start a new stored proof for the new active fork at that
fork's construction anchor: its genesis until the chain adopts a snapshot on it. Nothing from the
old stored proof enters the new one. After the reset, a pinned request for the old fork is served
through a verified successor or refused ([`REQ-SYNC-1-T2589H` (Minimum-target proving)](../peer-communication/synchronization.md#req-sync-1-t2589h)). Which other old-fork data the node
keeps, including the lineage records such an answer needs, and for how long, is
[`OQ-SPEC-PROOFSTORE-5-W48ZR6` (Old-fork data after a fork change)](../open-questions.md#oq-spec-proofstore-5-w48zr6).

**<a id="req-proofstore-8-xwemtj"></a>`REQ-PROOFSTORE-8-XWEMTJ` — Pruning below the on-chain snapshot.** Phase 1. A node MAY prune block
history, snapshots, full states, message blocks, and change points of the active fork strictly
below the mirrored chain anchor, and only when [`REQ-STOR-4-MF6FT6` (Obligation-bounded retention)](durability.md#req-stor-4-mf6ft6) permits it. In phase 1 it MUST
NOT prune data at or above the anchor, data that the stored proof still holds or names, or what a
synchronization payload carries: the fork genesis snapshot, its encoded state, and the outbound
message-block range from the on-chain tip to the fork genesis
([synchronization.md](../peer-communication/synchronization.md#responder-algorithm-proving-the-latest-state),
step 4). The participant union of the anchor block reads the snapshot of the block below it
([`REQ-SNAPSTORE-2-Q7E6TQ` (Derived reads fail explicitly)](snapshots-and-states.md#req-snapstore-2-q7e6tq)); how that input survives pruning is part of the retention rule. The rule
that decides when below-anchor data may go is [`OQ-SPEC-PROOFSTORE-1-SW4ZGT` (Retention rule for pruning below the on-chain snapshot)](../open-questions.md#oq-spec-proofstore-1-sw4zgt). Full-state retention
is [`OQ-SPEC-PROOFSTORE-6-X70EWK` (Full-state retention)](../open-questions.md#oq-spec-proofstore-6-x70ewk).

**<a id="inv-proofstore-2-nt5fd6"></a>`INV-PROOFSTORE-2-NT5FD6` — Absence is never evidence.** Phases 1 and 2. Data that is absent from local
storage because it was pruned, or because a compact proof never carried it, MUST NOT be read as
evidence of fraud, of a conflict, or of an invalid transition. No counter, fraud proof, slash, peer
punishment, or history conflict may rest on that absence. A reader that needs absent data treats it as unavailable
under its owner's rules; local ignorance alone is never a valid accusation
([`REQ-DISPUTE-PIPE-5-RZZB48` (Mirrored canonical audit)](../disputes/dispute-processing.md#req-dispute-pipe-5-rzzb48)). Missing signatures are different: they can lower the proved final
point and leave a valid tail ([`REQ-SP-8-9ZCCEJ`](../disputes/state-proofs.md#req-sp-8-9zccej)). Which absent data makes a reader fail, skip a
check, or lower its result is [`OQ-SPEC-PROOFSTORE-11-J7D4H1` (Missing-evidence policy with pruned storage)](../open-questions.md#oq-spec-proofstore-11-j7d4h1).

**<a id="req-proofstore-9-czta0n"></a>`REQ-PROOFSTORE-9-CZTA0N` — Pruning between proven parts of the stored proof.** Phase 2. This
requirement takes effect only after [`OQ-SPEC-PROOFSTORE-2-V4N7VH` (Pruning above the anchor and lost exact-height checks)](../open-questions.md#oq-spec-proofstore-2-v4n7vh) is decided and
[`REQ-STOR-4-MF6FT6` (Obligation-bounded retention)](durability.md#req-stor-4-mf6ft6) is changed to match; until then it permits nothing. Once in effect, a node MAY
prune an ordinary block above the anchor on the active fork when all of these hold: it lies in a gap
between two independently proven milestone runs of the stored proof (the kept milestone runs and
the newest milestone); no kept run needs it as evidence; it is neither the final point nor in the
tail; and no window, accepted duty, or reader named by that decision still needs it. Whether the
range between the anchor and the first such run also counts as a gap is part of that decision. Each
kept membership-hop milestone keeps evidence that by itself proves its own first block final
([`REQ-PROOFSTORE-3-QDXNH9`](proof-store.md#req-proofstore-3-qdxnh9)). A pruned height then reads as absent ([`INV-PROOFSTORE-2-NT5FD6`](proof-store.md#inv-proofstore-2-nt5fd6)). For
example, with anchor 50, the kept milestone [60, 61], and final point 75, blocks 62–74 may be
pruned; if the hop at 60 needs the run 60–65, the gap is only 66–74.

## Assumptions and constraints

- The stored proof uses the existing milestone form and verification rules of
  [state-proofs.md](../disputes/state-proofs.md). It is local, off-chain data: no contract or
  verification rule changes. Separated milestone runs already verify
  ([`REQ-SP-10-JMVHTB.T4.P8`](../disputes/state-proofs.md#req-sp-10-jmvhtb.t4.p8)).
- Direct access is the aim. The stored proof spares the walk over history, but proof size,
  encoding, verification, and update cost still grow with the kept milestones
  ([`OQ-SPEC-PROOFSTORE-10-ETB3H1` (Snapshot updates that bound the stored proof)](../open-questions.md#oq-spec-proofstore-10-etb3h1), [`OQ-32-5NDD24` (Proof and audit size bounds)](../open-questions.md#oq-32-5ndd24)).
- The construction anchor follows the local mirror of the chain anchor, which may lag the chain but
  never leads it ([`REQ-SP-8-9ZCCEJ`](../disputes/state-proofs.md#req-sp-8-9zccej)). A private final point never replaces it.
- Phase 1 prunes nothing above the anchor, but that does not make history above the anchor
  complete. A node that executed every block above the anchor holds them all. A node seeded by
  synchronization can lack history between the anchor and its first kept run and between kept runs
  ([`REQ-SP-10-JMVHTB.T4.P8`](../disputes/state-proofs.md#req-sp-10-jmvhtb.t4.p8)), and support exists only in the stored proof
  ([`INV-PROOFSTORE-1-5KG1NX`](proof-store.md#inv-proofstore-1-5kg1nx)). A reader that needs a block at an exact height above the anchor
  depends on which case applies ([`OQ-SPEC-PROOFSTORE-11-J7D4H1` (Missing-evidence policy with pruned storage)](../open-questions.md#oq-spec-proofstore-11-j7d4h1)). Phase 2 also removes executed
  history in gaps, and with it the history contiguity that [`REQ-BLKSTORE-3-S9V2KC` (Tip tracking and bounded traversal)](blocks.md#req-blkstore-3-s9v2kc) and
  [`REQ-SNAPSTORE-2-Q7E6TQ` (Derived reads fail explicitly)](snapshots-and-states.md#req-snapstore-2-q7e6tq) rely on.
- Pruning below the anchor already removes the block below the anchor block, whose snapshot the
  participant union of the anchor block reads ([`REQ-SNAPSTORE-2-Q7E6TQ` (Derived reads fail explicitly)](snapshots-and-states.md#req-snapstore-2-q7e6tq)). How that input is kept
  or replaced is [`OQ-SPEC-PROOFSTORE-1-SW4ZGT` (Retention rule for pruning below the on-chain snapshot)](../open-questions.md#oq-spec-proofstore-1-sw4zgt).
- Whether the stored proof survives a restart, and which of its contents must, is

- The order in which writers and readers of the stored proof take effect is
  [`OQ-SPEC-PROOFSTORE-12-BDFC1J` (Ordering of stored-proof writers and readers)](../open-questions.md#oq-spec-proofstore-12-bdfc1j). Each single operation follows

- Finality evidence is distinct from application-state validity. The stored proof proves which
  points are final; it does not prove that every application transition was correct.
- Shared durability, retention, and integrity rules: [durability.md](./durability.md). Behavior is
  the same on every supported host ([`REQ-RUNTIME-4-B0N70Y` (Platform equivalence)](../runtime/execution.md#req-runtime-4-b0n70y)).

## Security considerations

Protected assets are the node's ability to prove its latest final state, to serve verifiable
synchronization, and to audit and contest disputes, and the integrity of its block history. The
trust boundary is proof intake: a received proof is untrusted until it verifies, and the stored
proof is untrusted again when it is read back.

- **Poisoned history.** A verified proof can carry signed support blocks that never executed,
  including a forged block at a height whose real block is final in a later milestone. Stored as
  history, such a block could displace the honest block, move the installed head, or ground a false
  invalid-transition counter against an honest author. [`INV-PROOFSTORE-1-5KG1NX`](proof-store.md#inv-proofstore-1-5kg1nx) keeps support out
  of history and caps the head at the proven endpoint.
- **Absence as accusation.** Pruned or never-stored data can be mistaken for proof that a block,
  message, or state never existed, and an honest author slashed. A pruned participant-union input
  can make an honest relay's valid signature look like one from outside the channel, and the relay
  punished. [`INV-PROOFSTORE-2-NT5FD6`](proof-store.md#inv-proofstore-2-nt5fd6) forbids both readings.
- **Stale writes.** A seed, extension, or build computed before a fork change, an anchor advance, or
  a prune can publish evidence that the stored proof already dropped, or read data that pruning
  removed. [`REQ-PROOFSTORE-1-G11DH7`](proof-store.md#req-proofstore-1-g11dh7) and [`REQ-PROOFSTORE-7-T0EBMX`](proof-store.md#req-proofstore-7-t0ebmx) fix what may never be published; the ordering
  contract is [`OQ-SPEC-PROOFSTORE-12-BDFC1J` (Ordering of stored-proof writers and readers)](../open-questions.md#oq-spec-proofstore-12-bdfc1j).
- **Premature pruning.** Deleting evidence while a window is open, or while an accepted duty needs
  it, turns a contestable fault into an unenforceable claim. [`REQ-PROOFSTORE-8-XWEMTJ`](proof-store.md#req-proofstore-8-xwemtj) keeps phase 1
  inside [`REQ-STOR-4-MF6FT6` (Obligation-bounded retention)](durability.md#req-stor-4-mf6ft6); [`REQ-PROOFSTORE-9-CZTA0N`](proof-store.md#req-proofstore-9-czta0n) waits for [`OQ-SPEC-PROOFSTORE-2-V4N7VH` (Pruning above the anchor and lost exact-height checks)](../open-questions.md#oq-spec-proofstore-2-v4n7vh).
- **Anchor reversal.** If the chain removes an adoption after the node re-rooted on it, the dropped
  prefix is gone and the stored proof starts at an anchor the chain no longer holds. Verification
  then falls back to the chain tier ([`REQ-SP-9-RNXP56`](../disputes/state-proofs.md#req-sp-9-rnxp56)); the re-root trigger is
  [`OQ-SPEC-PROOFSTORE-8-QR7WWQ` (Re-rooting and base-layer finality of the adoption)](../open-questions.md#oq-spec-proofstore-8-qr7wwq).
- **Hostile merge.** A received proof could replace honest evidence of a kept hop, or carry a lower
  final point. [`REQ-PROOFSTORE-3-QDXNH9`](proof-store.md#req-proofstore-3-qdxnh9) allows only replacement evidence that proves the same first
  block by itself and never lowers the final point record; the merge rule is
  [`OQ-SPEC-PROOFSTORE-4-DZSGJP` (Merging a received or longer proof into the stored proof)](../open-questions.md#oq-spec-proofstore-4-dzsgjp).
- **Growth.** Kept milestones accumulate between anchor advances, and a participant that forces many
  membership changes grows every peer's stored proof. The bound is a snapshot update
  ([`OQ-SPEC-PROOFSTORE-10-ETB3H1` (Snapshot updates that bound the stored proof)](../open-questions.md#oq-spec-proofstore-10-etb3h1)) and the proof size limits of [`OQ-32-5NDD24` (Proof and audit size bounds)](../open-questions.md#oq-32-5ndd24).

Residual exposure: below the anchor, stale claims meet the chain anchor itself. A dispute below it
meets the below-anchor counter, and a timeout at or below it is superseded by the anchor
([fraud-proofs.md](../disputes/fraud-proofs.md)). Block fraud proofs have no window, so pruning
below the anchor gives up block fraud proofs whose evidence lay only in pruned blocks, such as an
old double sign; the adopted snapshot has already settled that history. Phase 2 also gives up, at
pruned heights, the exact-height checks that [`OQ-SPEC-PROOFSTORE-2-V4N7VH` (Pruning above the anchor and lost exact-height checks)](../open-questions.md#oq-spec-proofstore-2-v4n7vh) lists.
