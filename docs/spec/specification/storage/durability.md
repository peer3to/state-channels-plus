## Purpose and observable model

A participant's protocol obligations outlive its process. After a crash or restart, an honest node
must still be able to resume execution from its committed position, serve synchronization to peers,
detect and contest invalid on-chain actions within their windows, and complete any dispute or
recovery it had begun. Durable storage is the only local basis for all of that: whatever the protocol
may later require the node to _prove, replay, or contest_ must survive; whatever survives is still
untrusted input to the validation pipelines when it is read back.

The disk medium is a write-behind copy of memory. Memory stays the copy every read uses; disk lags it
and holds a consistent earlier point of it, loaded once when the channel is bound. A signature that
could get the node slashed leaves the process only after disk has confirmed everything stored before
it, so whatever a peer or the chain has seen from this node survives a crash. Lost writes that never
left the process are recovered from peers by the first synchronization after restart. Persistence is
enabled per runtime by its integrator.

## Requirements and invariants

**<a id="req-stor-1-d4xe73"></a>`REQ-STOR-1-D4XE73` — Complete durable set.** A node MUST keep durably, per channel and fork, every datum in
the [durable data classes](#durable-data-classes) that a protocol obligation could still require:
resuming execution, serving verifiable synchronization, constructing state proofs, meeting
watchtower/contest duties within open windows, and completing begun disputes or recovery. Data whose
loss silently converts an honest node into one that cannot meet an obligation is in the durable set
by definition.

**<a id="req-stor-2-tarp8s"></a>`REQ-STOR-2-TARP8S` — Commit-aligned durability.** Durable writes commit atomically with the owning
operation's effect boundary: a block and its consequences commit together
([`INV-BLOCK-PIPE-1-1AB2ME` (Atomic ordered commit)](../block-progression/block-processing.md#inv-block-pipe-1-1ab2me)); dispute evidence and actions
converge or stay retryable ([`REQ-DISPUTE-PIPE-4-3YVDSA` (Atomic recovery)](../disputes/dispute-processing.md#req-dispute-pipe-4-3yvdsa)); temporary
work never reaches durable state without a successful commit
([`REQ-SDK-ARCH-4-GTN7QN` (Execution isolation)](../runtime/sdk.md#req-sdk-arch-4-gtn7qn)). Observable events describe only durably committed transitions.

**<a id="req-stor-3-4rjger"></a>`REQ-STOR-3-4RJGER` — Restart recovery without trust.** A restarted node recovers from its durable set
and its first synchronization after the restart. Every datum read back re-enters the owning
validation pipeline as untrusted input — storage grants persistence, never validity — and recovery
is bounded: it either converges to the committed position or fails explicitly; it MUST NOT
half-apply. A restarted participant MUST install its own durable head (the latest stored block on
the persisted head fork, or that fork's genesis when it holds no block) before it serves or requests
any synchronization, and reconcile that head with one chain read: refill the local copies of the
chain's snapshot and of the dispute windows of its head fork and of every fork it marked as disputed;
clear a dispute marker whose dispute the chain does not hold, unless a transaction it sent may still
be unmined; and re-arm the on-chain posting of its own latest block, which runs on its own timer and
may post during the hold below, because that block carries a signature made before the crash. A
failed chain read fails the restore, and with it the persistent start: a head that read did not
reconcile is stale. It MUST then stay `SYNCED` — no block co-signature, join countersignature or
dispute from the restored head, no block authored or executed, no turn notification, no
participant-timeout action — until its first synchronization after the restart settles. That
synchronization may itself install a newer state and co-sign, notify a turn and arm a participant
timeout from it; nothing acts on the restored head. Held at `SYNCED`, it
audits no dispute, since only a committed participant audits, so it kills nothing and adds no
evidence until that synchronization settles; a dispute posted during the hold is not audited again
at release ([`FIND-STORAGE-13-3A4RES`](../../audit/open-findings.md#find-storage-13-3a4res)). When that synchronization fails for any reason (a failed or
undecodable answer, silence or a lost transport included) or its deadline passes with no participant
answering, it MUST abort as an observer does and arm nothing from the restored
head. Writes lost in the crash are own data that never left the process (and so never happened) or
peer data that the synchronization refetches. Recovery assumes the node stays online: chain events
after its last durable observation cursor are not replayed and a pending join is not resumed, and a
node offline through a contest window relies on a delegate
([`REQ-TRUST-4-KW24NF`](../security/trust-model.md#req-trust-4-kw24nf)).

**<a id="req-stor-4-mf6ft6"></a>`REQ-STOR-4-MF6FT6` — Obligation-bounded retention.** Data MAY be pruned only when no protocol obligation
can still require it: the relevant windows (dispute, kill, challenge, contest) are expired, the
on-chain snapshot has advanced past it, and no synchronization or watchtower duty the node has
accepted still depends on it. Pruning MUST NOT remove evidence needed to contest within any window
that is still open or can still be opened against retained state.

**<a id="req-stor-5-t6eqsa"></a>`REQ-STOR-5-T6EQSA` — Isolation, integrity, and versioned encoding.** Stores are keyed by channel and fork;
one channel's data can neither shadow nor corrupt another's. Corruption MUST be detected and fail
closed — a node serves no data it cannot verify against its commitments. Stored encodings carry
enough version identity that a later software revision either reads them correctly or refuses
explicitly; silent reinterpretation is prohibited. A load that meets a record it cannot decode, a
collection it does not know, an encoding version other than its own, a missing or different
partition identity, a head fork whose stored blocks do not link from the lowest stored height to the
head (height 0 linking to the fork's genesis snapshot), or no snapshot and state at the head MUST
refuse the bind, name the partition and the offending key, and release the medium; the node then
joins no transport and signs nothing for that channel. Only the head fork's chain is checked for
completeness: a node that joined by synchronization holds blocks above its anchor and the state at
its install point only. Discarding a partition to start as a fresh node is an explicit integrator
choice, never automatic, because it forgets the node's own signatures.

**<a id="req-stor-6-skp0km"></a>`REQ-STOR-6-SKP0KM` — Value semantics at the store boundary.** Every store operation exchanges
values, not references. A store MUST copy what a caller hands it and MUST copy what it hands back,
so that no object is reachable from both the caller and the store's own state. This holds for every
read shape without exception — reads by key, by coordinates, by range or index, and sequential
reads that yield entries one at a time. Consequently the only way to change stored data is an
explicit store operation: a caller that mutates a value it received MUST NOT thereby alter what a
later read returns, and a caller that mutates a value it previously stored MUST NOT thereby alter
stored state. The medium is irrelevant to this rule — it states the semantics a serializing backing
store gives for free, so an in-memory realization MUST NOT be observably weaker. A read that completes
asynchronously hands back a copy as well.

**<a id="req-stor-7-k1j7ea"></a>`REQ-STOR-7-K1J7EA` — Write-behind disk copy loaded once.** With persistence enabled, memory
MUST stay the copy every read uses and disk a write-behind copy of it: store operations and their
synchronous reads keep their contract, and no read goes to disk. Disk only lags memory, so a key
absent from memory is absent from disk. The disk copy MUST be loaded in full, in one all-or-nothing
pass, when the channel is bound and before any chain listener, transport join, or signature for that
channel; a load into a store that already holds a record MUST be refused rather than overwrite it.
Each synchronous storage step MUST reach disk as one atomic batch, and a batch is cut only between
steps, so after a crash disk holds a prefix of the steps. A batch carries the latest value of each
key written since the previous batch; a key set and then deleted in one window is one delete. Loading
restores every value under its key, the iteration order the in-memory store had, and every index
derived from the values; derived indexes are rebuilt, never stored. Whether a block advances its
fork's tip is decided by its first insertion, in memory and on disk alike. The pre-execution queue
is copied to disk too: an entry is written when it is queued or restored, a later merge into it
reaches disk only with the entry's next write, and a dequeued entry is deleted. A load drops every
queued entry whose agreement window passed while the node was down, without probing or blaming its
sources; the others keep the rest of their window and execute only after the first synchronization
settles ([`REQ-STOR-3-4RJGER`](durability.md#req-stor-3-4rjger)). A queued entry is re-validated
like any other when it executes; nothing on disk is trusted. A failed batch
is retried; when the retries are exhausted the storage fails, every waiting flush rejects, and the
runtime aborts.

**<a id="req-stor-8-25d06n"></a>`REQ-STOR-8-25D06N` — Durable before a slashable signature leaves.** A block the node
authored or confirmed MUST leave the process by any peer frame, a synchronization answer included,
only after the disk confirms every write the node made before that frame. Every chain transaction
the node sends MUST leave only after the disk confirms every write the node made before it; this
covers a dispute, a join submission, a top-up, and a snapshot post. Chain transactions that waited
for one confirmation leave in the order they were sent. Every disk batch is synced. The handshake
challenge is not channel state and is not covered. Signatures an application requests over the
client interface, and data sent in chain reads such as calls and gas estimates, are outside this
requirement. A failed write MUST keep the signature
inside the process and abort the runtime; it blames no peer. A signature lost in a crash before the
confirmation never left the process and has no effect: the restarted node treats the entity as never
produced. A restarted node MUST NOT sign a second, different entity at a coordinate whose signed
entity was confirmed. The confirmation a signature waits for survives a power loss on a host whose
platform can sync to stable storage, and at least a process or tab crash on a host whose platform
commits with relaxed durability; other writes may lag.

**<a id="req-stor-9-zr8a92"></a>`REQ-STOR-9-ZR8A92` — Closed by the one disposal.** The runtime's one disposal MUST close
durable storage after the cut: writes made before the cut drain to disk and are confirmed, then the
medium is closed and released so another runtime can open it. A write made after the cut changes
memory only, never reaches disk, and does not fail. A bind that fails closed, a disposal that
begins while the load is running, and a bind that begins after the disposal started still release
the medium.

**<a id="req-stor-10-xy96kg"></a>`REQ-STOR-10-XY96KG` — Persistence is opt-in.** A runtime keeps its storage in memory
only unless its integrator enables persistence when setting it up. With persistence off, nothing is
written to or read from disk, and the runtime behaves as one with no disk medium: a restart comes
back as a fresh node.

**<a id="req-stor-11-q4at07"></a>`REQ-STOR-11-Q4AT07` — Partition identity, ownership, and survival.** Each persisted
channel has one partition, identified by its chain, channel manager, state machine, and channel id,
however the channel was bound (direct connect or negotiation). A new partition records its identity,
encoding version, and the runtime's signer secret in one write. A runtime that resumes the channel
when it is set up without a secret of its own signs with the stored secret; a runtime given a secret,
at setup or when it binds the partition later, MUST be refused when that secret differs from the
stored one. At most one runtime MAY hold a partition at a time; a second open while
it is held MUST be refused on every platform, because two runtimes signing for one participant would
double-sign. A partition, its signer secret included, MUST NOT be deleted automatically, also not
when the channel closes: for a runtime-generated key it is the only copy of the key the settlement
paid. Deletion is an explicit integrator action. A runtime that clears a channel id it had bound (a
failed negotiation attempt) closes that partition and keeps it. The signer secret is stored
unencrypted; its
protection at rest is the host's.

## Assumptions and constraints

- The storage medium is durable across process restarts but not infallible: partial writes, torn
  state, and corruption are in scope; total media loss is not — a node that loses its durable set
  must recover as a re-synchronizing peer, not resume as if nothing happened.
- Storage capacity is finite; retention duties bound the minimum, pruning rules bound the growth.
- Durable state is local: nothing here weakens the chain's role as the arbiter, and locally stored
  data proves nothing to anyone else without the owning system's proofs.
- Platform storage APIs differ; the guarantees here are semantic and must hold on every supported
  platform ([`REQ-RUNTIME-4-B0N70Y` (Platform equivalence)](../runtime/execution.md#req-runtime-4-b0n70y)).
  Durability strength is the exception: a browser host commits with relaxed durability, so a
  confirmed write there survives a tab or process crash but not necessarily an OS crash or power loss
  ([`REQ-STOR-8-25D06N`](durability.md#req-stor-8-25d06n)).
- Writes reach disk in synced batches on a short timer. Only a peer frame carrying a block the node
  signed, a synchronization answer, and a chain transaction wait for the disk; a write no such send
  follows may be lost in a crash. Recovery of those writes depends on the peers that answer the
  restart synchronization ([`REQ-STOR-3-4RJGER`](durability.md#req-stor-3-4rjger)).
- Restart recovery assumes the node stays online: what the chain did while it was down reaches it only
  through that synchronization, and a pending join is not resumed. A node that may be offline through
  a contest window needs a delegate ([`REQ-TRUST-4-KW24NF`](../security/trust-model.md#req-trust-4-kw24nf)).
- Each authored or confirmed block costs one disk commit before it leaves, and the state mutex waits
  for it; a chain transaction waits for its disk commit before it takes a nonce.
- Persistence is off unless enabled ([`REQ-STOR-10-XY96KG`](durability.md#req-stor-10-xy96kg)); a runtime
  without it has no restart recovery and resynchronizes as a fresh node.
- The store's iteration order, which some stores' callers rely on, is part of what a load restores.

## Security considerations

Protected assets are the node's ability to prove, replay, and contest — losing them converts safety
guarantees into unenforceable claims. Threats include crash-window loss of commit-aligned state,
premature pruning that destroys contest evidence while a window is open, cross-channel/fork key
confusion, corrupted stores silently served to peers or pipelines, downgrade/upgrade
misinterpretation of stored encodings, and an adversary timing an attack to a victim's restart.
Recovery re-validation is the containment: stored data is untrusted at read-back, so a corrupted
store can deny service but cannot inject validity.

Restart double-signing is the main slashing risk the disk medium addresses: a node that forgets a
block or dispute it signed can sign a different one at the same coordinate. Confirming the disk write
before the signature leaves closes that window; a signature lost before confirmation was never seen.
Two runtimes on one partition (two tabs, two processes) recreate the risk, so the partition is held
exclusively. A restarted participant acting on its stale head before its first synchronization could
take a stale turn, a stale co-signature or a stale timeout action, so it stays `SYNCED` until that
synchronization settles, and aborts when no participant answers it.
Dispute markers written before a crash could block signing on a fork forever, so they are reconciled
against the chain at restart. Bad disk state fails closed rather than resuming from a partial
history. The signer secret sits unencrypted in the partition: anyone who can read the host's storage
for that origin or user can take the key. Automatic deletion on channel close is excluded because
the partition can hold the only copy of a funded key. Residual risks: a confirmed write in a browser
can be lost to an OS crash or power loss; protection of the signer secret at rest is left to the host;
a signature an application requests over the client interface is not held back by the disk.

## Future Work

_Non-normative._ Portable store-format recommendations for cross-implementation recovery; pruning
policy presets per deployment class; encryption of the stored signer secret, with a key policy of
minimum interruption to the end user (ideally a player never notices the chain: no extra password and
no prompt on each restore); an explicit integrator operation that deletes a partition; making
persistence the default.
