## Purpose and observable model

A participant can hold contract storage it did not read through a trusted call: an RPC endpoint hands
it slot values together with a proof. Before the participant relies on such a value, it checks the
proof against a state root it already trusts. The check has three outcomes for a slot: the root
commits to a value, the root commits to the slot holding nothing, or the proof does not decide. Only
the first two give the participant a value. Chains prove storage in different representations, so the
check sits behind one interface with one verifier per representation. The same holds for what the
participant needs of an account besides storage: its nonce, its balance and its code. The participant
can also fetch such state itself: it asks a node for its best block and for a proof of what it wants
to read at that block, and keeps only what the proof decides.

## Requirements and invariants

**<a id="req-stproof-1-j20p5y"></a>`REQ-STPROOF-1-J20P5Y` — A slot value is accepted only when the proof decides it.** Given a
state root, a contract address, a list of slots and a proof, the verifier MUST return, for every
slot and in the order asked, the 32-byte value the state root commits to. A slot the state root
commits to hold nothing reads as zero. When the proof does not decide every asked slot, the verifier
MUST fail and return no value for any of them. A proof does not decide a slot when a node on the
slot's path is absent from the proof, when the content of a node does not hash to the reference that
leads to it, when the state root is not the hash of a node of the proof, when a node on the path is
malformed, or when the committed value is not 32 bytes long. A slot the proof does not decide MUST
NOT read as empty. Nodes of the proof that lie on no asked slot's path are ignored.

**<a id="req-stproof-2-abcqr7"></a>`REQ-STPROOF-2-ABCQR7` — One verifier per proof representation.** Every verifier MUST meet
[`REQ-STPROOF-1-J20P5Y`](storage-proofs.md#req-stproof-1-j20p5y) through the same interface, so that
the caller does not depend on the representation. The first representation is the Substrate read
proof of a Frontier chain: contract storage is the EVM pallet's storage map keyed by address and
slot inside the chain's Blake2-256 state trie, and the state root is the one in the Substrate block
header. Its verifier MUST derive the slot's trie key the way the chain does, so that a proven value
equals what the chain's own storage read returns at that block. It MUST read a value the trie holds
by hash (state version 1) through the proof node that carries the value, and MUST read the nodes of
both state versions. It MUST refuse an address that is not 20 bytes and a slot that is not 32 bytes
before reading the proof, as either would derive the key of another entry.

**<a id="req-stproof-3-nvjgr0"></a>`REQ-STPROOF-3-NVJGR0` — A pushed partition is accepted only as its proof decides it under its own header.** An endpoint
can push to a subscription, once for each block, the block header, the block's Ethereum header, keys
of the state trie with the values they hold, and trie nodes. The first message syncs: it holds every
key of the partition and the whole proof of them. A later message holds the keys whose value changed
or that the partition took in, and only the trie nodes no earlier message carried. The participant
MUST take the state root from the header and MUST identify the block by the hash of the header and by
the Ethereum block hash the chain wrote into the header; it MUST reject the message when the header
carries no such hash or more than one, and when the Ethereum header does not hash to it. It MUST accept
a message only when, with the trie nodes it held and those of the message, every key it holds after
the message reads under the state root as the value it holds; a key pushed as holding nothing MUST
prove to hold nothing. It MUST reject a later message before any sync, and a later message of an
earlier block than the one it holds; a later message of the block it holds MUST be ignored, and one of
another block of the same height, as a reorg pushes, MUST be taken as any other. A message can name
`released` keys, the keys the subscription held that the endpoint no longer keeps current from that
block on, left out when there are none; the participant MUST hold none of them after the message and
MUST check every other key it holds as above, so that a message that leaves out a held key's new value
without naming it released is rejected. A message whose `released` is not a list of whole-byte
hexadecimal strings is no pushed message and MUST be rejected. A rejected message MUST leave
the participant holding nothing of the subscription until the next sync. After an accepted message it
MUST keep only the trie nodes its keys use under the new root. The block values a call reads at the
block are those of the accepted Ethereum header.

**<a id="req-stproof-4-xk5s64"></a>`REQ-STPROOF-4-XK5S64` — An account's nonce, balance and code are accepted only when the proof decides them.** Given
a state root, an address and a proof, the verifier MUST return the nonce and the balance, and
separately the code, that the state root commits to, so that they equal what the chain's own
Ethereum reads return at that block. An account the state root commits to hold nothing for has nonce
and balance zero, and an account it commits to hold no code for has empty code. When the proof does
not decide the asked entry, in the sense of [`REQ-STPROOF-1-J20P5Y`](storage-proofs.md#req-stproof-1-j20p5y),
the verifier MUST fail: an undecided account MUST NOT read as absent and undecided code MUST NOT read
as empty. The verifier of the Frontier representation reads the nonce and the balances from the
chain's account entry of the same 20 bytes, and the code from the EVM pallet's code map, also where
the trie holds the code by hash. Its balance is the free balance less what the chain keeps back: the
part of the frozen balance that exceeds the reserved balance, or the chain's existential deposit where
that is more, and never less than zero. The existential deposit is a constant of the chain that the
caller supplies. It MUST refuse an account entry that is not as long as the chain's account entry,
code that is shorter or longer than the length it announces, and an address that is not 20 bytes.

**<a id="req-stproof-5-hrdxeg"></a>`REQ-STPROOF-5-HRDXEG` — A read from a node yields only what its proof decides, at one block.** The participant
can ask a node for its best block and then, for that block, for storage slots, nonce and balance, and
code of several accounts at once. It MUST compute the block's hash from the header the node gave and
take the state root and the Ethereum block hash from that header, and MUST fail when the node gives
no well-formed header or the header carries no single Ethereum block hash. It MUST ask for the proof
at that block's hash and return, for every account in the order asked, only what
[`REQ-STPROOF-1-J20P5Y`](storage-proofs.md#req-stproof-1-j20p5y) and [`REQ-STPROOF-4-XK5S64`](storage-proofs.md#req-stproof-4-xk5s64)
prove under that block's state root, and nothing that was not asked. When the node gives no
well-formed proof, or the proof does not decide everything asked, the whole read MUST fail with the
failure of a proof and yield no value. A read at a block obtained earlier MUST yield that block's
state after the chain moved on. A read that asks nothing MUST NOT ask the node for a proof. A proof
asked through a watch ([`REQ-LC-12-VPAAP0`](light-client.md#req-lc-12-vpaap0)) MUST be checked the same way.

**<a id="req-stproof-6-casbqp"></a>`REQ-STPROOF-6-CASBQP` — The block values a call reads are accepted only as the block commits to them.** The
participant can ask a node for the values a contract call reads of a block: its number, timestamp,
coinbase, gas limit, difficulty and randomness. It MUST take them from the Ethereum block header the
chain's state holds for that block, proven under the block's state root as
[`REQ-STPROOF-5-HRDXEG`](storage-proofs.md#req-stproof-5-hrdxeg) proves any other entry, and MUST fail
with the failure of a proof when the state holds no such header, when the entry ends inside the
header, or when the header does not hash to the Ethereum block hash of
[`REQ-STPROOF-3-NVJGR0`](storage-proofs.md#req-stproof-3-nvjgr0) for that block. The timestamp a call
reads is in whole seconds, rounded down from the chain's clock. The base fee a call reads is not in
the header: it is a constant of the chain that the caller supplies.

## Assumptions and constraints

- A pushed header is taken as the chain's. The check binds the writes, the logs and the proof to that one
  header; it does not bind the header to the chain.
- The caller supplies a state root it trusts. The verifier establishes no trust in the root and does
  not fetch it.
- A best block is taken as the chain's on the node's word, like a pushed header. A read binds the
  values to that block's header; it does not bind the header to the chain.
- The base fee, like the existential deposit, is taken on the caller's word.
- The existential deposit is taken on the caller's word. A wrong one gives a wrong balance and leaves
  nonce, code and storage as proven.
- The Frontier verifier of accounts holds for a chain whose account of an address is the address's own
  20 bytes.
- A proof speaks for one state root. It says nothing about the slot at another block, and nothing
  about slots that were not asked.
- The verifier checks values, not completeness: whether the participant was given every slot that
  changed is outside this document.
- The hash function of the representation is collision resistant.
- The work of one check is bounded by the size of the proof and the length of the keys: every node
  is hashed once and a path visits at most one node per key nibble.

## Security considerations

Assets: the contract storage a participant holds locally and decides from. Trust boundary: the
proof and the values come from an RPC endpoint and are untrusted; only the state root is trusted.
Threats and defenses: an endpoint that sends a wrong value cannot produce nodes that hash up to the
root; an endpoint that withholds a node to make a stored slot look empty is refused, because an
undecided slot never reads as empty; malformed or truncated nodes are refused and cannot make the
check run without bound; a value of another length is refused, so no shorter or longer value is
padded or cut into a slot. A slot or address of the wrong length is refused before the proof is read,
because it would silently prove another entry. An account entry or code of an unexpected length is
refused for the same reason, and a node that withholds the proof node carrying code cannot make a
contract look like an account without code. A node that answers a read with the proof of another
block is refused, because that proof does not lead to the asked block's state root. Residual risks: a state root taken from the same
endpoint as the proof makes the check catch faults and omissions of that endpoint but not a
consistent lie, and an endpoint can still withhold slots that changed.
