## Purpose and observable model

Protocol work may run inline or across isolated execution contexts. Ports, workers, processes, and platform
adapters must preserve the same typed operation, ownership, ordering, error, cancellation, lifecycle, and
serialization semantics as direct execution. A participant spans up to three contexts: the application
context, which holds no participant state; the runtime host, which owns participant state, the signing key,
and the chain nonce; and the local execution engine, which owns the EVM state, including the separate
state-machine instance used for replay. Contexts interact only by serialized messages.

## Requirements and invariants

**<a id="inv-runtime-1-akrhak"></a>`INV-RUNTIME-1-AKRHAK` — Execution equivalence.** Inline and isolated execution given the same inputs and state
MUST produce the same result, committed effects, events, and failure classification. Communication across a
context boundary is defined once, as serialized messages over a paired channel, so a component moves between
inline and isolated placement without changing its contract. Equivalence covers the blocks, signatures, and
state roots produced and accepted; the chain actions taken, with their arguments and order relative to
protocol events; the application events emitted and their payloads; and the identity (name, code, revert
data) of a failing request. Timing, latency, log output, and internal task interleaving are out of scope.
Every combination of runtime-host and executor placement MUST satisfy it.

**<a id="req-runtime-1-rsm6mz"></a>`REQ-RUNTIME-1-RSM6MZ` — Transfer-safe boundary.** Every cross-context value MUST have an explicit canonical
encoding that preserves large integers, binary data, optional branches, errors, and correlation identity.
Errors keep their name, message, code, revert data, and originating participant. Application extensions
(the network service root, the runtime host root, precompiles) cross as declarative manifests resolved
in the receiving context, never as live objects; the host root manifest names the class that becomes the
runtime host root, as the network service manifest names the network service root
([`REQ-RPC-9-8FFE6S` (Application host root)](../peer-communication/rpc.md#req-rpc-9-8ffe6s)). A value with no supported encoding, such as an injected signer object or an unsupported
transaction field, MUST be rejected at the producer before it crosses.

**<a id="req-runtime-2-kbxktg"></a>`REQ-RUNTIME-2-KBXKTG` — Ownership and ordering.** Mutable resources have one context owner; requests affecting the
same ordered domain MUST execute in causal order without late or duplicate completion. Another context
reaches an owner's state only by request. Isolating execution adds latency, not concurrency of live-state
mutation: live-state application stays totally ordered across the executor boundary.
A paired channel delivers its messages in send order, and the event and error streams rely on that
order. Request correlation across this internal boundary needs no authenticity check, because the
paired context is the only writer of the channel; a network settlement, by contrast, must come from the
addressed peer ([`REQ-RPC-2-SZDTTM` (Request lifecycle)](../peer-communication/rpc.md#req-rpc-2-szdttm)). An inline runtime
host may serve several participants in one context, so it scopes every handler invocation to its
participant; an isolated host serves exactly one participant and needs no such scoping.

One connect operation crosses the runtime boundary with a channel identifier and an optional serializable
record containing independent opening permission, membership intent, full balance, and unmatched matcher
timeout. Inline and isolated routes return the same Boolean. Balance is dormant unless membership is
requested. A separate targeted cancellation operation carries only the channel identifier and returns a
Boolean; it owns unmatched matching only. Neither operation adds a second targeted membership owner.

Initial channel load starts from the first connected authenticated participant resolved from authoritative
chain state, uses the shared sync call's two-window default timeout, and aborts an uncommitted runtime on
failure. Exact-peer block recovery uses the same call with the same default and preserves the runtime.
After accepted pending or participating state, later operational failure preserves the live runtime and
channel. An observed fixed-target open causes one bounded entry into that operation's locked post-open
branch, never general matching or target reselection. Request handlers route replies by authenticated peer
address when present, with the inbound transport as the addressless fallback. Original-transport retirement
rejects its pending requests.

**<a id="req-runtime-3-vqxw59"></a>`REQ-RUNTIME-3-VQXW59` — Lifecycle convergence.** Startup, readiness, failure, cancellation, disposal, and restart
MUST settle every request and release every owned resource exactly once. A reply to a requester whose connection already closed MUST be dropped without an error; that requester already rejected the request. A runtime-host startup failure MUST reject its creation and every pending request; loss of the application's connection MUST make the runtime host dispose itself. Readiness MUST remain pending until the application lifecycle hook and all resources it declares ready have completed. A failed readiness hook MUST preserve its original error and close partially created resources. Each isolated context's performance monitor MUST start only after that context has completed its own readiness work and MUST enforce the configured delay threshold by throwing in that context. Every isolated context (the sdk worker and the contract-executor worker alike) follows one error policy: an error caught outside a request, including the monitor's throw, is reported to the application as one detached runtime error and the context keeps serving; with no application subscriber it surfaces as an unhandled failure in the application context, as an inline host's would; only a failure before the context's error funnel exists, or an exit the runtime did not request, is fatal for that context. The funnel MUST be registered before the context serves requests or posts readiness. SDK executor creation is owned by its runtime endpoint. Detached executor reports MUST reach the application through that owner. The structured delay data of a monitor error MUST survive every port hop.

Parents MUST retain readiness separately for each registered child. A readiness notification received before a waiter is installed MUST satisfy that later waiter; a startup failure or connection loss before readiness MUST reject that child's wait without settling a sibling's wait. A root signals readiness only after its required initialization and the children required for that initialization complete. External bridge installation is not part of readiness: forwarding endpoints may be ready before the destination attaches, and negotiation waits for attachment. Client communication readiness means that its host connection and child initialization are usable. Application setup uses that connection for required deployments and adapters, and returns only after those operations finish. Domain operations retain their separate admission checks.

Graceful disposal of a runtime host MUST first cut every boundary with a lasting effect in one synchronous step (network, chain sends, the parent event bus; durable storage joins the cut when the runtime has one), then, before the child disposal, release once each resource of the runtime that something outside it can still reach: its timers, its chain subscriptions and the waits that hold chain listeners, its subscriptions to objects shared across the context, its local discovery sessions, its direct peer connections (one still negotiating included), and an abort's log flush. After the child disposal, every listener the runtime left on a chain connection that outlives it MUST be removed. State held only in memory is dropped without a teardown step; a disposed runtime's timer, chain log or shared-object callback MUST NOT reach it afterwards. Work a cut boundary may hold is not drained. The disposal itself answers none of the application's pending channel requests (connect, lobby match, channel opening, join, top-up) and does not wait for them: one still running when the connection closes rejects with the runtime-disposed error. A channel request whose handler finishes after the cut and before the connection closes still answers with that handler's result (an in-flight sync request the cut failed answers its failure path; a call parked on the state mutex runs on the cut runtime, and nothing it produces leaves the runtime). The disposal waits for no request handler still running for its parent: a request whose handler has not answered when the connection closes rejects with the runtime-disposed error; only the acknowledgement of the disposal itself still leaves. Before the connection closes, a disposal that is not an abort flushes the runtime's logs once, so what it logged while disposing, its chain-spending report included, reaches the log upload; an abort's flush keeps its one deadline ([`REQ-LOG-11-F5TJQC`](log-collection.md#req-log-11-f5tjqc)) and is not repeated. It MUST then await child disposal outcomes before final local cleanup. Preparation or child failure MUST NOT skip final cleanup. Quiescence MUST await child drains before completing the local runtime-wide drain and return the collected failures. Repeated cleanup calls MUST share their completion and result. Detached work still in flight after the turn in which a root's disposal begins is settled by that disposal: a later failure of that work is the disposal's outcome and MUST NOT surface as a runtime error, an unhandled rejection, or a drain failure. Work already rejecting in that turn, such as the error that caused an abort, and the disposal's own failure stay visible. Closing a direct connection through a WebRTC bridge that is disposing or disposed MUST complete without a failure, also a close whose request the disposal rejects: the disposal closes that connection. Cleanup requests flow from parent to child; a child MUST NOT recursively initiate cleanup of its parent. Required disposal acknowledgements precede closure of their response connection. Forced connection removal remains separate from graceful disposal and can reject pending work immediately. A disposal that begins at any point of a runtime's setup MUST end in the same cut and disposed runtime once a start still in flight returns: a setup step that completes after the cut cuts and disposes what it built, sends nothing, and fails the setup. A fatal participation abort MUST dispose the owning runtime and all descendants, close their communication endpoints, and reject subsequent calls in either placement; the abort is that same disposal, so the application's pending and later calls end as after a disposal. This MUST NOT dispose an independent sibling runtime.

Owner-initiated connection closure MUST establish expected worker shutdown before the child can observe parent loss. A child with no live parent can finish cleanup without acknowledgement; this must not create a second fatal exit report.

Top-level creation MUST run inline, await initialization, and return a direct reference to the initialized root. Worker creation without an explicit parent MUST create, for that creation alone, a hidden parent with no domain service in the caller's context, connect the worker to it through the same typed boundary as any parented worker, and return the usual typed remote reference. The caller neither sees nor manages that hidden parent. A hidden parent MUST NOT be shared or reused across creations. Disposing the returned reference MUST first complete the worker's own cleanup and then dispose its hidden parent, also after the worker has ended unexpectedly; a failed worker startup MUST dispose its hidden parent and reject creation. Disposing or failing one parentless worker MUST leave every other parentless worker and its hidden parent usable. Parentless worker support never replaces an explicitly supplied parent, and parentless inline creation keeps returning the direct local root. Every concrete root uses the same initialization contract whether standalone or parented; standalone creation adds no parent connection or parent-ready notification. A root may explicitly create children during its initialization. Common creation MUST establish any parent relationship before domain initialization and complete readiness afterward. Concrete domain initialization MUST NOT require separate attachment or shutdown wiring.

Child creation MUST provide the same typed communication boundary in inline and worker placement, owned by an existing parent. Creation completes after the child and its required startup descendants are initialized and connected. Externally forwarded bridge endpoints may attach afterward. The caller need not perform a separate worker startup or executor initialization operation. Startup arguments cross a clone boundary in either placement; local dependencies remain local. A failed child must not dispose its parent or siblings. Every root has at most one parent. Its returned remote reference owns communication and cleanup together, without a separately managed transport. A bridge forwarding endpoint belongs to its requesting host, and the native connection endpoint belongs to that forwarding endpoint. Multiple inline hosts sharing one worker MUST retain independent bridge capabilities. Disposing either host MUST leave the other host’s connections usable.

An application-defined service extension built by a runtime host, and an application-defined precompile factory loaded by a contract executor, MUST receive a local reference to the exact root that owns them, so they can create their own children under it. The reference MUST be available while that owner is still starting, before its readiness, and MUST stay in the owner's context: it is never serialized, sent across a context boundary, or carried in the extension's options. Children created under it are the owner's children, and disposing the owner disposes them. Several runtimes sharing one context MUST each supply their own owner, and disposing one runtime MUST leave the other runtimes' children usable. An EVM built outside an executor root supplies no owner.

Graceful disposal of a contract executor MUST first close admission to executor operations (deployment, call, and simulation). An operation that arrives after admission closes MUST settle with a rejection without entering the EVM. Every operation admitted before that point, including one still waiting for the execution order, that settles within the disposal drain limit MUST settle with its own result or error before the executor's children are disposed, because an admitted operation may still call such a child. The executor's wait for admitted operations MUST be bounded by a fixed drain limit. An operation still unsettled at that limit is abandoned: disposal MUST then dispose the children and complete, the operation's caller MUST receive the disposal rejection even when the operation later succeeds or fails, that later outcome MUST NOT reach the caller, and the abandoned operation MUST NOT surface as a runtime error, an unhandled rejection, or a drain failure, because nothing uses its result after shutdown. Repeated disposal MUST share one completion.

**<a id="req-runtime-4-b0n70y"></a>`REQ-RUNTIME-4-B0N70Y` — Platform equivalence.** Platform-specific transports and worker mechanisms MAY differ,
but must expose the same protocol behavior and explicitly reject unsupported capabilities. Values crossing
extension and bundle boundaries MUST be recognized through their declared public contract, not constructor
identity that is local to one JavaScript module graph. An application-defined event hook with a cloneable
payload MUST cross the generic runtime event bridge by name without requiring that name in the SDK's base
hook declaration.

**<a id="req-runtime-6-6f4ssm"></a>`REQ-RUNTIME-6-6F4SSM` — Cross-context clock equivalence.** An isolated contract executor MUST
observe the same estimated chain time as the inline executor of the same runtime
([`REQ-TIME-5-S9NQXK`](../protocol-model/time.md#req-time-5-s9nqxk)): the host passes its Clock adjustment at initialization
and the isolated context derives the time from its own wall clock, so both contexts agree within the
one-second sampling boundary on every platform.

**<a id="req-runtime-7-a2var0"></a>`REQ-RUNTIME-7-A2VAR0` — Bounded isolated-context teardown.** After an isolated
context has completed its disposal, it MUST end within a fixed drain bound. The bound is armed before the
context releases the resources it can enumerate, so no failure while releasing them can skip it. A
resource that refuses a second release (one its owner is already releasing) MUST NOT stop the release of
the others. Its owner MUST NOT force-stop it: on a host where forcing a context that still holds native
resources to stop aborts the whole process, only the isolated context may end itself, and a context's own
end MUST NOT abort its owner's process even while a native resource the host does not enumerate is still
open. If its event loop has not drained when the bound expires, the context MUST collect a bounded,
serializable description of what still holds it (its active, referenced host handles and its active
resource kinds), deliver that description to its owner, and then end itself with a distinct drain-timeout
status. The end is unconditional: when the description cannot be collected, the context delivers none and
still ends. The owner MUST receive a delivered description before it classifies the end, MUST complete the
disposal, and MUST record a warning that carries the description, or no description when none arrived; an expected
drain-timeout end is not a runtime failure. A context that drains within the bound ends normally and no
warning is recorded. An end the owner did not request stays fatal whatever its status. A host that can
stop an isolated context safely from outside may do so and needs no self-drain bound. Before such a host stops a
context that reached readiness, the owner MUST wait for the context to report that it is closing, which the
context does after its own log sends settled ([`REQ-LOG-10-69CTN1` (A thread that is ending waits only for its own logs)](log-collection.md#req-log-10-69ctn1)), for at most the log flush bound
plus a fixed close margin, and MUST keep the context's connection open until then. When the bound passes
first, the owner MUST record a warning that carries the bound and then stop the context; a failure to record
the warning MUST NOT stop the disposal. A context that has not reached readiness, or that the owner saw fail,
gets no wait.

**<a id="req-runtime-8-m3enfm"></a>`REQ-RUNTIME-8-M3ENFM` — An isolated context's failure names its cause.** This requirement
applies to browser hosts. A Node.js host passes the error that escaped the context to the owner as it is,
so its message already names the cause. When a browser host reports to the owner that an isolated context
failed (its script failed to load or parse, or an error escaped the context), the owner MUST fail the context with an error whose message names the real cause. For
an error the host reports with a message, that is the message and its source position (script, line,
column); for one without a message, that it has no error message, with the position. For a script that
failed to load or parse, which the host reports with no cause, it is the context's absolute script location,
whether the host received the script, and the result of one bounded re-fetch of the script, read in full. A
script the host received failed to parse or link, with the status and size it received and the re-fetch
result, so a received copy that differs from what the server sends now shows. A script the host did not
receive failed to load: with the status when the re-fetch answers an error status, otherwise with the
re-fetch result (its success status and size, or its error). The owner MUST log the failure at error level with
the kind of host event, the script location, the context name and the time since the owner asked for the
context, plus the host's message and position, or what the host received and the re-fetch result. Only a load or parse failure gets the
re-fetch, at most once per context. The logging MUST NOT change the outcome: when the log write fails, the
context still fails with the same error. The owner handles the host's failure event, so the host does not
report it a second time.

**<a id="req-runtime-9-p5vpt5"></a>`REQ-RUNTIME-9-P5VPT5` — An uncaught non-error failure is reported as one error.**
When a value that is not an error object escapes every handler in an isolated context, the context MUST
report one error whose message names how the value escaped (an unhandled rejection or an uncaught
exception), the context that caught it, and the value's text, or its object type tag when the value has
no text conversion; the error keeps the value as its cause in
that context, and only the error crosses a context boundary. An error object that escapes is reported
unchanged. When the host reports an uncaught exception by an event that carries no error object, the
error is built from the event's message and script location. A component that receives a failure that is
not an error object from a host boundary, such as a socket's error or close event, MUST convert it at that
boundary into an error with what it knows; every other component handles error objects only.

**<a id="req-runtime-5-wj1xkk"></a>`REQ-RUNTIME-5-WJ1XKK` — Required host environments: browser and Node.js.** The supported-host set is a
system-wide commitment, not an implementation convenience. For this protocol version a conforming
client MUST run in both **browser** and **Node.js** host environments, and every protocol
capability — authentication, block progression, synchronization, dispute participation, local-mirror
evaluation, storage, recovery — MUST be available with identical observable behavior in both.
Host-conditional code paths (transports, worker mechanisms, timers, crypto providers, storage
media) are permitted only beneath the equivalence boundary of [`REQ-RUNTIME-4-B0N70Y`](execution.md#req-runtime-4-b0n70y)/[`INV-RUNTIME-1-AKRHAK`](execution.md#inv-runtime-1-akrhak); a
protocol capability that exists on only one host is a conformance defect, not a platform
limitation. Where one host lacks an isolation or performance facility (e.g. no worker support),
the inline path MUST provide the full capability at reduced performance, never reduced behavior.

Thread monitoring MUST be idempotent across loggers sharing a physical thread: repeated start preserves the active monitor and repeated stop has no further effect. Disposing a non-owner logger MUST NOT stop the active monitor. An explicit executor clock adjustment, including zero, MUST take precedence over a shared initialized clock; without an adjustment, the initialized clock remains the fallback.

**<a id="req-run-2-gbcz5b"></a>`REQ-RUN-2-GBCZ5B` — No shared mutable memory across contexts.** The protocol MUST NOT depend on
shared mutable memory between the application context, the runtime host, and the execution engine; every
inter-context interaction is a serialized message. This is a design constraint, not a platform limitation.

**<a id="req-run-13-27ye2t"></a>`REQ-RUN-13-27YE2T` — Isolated placement is the default.** Isolating the runtime host and isolating
the execution engine are both the intended defaults, uniformly on every host; placement MUST NOT branch by
environment profile. Inline placement is the fallback for hosts without usable workers. Isolation is a
client-side performance strategy, not server scaling.
Rejected alternatives (2026-08-10): per-environment placement profiles, because profile branching
multiplies the configuration matrix the equivalence criterion must cover; and keeping inline as the
default until measured, because it treats the target architecture as speculative.

**<a id="req-run-14-yahyr4"></a>`REQ-RUN-14-YAHYR4` — Mid-range mobile browser envelope.** A channel of about six participants MUST
run within a mid-range mobile browser: on the order of 4 GB device RAM, a few hundred MB of usable
JavaScript heap for the whole application, and a mobile-class CPU. The envelope is a hard budget: the three
contexts of a participant must be made to fit it; placement does not change to fit the device.

## Assumptions and constraints

- Contexts may crash, stall, terminate, or deliver a late response.
- Serialization and message queues impose finite size, memory, and scheduling limits.
- The supported hosts are browser and Node.js ([`REQ-RUNTIME-5-WJ1XKK`](execution.md#req-runtime-5-wj1xkk)); platform APIs differ between them,
  so shared semantics cannot depend on an API unavailable in the other host.
- Browser hosts add constraints Node.js does not: no raw sockets (transports must use
  browser-available channels), storage quotas, tab lifecycle (suspension/termination without
  notice, which the recovery rules of [../storage/durability.md](../storage/durability.md) must
  absorb), and stricter same-origin/network policies.
- Isolation improves fault containment but does not make untrusted protocol data safe.
- Loss of the other context is signalled reliably on Node.js but only best-effort in browsers; a request
  timeout is the backstop for a missed loss. Disposal and quiescence carry no generic request timeout and
  own their bounds.
- On a host where forcing a context to stop is unsafe, an isolated context ends by draining its resources
  after disposal, never by forced termination from its owner. A cleanup that does not drain within the drain bound of [`REQ-RUNTIME-7-A2VAR0`](execution.md#req-runtime-7-a2var0) ends the
  context itself, and its owner records a warning naming what held it. Resources the host does not
  enumerate (native addon handles or requests, timers) can only be described, not released, before that
  end. The premise that a context's own end is safe with such a resource open is checked for a
  bound native UDP socket; a native request that never completes is not covered.
- The executor's wait for admitted operations during disposal is bounded by the disposal drain limit, not
  by the operation. Abandoning an operation at the limit discards its outcome but does not cancel it: it may
  keep running in its context and later succeed, or fail against an already disposed child; neither outcome
  reaches its caller, which already holds the disposal rejection, and neither is reported. An operation whose result matters to its caller must settle within the limit.
- A browser reports a worker script that fails to load or parse as a plain event with no message, so the
  owner can name that cause of [`REQ-RUNTIME-8-M3ENFM`](execution.md#req-runtime-8-m3enfm) only from what the browser recorded and its own re-fetch.
  The browser records a load in its resource timing only for a response it received (Chromium: a success
  status), so a recorded load that failed did not parse or link, and a missing one did not load. An
  observer gets each record even when the page's timing buffer is full. The re-fetch shows what the
  server answers now, which can differ from the failed load. When workers of the same script start together, a
  recorded load may be another worker's. A script's top-level error reaches the owner as an error with its
  message, not as this plain event.
- A browser host stops a worker from outside and signals no closed connection to it. A disposed worker
  therefore closes itself only after its disposal is acknowledged over the still-open connection. The
  owner waits for its closing report only up to the bound of [`REQ-RUNTIME-7-A2VAR0`](execution.md#req-runtime-7-a2var0); a worker whose own log
  sends run past that bound is stopped with them, and those logs are lost.
- A supported production bundle may contain more than one compatible module graph. JavaScript constructor
  identity is stable only inside one graph and cannot define cross-extension behavior.

## Security considerations

Threats include serialization corruption, confused ownership, response mis-correlation, unbounded queues,
use-after-dispose, stale worker mutation, platform drift, and test-control capability leakage. Privileged
control channels must be unavailable in production protocol sessions. Local owner references given to
application extensions are live capabilities in their own context; confining them to that context keeps
one runtime's extension from creating children under, or disposing, another runtime sharing the same
context. The bounded executor drain caps how long an admitted operation that never settles can delay that
executor's disposal, and every owner disposal waiting on it, at the drain limit; the residual cost is that
such an operation loses its result and its caller sees only the disposal rejection. The teardown drain
bound of [`REQ-RUNTIME-7-A2VAR0`](execution.md#req-runtime-7-a2var0) caps how long a resource leaked by a disposed isolated context can hold its
owner's disposal; the residual risk is that the leak itself stays unfixed behind a warning, so the warning
must name the resources that held the context. The load-failure re-fetch of
[`REQ-RUNTIME-8-M3ENFM`](execution.md#req-runtime-8-m3enfm) requests only the script location the owner already asked to run, once and bounded,
so it adds no new network target; its log facts carry that location, including any query data in it, into
the owner's logs. The error of [`REQ-RUNTIME-9-P5VPT5`](execution.md#req-runtime-9-p5vpt5) carries the uncaught value's text into
error reports and logs. The concrete
per-context memory budget and per-participant ceiling for the device envelope of
[`REQ-RUN-14-YAHYR4`](execution.md#req-run-14-yahyr4) are open
([`OQ-38-EY27T5` (Runtime budgets, scheduling determinism, and test isolation)](../open-questions.md#oq-38-ey27t5)).
