## Purpose and observable model

A participant implementation coordinates transport, RPC, block validation, state execution, agreement,
storage, chain observation, recovery, and application events behind one lifecycle. Components may be split
or replaced, but a peer must observe the same protocol results and ordering as a single coherent participant.

The participant turns an ordinary instance of the application's contract into an enshrined peer-to-peer
contract: calling it executes the state machine off-chain between peers, with the chain as fallback
arbiter. The application drives and observes the participant only through the returned surface: the
enshrined contract, a channel signer and a chain signer that forward to the runtime, one event surface,
typed remote calls to its own or another peer's runtime, error observation, quiescence, and disposal.

The public discovery operations are `joinLobby(topic, options?)` and `leaveLobby(topic)`. The separate
fixed-target operations are `connectToChannel(channelId, options?)` and
`cancelConnectToChannel(channelId)`. Connect options independently permit opening (`autoOpen`), request
membership (`shouldJoin`), supply a full balance, choose to stay spectating when the channel is full
(`shouldSpectateWhenFull`), and bound only unmatched rendezvous (`timeoutMs`). A
balance is dormant without `shouldJoin`. Omitted and `null` timeout values leave matching unbounded;
match acceptance permanently removes the timer. Callers never supply a join deadline.

Connect returns `true` at exact-channel `SYNCED` when membership was not requested. With `shouldJoin`, it
returns `true` after confirmed genesis membership or a successful existing membership receipt reaches
`PENDING_PARTICIPANT` or `PARTICIPATING`. A finite unmatched timeout, valid cancellation, refusal, or
pre-boundary operational failure returns `false`. Initial observer sync failure disposes the runtime, so
the caller must create a new runtime. Accepted pending or participating state remains attached after later
operational failure and cannot switch targets before normal exit or dispute handling.

Targeted cancellation is not a `leaveLobby` alias. It succeeds only while that channel owns an unmatched
targeted attempt and settles connect as `false`. A wrong channel or post-acceptance request returns `false`
without mutation. No second public targeted join operation exists.

The public connection operations are `getOpenConnections()` and the `onConnectionsChanged(connections)`
event. Each entry names one active peer connection by the peer's checksum address and its transport kind.
Both reach a client of an isolated runtime the same way as every other public operation and event.

`leaveChannel()` starts the terminal leave and returns at once. The `onLeftChannel()` event fires once whenever
the runtime's membership or pending join ends and it drops to `SYNCED`, whatever ended it: a leave, an authored
exit, a slash, an eviction, or a join that was refused or expired before it landed
([`REQ-LIF-10-QR8NQ9` (Terminal runtime departure)](../settlement/lifecycle.md#req-lif-10-qr8nq9)). A join failure
that aborts the runtime fires it before `onAbort`. The runtime exposes no query for its own join state: an
application learns that a join landed from the status and that it ended from `onLeftChannel`.

## Requirements and invariants

**<a id="inv-sdk-arch-1-knax7f"></a>`INV-SDK-ARCH-1-KNAX7F` — Coherent participant state.** Services MUST converge on the same channel, fork, peer,
proof, and lifecycle state; no service may privately establish a conflicting protocol truth.

**<a id="req-sdk-arch-1-7h14h6"></a>`REQ-SDK-ARCH-1-7H14H6` — Explicit ownership.** Each mutable operation, state store, external effect, and recovery
decision MUST have one canonical owner and all other components MUST delegate to it.
Membership reads MUST have one membership owner while preserving the caller's observation policy:
local-only pending-join observation starts force-join counters only once the local chain mirror lists
the join; departure protection checks local pending membership first and, only when absent, confirms
against chain pending membership; expiry or drop checks read the chain's seated and pending participant
sets directly. A signer in either chain set is still on chain. These policies MUST NOT be collapsed.
Consolidating ownership MUST NOT add caching, outage fallback, or earlier force-join observation.
A chain confirmation of local absence is part of the departure policy, not RPC-failure recovery.
The join owner also encapsulates the automatic snapshot-race retry as one logical operation. Its public
interface exposes only the final specified outcome, not the intermediate refusal, a transient `SYNCED`,
or a membership-end event during fresh collection; see
[`REQ-JOINSIG-1-8X1A4V` (Pinned-state authorization)](../peer-communication/join-authorization.md#req-joinsig-1-8x1a4v).

**<a id="req-sdk-arch-2-qbzat8"></a>`REQ-SDK-ARCH-2-QBZAT8` — Ordered lifecycle.** Initialization MUST establish dependencies before accepting work;
shutdown MUST stop intake, settle or reject owned work, release resources, and prevent late callbacks from
mutating disposed state.

**<a id="req-sdk-arch-3-whtdwx"></a>`REQ-SDK-ARCH-3-WHTDWX` — Event fidelity.** Public events MUST describe committed participant state transitions,
not speculative intermediate work, and MUST preserve causally significant ordering. A failing event
consumer MUST NOT block other consumers or fail the committed transition, and a transition's application
contract events are emitted before the next turn begins.

**<a id="req-sdk-arch-4-gtn7qn"></a>`REQ-SDK-ARCH-4-GTN7QN` — Execution isolation.** Temporary validation, replay, and query work MUST NOT mutate the
live application state or durable protocol state unless the owning operation commits successfully.
Dispute replay and canonical validation run against a separately deployed instance of the application state
machine, never the live one, because replay repositions it at arbitrary historical states; this separation
is independent of where execution is placed.

**<a id="inv-sdk-1-de9yed"></a>`INV-SDK-1-DE9YED` — Application access only through the public surface.** All application
interaction with the participant MUST cross the runtime boundary through its public surface; direct access
to internal participant state is unavailable in every placement.

**<a id="req-sdk-arch-5-aam7yk"></a>`REQ-SDK-ARCH-5-AAM7YK` — Chain submissions survive concurrent inclusion.** A chain transaction the
runtime submits without a caller gas limit MUST be sent with headroom over a fresh gas estimate, never a
fixed limit, so a concurrent transaction included first (such as another honest participant's dispute
in the same evidence window) cannot make it run out of gas; a caller's explicit limit MUST be sent
unchanged.

**<a id="req-sdk-arch-6-8de4er"></a>`REQ-SDK-ARCH-6-8DE4ER` — Chain spending is observable.** A participant MUST aggregate what its own
chain transactions cost, keyed by the called contract and the called function, and MUST expose that aggregate on its public
surface and report it once when the participant is disposed. Only transactions that mined count. A mined transaction that
succeeded MUST contribute to its key's success count, success total, minimum, and maximum cost. A mined transaction that
reverted MUST instead contribute to that key's separate reverted count and reverted total, since it still cost what it
burned while costing a fraction of the completed call: reverted cost MUST NOT enter the success total or either bound. A
transaction that never mines MUST NOT be counted, and a transaction that was never sent MUST NOT appear at all. Observing cost MUST NOT change a sender's result, its ordering, or
the nonce the participant allocated, and MUST NOT let a failed observation surface as a participant failure. A function the
participant's surface does not name MUST still be identified by its selector.

**<a id="req-sdk-arch-7-h64k87"></a>`REQ-SDK-ARCH-7-H64K87` — Open connections are observable.** A participant MUST expose a snapshot
of its active peer connections, one entry per connection with the peer's identity and the connection's
transport kind. A connection whose peer identity is not yet known MUST be left out. After every change
of the active connection set — a connection joining it, or leaving it through an expected or an
unexpected close — the participant MUST emit the new set once. Adding a connection that is already in
the set or closing one that is already gone MUST NOT emit anything. The snapshot and the event MUST
reach a client of an isolated runtime with the same content.

## Assumptions and constraints

- Dependencies expose deterministic typed boundaries and compatible protocol versions.
- One running participant per signing identity.
- The application state machine obeys the deterministic execution rules; otherwise local execution,
  replay, and fraud proofs diverge.
- A participant may use inline or isolated execution, but observable ordering and failure semantics match.
- SDK feature logic assumes a stable, always-available RPC connection. RPC infrastructure availability
  and outage handling are one SDK-level concern, not feature-by-feature recovery logic. Redundancy is
  planned to support this assumption; its mechanism is outside this specification.
- An RPC infrastructure outage does not become a normal protocol refusal. Unexpected errors must
  surface; feature logic does not add cleanup, fallback, or failure-injection cases solely to survive
  a theoretical RPC outage. Legitimate chain refusals retain their specified handling and tests.
- Durable storage failures and lagging chain observations must remain explicit at their owning boundary.
- Component boundaries do not imply independent trust: untrusted peer and chain data remains validated.

## Security considerations

Assets include signing authority, live application state, durable proofs, peer identity, and event consumers.
Threats include confused ownership, stale callbacks, partial initialization, split-brain stores, unvalidated
cross-service data, reentrant event handling, and cleanup races. Failure must be contained at the owning
boundary and may not silently advance protocol state.

The open-connection snapshot and its change event expose peer identities and transport kinds to the
local application only; they carry no peer-supplied data beyond the authenticated identity, and the
application must not treat a listed connection as proof of channel membership.
