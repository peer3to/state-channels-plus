## Purpose and observable model

A participant reads the base chain and sends its transactions through one or more RPC endpoints of one
chain, and observes the manager's events through the storage diff service's records of that chain
([storage-diff-service.md](./storage-diff-service.md)). The endpoints form an ordered list. A single
endpoint is the list of one. Losing the connection to one endpoint must not stop chain access while
another listed endpoint is reachable, and an event of a block mined while the service connection was
lost must not be missing from the runtime's observed manager events. The application uses the same endpoint set through the
chain access the SDK gives it, with the same failover, instead of opening its own connections; its log
subscriptions come from the endpoints, have no such recovery and can leave a gap
([`FIND-RPC-4-7H2R11`](../../audit/open-findings.md#find-rpc-4-7h2r11)).

## Requirements and invariants

**<a id="req-chainobs-1-5jthy8"></a>`REQ-CHAINOBS-1-5JTHY8` — Ordered endpoint set.** The configuration MUST name the endpoints
in priority order. When the list is absent or empty, the single configured endpoint is the whole
list. Every entry MUST be a WebSocket-compatible endpoint; an entry that is not rejects startup.
Startup MUST complete as soon as one listed endpoint is connected; the others keep connecting in
the background, and every connection attempt is bounded in time. When no endpoint connects, startup
MUST fail, naming every endpoint by scheme and host only, and release every connection it opened.
The first connected endpoint fixes the chain: an endpoint that serves another chain MUST be refused
and keeps being retried.

**<a id="req-chainobs-2-2ncsq3"></a>`REQ-CHAINOBS-2-2NCSQ3` — One endpoint per request, with failover.** Every chain request,
read or transaction, MUST go to the first listed endpoint that is connected. It moves to the next
connected endpoint only when that endpoint has no connection or loses it before answering; a request
in flight on a dropped endpoint MUST be answered by the next connected endpoint, not wait for the
dropped one. A transaction MUST NOT be sent to several endpoints at once. An endpoint's own answer,
including a rejection, is final for that request. While no endpoint is connected, a request waits
for the first endpoint to reconnect; the participant MUST warn once when its last connected endpoint
drops. Shutting the chain access down MUST reject every waiting request and every request still in
flight on an endpoint. Stopping its reconnects MUST reject every waiting request; a request in flight
on an open connection then still gets its answer, and fails only if that connection drops.

**<a id="req-chainobs-3-n137zp"></a>`REQ-CHAINOBS-3-N137ZP` — Manager events from the storage diff service, through connection loss.** The
participant MUST take the channel's manager events from the storage diff service's records, not from a
subscription on an endpoint: each event once its block is on the service's best chain, in block and log
order, from the block after the head the participant saw when it selected the channel. A service
connection that is lost MUST be renewed and subscribed again, and an event of a block mined while it was
lost MUST be processed after it is back. When a reorganization replaces a block whose events were handed
on, at the same height or deeper, those events MUST be handed on again marked removed, newest first, and
then the events of the replacing chain; the events of the newest 128 handed-on blocks are kept for this.
The events of blocks the service no longer retains MUST be read from the endpoints, up to the head of the
endpoint that answers; an event already handed on for the same block is not handed on again, and one in
a block whose hash changed is handed on again as removed first. A connection of the chain access that
drops, including one that stops answering a periodic liveness check without closing, MUST be reconnected
with a bounded backoff, independently of the other connections. A liveness check answered with an error
proves the connection alive. Log queries read block windows no wider than a configured positive maximum,
in ascending order, and schedule each window's events before reading the next; a retry reads again from
the window that failed. A maximum that is not a positive integer MUST reject startup. A block subscription asks each endpoint for `newHeads`; an endpoint that refuses
it and names `newBlockHeaders` as a kind it offers (Asset Hub's eth-rpc) MUST be asked for
`newBlockHeaders` instead, whose pushes carry the same header number, on that connection and on every
renewed one, and that subscription ends when the last block listener is removed. Any other refusal is
not retried with another kind.

**<a id="inv-chainobs-1-asvkc1"></a>`INV-CHAINOBS-1-ASVKC1` — Exactly-once event processing.** One chain event
delivered more than once, by another stream, by a read of the endpoints, or after the service connection
is renewed, MUST be processed once. Event identity
includes the containing block, so an event re-mined in another block after a reorganization is a new
event. An event the chain reports as removed by a reorganization is logged and ignored; its earlier
effects are not undone. An event delivered below the completed-block progress marker is dropped: its
block is fully processed.

**<a id="req-chainobs-4-ja3yf8"></a>`REQ-CHAINOBS-4-JA3YF8` — Application chain access over the same endpoint set.** The SDK MUST
give the application a chain access built from the same endpoint configuration as the runtime's, with
the same startup ([`REQ-CHAINOBS-1-5JTHY8`](chain-observation.md#req-chainobs-1-5jthy8)) and the same request failover and waiting
([`REQ-CHAINOBS-2-2NCSQ3`](chain-observation.md#req-chainobs-2-2ncsq3)); failover and the decision when a request fails stay inside that chain
access, not at the application's call sites. A subscription to a contract-log filter on it MUST be made on
the connection of every connected endpoint, and again on every reconnected connection, and MUST deliver
each matching log once, identified by its block hash and log index, however many endpoints deliver it.
A log 128 or more blocks below the highest delivered log counts as delivered and is not delivered;
identities are kept for the logs above that bound. Removing the last listener of a filter MUST end that subscription on every endpoint. A
subscription request that the chain access's own shutdown cancels MUST NOT raise an unhandled failure.

## Assumptions and constraints

- Every listed endpoint serves the same chain; the participant does not merge different chains.
- The configured log-query window maximum is at or below every endpoint's own log-query range limit.
- Every listed endpoint is trusted, a backup included, and so is the storage diff service whose records
  carry the manager events: a forged event can advance the progress marker. Verifying events against
  another source is out of scope ([../security/trust-model.md](../security/trust-model.md)).
- At least one listed endpoint is honest and eventually reachable.
- A transaction that the first endpoint accepted but never propagated before it dropped leaves a
  nonce gap that later transactions through the next endpoint queue behind; this is a known limit.
- The service's record of a block carries that block's events of the channel in log order.
- A reorganization deeper than the 128 kept blocks hands on the replacing chain's events, but the
  replaced events below the kept blocks are not handed on again as removed.
- A block that the service no longer retains and whose events are read from the endpoints is known to
  the participant only by the events it holds: a reorganization of such a block that leaves no event
  in it is not handed on as removed.
- **Chain finality.** This document's refinement of trust-model assumption A1
  ([../security/trust-model.md](../security/trust-model.md)): every event, receipt and read an
  endpoint returns is treated as final. An included transaction is acted on at its first inclusion,
  reads use the chain head, the progress marker is a block number without a block hash, and an event
  a reorganization removes is logged and ignored, its effects not undone. This is a known-wrong
  simplification on any chain that can reorganize, kept for now because every chain-facing decision
  (genesis install, joins, disputes, reductions, slashing, exits) relies on it. Lifting it is a
  cross-cutting change, not a local fix; see Future Work.
- Recovery queries that deliberately read below the progress marker are not stream deliveries and are
  not subject to the below-marker drop.
- An application log subscription ([`REQ-CHAINOBS-4-JA3YF8`](chain-observation.md#req-chainobs-4-ja3yf8)) has no re-read: a log emitted while
  every endpoint was disconnected is not delivered, and an endpoint that reconnects does not deliver the logs
  it missed. It delivers no reorganization removal. The application that needs completeness reads the
  logs again itself.
- After startup the chain access never fails a request because every endpoint is down: the request waits
  for a reconnect, without a time limit, until shutdown or a stop of reconnects.

## Security considerations

Assets: the completeness and uniqueness of observed manager events, which every dispute, exit, and
membership decision relies on, and the participant's transaction nonces. A lost service connection can
hide events until it is back; the events of the blocks mined meanwhile are delivered once it is, and
listing several endpoints keeps reads and transactions available meanwhile. A redelivered event can be
processed twice; block-scoped identity and the progress-marker drop prevent it. Sending one transaction
to one endpoint at a time avoids leaking it to every endpoint and keeps nonce reconciliation with one
source. Endpoint URLs can carry credentials, so logs and errors name an endpoint only by scheme and host.
A liveness check bounds how long a connection that died silently can hold requests. Every listed
endpoint and the storage diff service are trusted: a dishonest one can forge events and advance the
progress marker so that honest events below it are dropped; cross-checking events is out of scope.
Residual risks, all from the chain-finality assumption: a reorganization's removed events stay applied
(they are handed on as removed and ignored), a transaction acted on at its first inclusion can be
reorganized out while the local state built on its receipt stays, a head read can return state a
reorganization later reverts, and an event in a replacement block below the progress marker is dropped
by the below-marker rule. Other residual risks: a transaction lost with its endpoint leaves a nonce gap,
and a reorganization deeper than the kept blocks, or of a block read from the endpoints that held no
event, is not handed on as removed. The application's chain access uses the same trusted endpoints and
the same liveness check, so it adds no new trust boundary; its log subscriptions come from the
endpoints, deduplicate by block hash and log index but neither re-read missed logs nor report removed
ones, so an application that relies on them alone can miss a log emitted during a full outage or keep
the effect of a removed one.

## Future Work

_Non-normative._ Verify one endpoint's events against another before they advance the progress
marker, and mark endpoints that answer with errors as unhealthy.

_Non-normative._ Lift the chain-finality assumption for events, receipts and reads alike: either act
only on finalized chain data, or track the progress marker by block hash and roll back every effect
of a removed event (local diamond state, storage, the progress marker and any decision taken from
it) together, combined with taking receipt- and read-based decisions only at `finalized` (or
re-checking the including block hash before relying on them).
