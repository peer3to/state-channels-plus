## Purpose and observable model

A participant reads the base chain, sends its transactions, and observes the manager's events through
one or more RPC endpoints of one chain. The endpoints form an ordered list. A single endpoint is the
list of one. Losing the connection to one endpoint must not silence chain observation or stop chain
access while another listed endpoint is reachable, and an endpoint that comes back must not leave a
gap in the observed events.

## Requirements and invariants

**<a id="req-chainobs-1-5jthy8"></a>`REQ-CHAINOBS-1-5JTHY8` — Ordered endpoint set.** The configuration MUST name the endpoints
in priority order. When the list is absent or empty, the single configured endpoint is the whole
list. Every entry MUST be a WebSocket-compatible endpoint; an entry that is not rejects startup.
Startup MUST complete as soon as one listed endpoint is connected; the others keep connecting in
the background, and every connection attempt is bounded in time. When no endpoint connects, startup
MUST fail, naming every endpoint by scheme and host only, and release every connection it opened.
The first connected endpoint fixes the chain: an endpoint that serves another chain MUST be refused
and keeps being retried.

**<a id="req-chainobs-2-2ncsq3"></a>`REQ-CHAINOBS-2-2NCSQ3` — One endpoint per request, with failover.** Every chain request,
read or transaction, MUST go to the first listed endpoint that is connected. It moves to the next
connected endpoint only when that endpoint has no connection or loses it before answering; a request
in flight on a dropped endpoint MUST be answered by the next connected endpoint, not wait for the
dropped one. A transaction MUST NOT be sent to several endpoints at once. An endpoint's own answer,
including a rejection, is final for that request. While no endpoint is connected, a request waits
for the first endpoint to reconnect; the participant MUST warn once when its last connected endpoint
drops. Shutting the chain access down MUST reject every waiting request and every request still in
flight on an endpoint. Stopping its reconnects MUST reject every waiting request; a request in flight
on an open connection then still gets its answer, and fails only if that connection drops.

**<a id="req-chainobs-3-n137zp"></a>`REQ-CHAINOBS-3-N137ZP` — Per-endpoint observation with reconnect and catch-up.** The
participant MUST subscribe to the channel's manager events on every connected endpoint. A dropped
endpoint, including one whose connection stops answering a periodic liveness check without closing,
MUST be reconnected with a bounded backoff, independently of the other endpoints, and its
subscription renewed. After a reconnect, the participant MUST re-read the channel's events on that
endpoint from its completed-block progress marker, inclusive, up to that endpoint's head, so that an
event emitted while the endpoint was down is processed. Events the renewed subscription delivers are
held until the re-read has been scheduled, and the completed-block progress marker MUST NOT advance
past the re-read's first block until the re-read has read up to the head or is abandoned, so neither
a newer event nor one another query completes can move it past blocks not yet read. A re-read is
abandoned, and its hold on the marker ends at once, when its endpoint's connection ends, even while a
read still waits for that endpoint to reconnect, when the channel subscription is cleared or replaced,
or when the participant shuts down; the endpoint's next connection starts a new re-read. A failed
re-read MUST be retried with the reconnect backoff while the endpoint stays connected. After the first
failed read, the retries read the remaining windows through the first connected endpoint, the one every
other request uses, not through the reconnected endpoint, so one endpoint that keeps failing its reads
cannot hold the marker. Those retries MUST still read up to the reconnected endpoint's head: while the
first connected endpoint's head is below it, they read nothing and are retried with the reconnect
backoff. When the reconnected endpoint answers no head at all, they read up to the first connected
endpoint's head. The re-read, and every
other log query, reads block windows no wider than a configured positive maximum, in ascending order,
and schedules each window's events before reading the next; a retry reads again from the window that
failed. A maximum that is not a positive integer MUST reject startup. A liveness check answered with an error proves the
connection alive. Before any event completed a block, the re-read starts at the block where the
subscription began.

**<a id="inv-chainobs-1-asvkc1"></a>`INV-CHAINOBS-1-ASVKC1` — Exactly-once event processing across endpoints.** One chain event
delivered by several endpoints, or by a stream and a re-read, MUST be processed once. Event identity
includes the containing block, so an event re-mined in another block after a reorganization is a new
event. An event the chain reports as removed by a reorganization is logged and ignored; its earlier
effects are not undone. An event an endpoint's stream or re-read delivers below the completed-block
progress marker is dropped: its block is fully processed.

## Assumptions and constraints

- Every listed endpoint serves the same chain; the participant does not merge different chains.
- Every listed endpoint is trusted, a backup included: a listed endpoint can forge events on its
  subscription and advance the progress marker. Verifying one endpoint's events against another is
  out of scope ([../security/trust-model.md](../security/trust-model.md)).
- At least one listed endpoint is honest and eventually reachable.
- A transaction that the first endpoint accepted but never propagated before it dropped leaves a
  nonce gap that later transactions through the next endpoint queue behind; this is a known limit.
- An endpoint delivers a block's events in order on one connection.
- A connection that drops in the middle of one block's events can leave part of that block unread until
  a later recovery query; the inclusive re-read covers the progress-marker block itself.
- Undoing the effects of a removed event is out of scope.
- Recovery queries that deliberately read below the progress marker are not stream deliveries and are
  not subject to the below-marker drop.

## Security considerations

Assets: the completeness and uniqueness of observed manager events, which every dispute, exit, and
membership decision relies on, and the participant's transaction nonces. A dropped or censoring
endpoint can hide events; listing several endpoints and re-reading after reconnect bounds that to the
time all endpoints are unreachable. A lagging endpoint can redeliver old events; block-scoped identity
and the progress-marker drop prevent double processing. Sending one transaction to one endpoint at a
time avoids leaking it to every endpoint and keeps nonce reconciliation with one source. Endpoint URLs
can carry credentials, so logs and errors name an endpoint only by scheme and host. A liveness check
bounds how long a connection that died silently can hide events or hold requests. Every listed
endpoint is trusted: a dishonest endpoint, a backup included, can forge events and advance the
progress marker so that honest events below it are dropped; cross-endpoint verification is out of
scope. A re-read's hold on the progress marker ends when its endpoint's connection ends or when the
first connected endpoint has read its remaining windows, so an endpoint that vanishes during its
re-read, or stays connected and fails every read, cannot hold the marker; only the first connected
endpoint, which every request already depends on, can. Residual risks: a reorganization's removed
events stay applied, a mid-block drop can delay part of a block until recovery, a transaction lost with
its endpoint leaves a nonce gap, and while the first connected endpoint keeps failing a re-read's
windows (a range limit below the configured maximum, a rate limit, a pruned node) or stays behind the
reconnected endpoint's head, the marker stays held: completed work below later blocks is not released and recovery queries read from the held block
until the read succeeds or the re-reading endpoint's connection ends.

## Future Work

marker, and mark endpoints that answer with errors as unhealthy.
