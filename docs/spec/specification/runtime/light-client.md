## Purpose and observable model

A participant reads the base chain through RPC endpoints
([chain-observation.md](./chain-observation.md)). An endpoint that answers a read is believed for the
answer. With the light client on, the participant does not take the answer: it has the endpoint prove
the state the read needs ([storage-proofs.md](./storage-proofs.md)) and works the answer out itself, a
contract call by running the contract in a local EVM over the proven state. To the caller nothing
changes: the same read gives the same answer the endpoint would give for the same block. The light
client is optional: it is on when the endpoint serves the light client endpoints. A participant whose
endpoint does not serve them reads as before, and a participant whose light client fails keeps
reading through the endpoint while the failure is made known.

For the channel a participant follows, the endpoint pushes the channel's partition: every state key
the transactions that logged the channel's id touched, reads included, with a proof under each new
block's state root. The participant reads that state without a request. What the partition does not
hold, it has the endpoint prove at the same block.

## Requirements and invariants

**<a id="req-lc-1-jt5pkt"></a>`REQ-LC-1-JT5PKT` — Reads at the latest block are answered from proven state of one block.** With the
light client on, a contract call, a storage read, a code read, a balance read and a transaction count
read that ask for the latest state MUST be answered from state proven under the state root of one
block, and the endpoint MUST NOT be asked for the answer itself. That block is the newest block a
subscription on the endpoint that serves the participant's requests pushed and the participant
accepted, or that endpoint's best block when none of its subscriptions holds one; what another
endpoint pushed MUST NOT set it. It MUST NOT be below the highest block the participant has seen in the
endpoints' new heads and in the receipts and block numbers they answered: a read whose newest pushed
block is below that MUST wait for the push at most one block time and then read at the endpoint's best
block, and once such a wait timed out, reads MUST NOT wait again until a push is accepted. The answer MUST equal the endpoint's own answer for that block: a returned value, the data
of a revert, and the block values a call reads. Everything one read uses MUST be proven at that one
block. A read made after the participant received a transaction's receipt MUST see that transaction's block
or a later one. A call MUST run on the rules of the chain's EVM: the code size limit, and only
the precompiles the chain serves. What a call writes, a frame that reverted included, MUST NOT be
visible to any later read, and code the call created MUST stay for the rest of the call unless the
frame that created it reverted. Reads made at the same time MUST each get their own answer.

**<a id="req-lc-2-pmy1vg"></a>`REQ-LC-2-PMY1VG` — What cannot be answered from proven state goes to the endpoint.** The following
MUST be sent to the endpoint and are no failure: a read at a block other than the latest, a pending
read, a call that carries a gas limit, a gas price or other fee fields the endpoint must price, a call
that carries value, a call that reaches an address the chain serves with a precompile of its own, a
call that reads the hash of an earlier block or the blob base fee, a call that fails without reverting, and every request
that is not one of the reads of [`REQ-LC-1-JT5PKT`](light-client.md#req-lc-1-jt5pkt). Each call so
left to the endpoint after it started locally MUST be counted apart from failures. A transaction that
was mined and failed without revert data MUST be replayed at the block its receipt names, so that the
endpoint answers the replay at the state the transaction failed on and not an older pushed block.

**<a id="req-lc-3-w7rrhm"></a>`REQ-LC-3-W7RRHM` — A failed read falls back to the endpoint and is made known.** When the light
client cannot answer a read it should answer, because a proof is refused, the endpoint does not give
what a proven read needs, or the read keeps finding state missing after 256 passes, the read MUST be
answered by the endpoint instead, so that the participant keeps working. Every such read MUST be
logged as an error that tells a refused proof from any other failure, and MUST be counted. A later
read MUST be tried from proven state again. A read that fails because the chain access was closed,
destroyed or with no endpoint connected and none reconnecting, MUST fail as it would without the light
client, uncounted and unlogged.

**<a id="req-lc-4-e29y46"></a>`REQ-LC-4-E29Y46` — The light client is on when the endpoint serves it.** At the first read the light
client may answer, and when a channel is followed, the participant MUST ask the endpoint that serves
its requests which methods it serves, unless that endpoint already answered. An answered list, and an
answer that the endpoint does not serve the question (JSON-RPC's "method not found", or the "method not
supported" Hardhat gives), MUST be kept for that endpoint for the rest of the participant's life; each
endpoint is asked on its own. A question the endpoint did not answer MUST count the read as failed, as
[`REQ-LC-3-W7RRHM`](light-client.md#req-lc-3-w7rrhm) requires, and MUST be asked again at the next
read. While the serving endpoint does not list the light client endpoints, every read MUST go to it as
without the light client, MUST be counted, and the participant MUST log once per endpoint, not as an
error, that the endpoint does not serve them; the participant MUST NOT start its subscriptions then.
A connection whose endpoint answers a subscribe that it does not serve the method MUST NOT be asked to
subscribe again, and this MUST be logged once, not as an error.

**<a id="req-lc-5-mm0bm9"></a>`REQ-LC-5-MM0BM9` — A followed channel is subscribed on every connection.** The participant can be
told to follow a channel of a contract, and to stop. While a channel of a contract is followed and the
endpoint serves the light client endpoints, the participant MUST hold one subscription for that
contract and the log topics of its followed channels on every connection to an endpoint, MUST
subscribe again on a connection that reopens, and MUST end the subscription when no channel of the
contract is followed. What a connection that ended pushed MUST NOT be used. A channel followed while the
endpoint has not answered which methods it serves MUST stay followed, and its subscriptions MUST be
made once the serving endpoint answers that it serves the light client endpoints, when the next channel
is followed or at the next read.

**<a id="req-lc-7-w8wdn3"></a>`REQ-LC-7-W8WDN3` — A refused or ended subscription syncs again and is made known.** A pushed
message that [`REQ-STPROOF-3-NVJGR0`](storage-proofs.md#req-stproof-3-nvjgr0) rejects MUST leave its
subscription holding nothing, MUST be counted and logged as an error, and the participant MUST open the
subscription again after one block time (2 s), so that the endpoint syncs it and an endpoint whose
messages keep being refused is not asked for a whole partition at every round trip. A subscription the
endpoint ends MUST be opened again after the same wait, and the endpoint's reason MUST be logged as a
warning. Each opening again MUST be counted. Until the new sync arrives, reads MUST be answered as
[`REQ-LC-9-KWXV43`](light-client.md#req-lc-9-kwxv43) requires for state no subscription holds; they are
no failed reads.

**<a id="req-lc-8-bbyc51"></a>`REQ-LC-8-BBYC51` — A participant follows the channel it has selected.** When a participant selects
a channel, it MUST tell its chain access to follow that channel of the channel's contract, with the
channel's id as the log topic. When it clears the selection, selects another channel or is disposed,
it MUST tell its chain access to stop. Chain access without the light client MUST ignore both.

**<a id="req-lc-9-kwxv43"></a>`REQ-LC-9-KWXV43` — A read takes from the pushed partitions what they prove at its block.** A read
at a block MUST take every value that the state a subscription on the serving endpoint holds at that
block proves, and MUST NOT ask the endpoint for it. Only what none of those subscriptions' state proves
at that block MUST be proven by
the endpoint at that block, in one request per pass. The block values a call reads MUST be those of the
Ethereum header the subscription's message carried for that block. A read answered without any request
to the endpoint MUST be counted apart from a read that needed a proof from it. A read that waits for a
proof from the endpoint MUST NOT keep another read from running.

**<a id="req-lc-10-ycp80w"></a>`REQ-LC-10-YCP80W` — The stages of each accepted pushed block are kept.** For each pushed message
the participant accepts, it MUST keep the block's number, the times the endpoint gives for the end of
the block's execution, for the message being complete and for its sending, the times the participant
received and verified it, and how many proof nodes it added and holds: the last 1024 of them, readable
by the operator with the counts.

## Assumptions and constraints

- The chain is one whose state the participant can check: a Frontier chain with the constants, the
  EVM rules and the precompiles of the configured chain. The first and only chain is peer3. The local
  EVM's package knows no hardfork after Prague while the chain runs Osaka: an opcode only Osaka has
  fails locally, and such a call goes to the endpoint.
- The endpoint's header is taken as the chain's ([storage-proofs.md](./storage-proofs.md)). The light
  client checks answers against the block the header names; it does not check the block against the
  chain.
- The local EVM runs a call as Ethereum does. Gas is not charged as the chain charges it, so a call
  that depends on a gas limit is the endpoint's.
- The chain reports a balance less the existential deposit it keeps back. A call that carries value
  goes to the endpoint; a transfer inside a call to an account below the deposit is reported locally
  without it.
- What no subscription holds is proven for one read at one block and kept only for reads at the same
  block.
- A partition holds what the channel's transactions touched. The channel's contract is assumed to log
  the channel's id in every transaction whose reads and writes the channel's own reads use; a key no
  such transaction touched is proven at each read.
- The endpoint pushes every best block to a subscription, in block order. A read waits for a push only
  when it lags the highest block seen in new heads and receipts, and at most one block time; otherwise
  it reads at the newest block the serving endpoint's subscriptions hold. The engineer decided this
  block floor on 2026-11-21. The engineer decided on
  2026-11-20 that with several endpoints only the one serving the participant's requests sets that
  block.
- A fallback gives the participant the endpoint's unproven answer. The counts and the error log are how
  an operator learns that reads are not being proven.

## Security considerations

Assets: the chain state a participant decides from. Trust boundary: the endpoint is untrusted for the
state it serves; the header of a block is taken on its word. Threats and defenses: an endpoint that
answers a read with a wrong value is not asked for the value; an endpoint that proves or pushes a
wrong value is refused by the proof check, and a refused push is logged and counted and makes the
subscription sync again; an endpoint that refuses to prove, or proves another block, makes the read
fall back to its unproven answer, which is the same trust a participant without the light client
gives, and the fallback is logged and counted so that it does not pass unseen; an endpoint that stops
pushing while its new heads move on makes reads wait one block time once and then read, proven, at its
best block; an endpoint whose new heads stop too leaves reads at the last block it gave, as an endpoint
whose best block stops moving would;
with several endpoints, a made-up header from an endpoint that does not serve the participant's
requests cannot move the block reads are made at.
Residual risks: an endpoint that makes up a consistent header and the state under it, an endpoint that
lies consistently about which block is the best one, and a participant that ignores the counts.
