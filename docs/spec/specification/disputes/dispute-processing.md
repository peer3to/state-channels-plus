## Purpose and observable model

A dispute pipeline converts a stalled or contested off-chain fork into an objectively auditable base-layer
decision. It binds intake to a channel and fork, reconstructs the claimed history, verifies authorization and
proofs in protocol order, classifies fraud or unavailability, reduces to the canonical survivor set, creates
the successor fork, and returns participants to normal execution without losing evidence.

Every honest participant embodies three roles at once: **disputer** (escalate when cooperation
broke), **auditor** (validate every dispute others commit on-chain, killing invalid ones during the
kill period), and **reducer** (fold the window's committed disputes into one successor fork after
the kill period and return to execution). The game's rules — valid inputs, window lifecycle,
precedence, reduction algebra — are owned by [disputes.md](./disputes.md); this document owns the
processing algorithm that plays them.

## Pipeline algorithm

### Stage 1 — Escalation (disputer role)

Escalation is once per fork per node, and a failed submission releases that guard for retry. The
triggers and the dispute input each contributes:

| Trigger                                                                                                                                                                    | Contributed input ([`REQ-DIS-1-XAJ1VA`](disputes.md#req-dis-1-xaj1va))                      |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Objective block fault observed by the block pipeline ([`REQ-BLOCK-PIPE-8-N529VH`](../block-progression/block-processing.md#req-block-pipe-8-n529vh))                       | The stored fraud evidence, applied on-chain in the same atomic submission → slash-set entry |
| Author timeout detected (below)                                                                                                                                            | The timeout claim                                                                           |
| Voluntary exit without unanimous signatures                                                                                                                                | Self-removal                                                                                |
| Own join ignored beyond the inclusion window ([`REQ-IX-3-H8WCVY`](../interactions.md#req-ix-3-h8wcvy))                                                                     | Forced inbound inclusion (on-chain inbound tip newer than the fork's applied tip)           |
| Slash observed on an undisputed fork; a killed dispute leaving its window empty; reduction finding an empty window; audit finding the node holds outcome-changing evidence | The node's own view with merged evidence                                                    |

**Timeout detection.** After every committed block, schedule a check for the next scheduled
author: skip when the target is the node itself, the node does not participate, or the block
arrived. When due (previous relevant timestamp plus the full cooperative window,
[time.md](../protocol-model/time.md)): do not submit into a window that opened before the timeout
became valid; recover the _predecessor's_ on-chain posting first (it may grant the target extra
time — reschedule); then check the _target_ slot's calldata commitment — a commitment whose block
the pipeline did not accept yields a **forced** timeout claim, no commitment a normal one. Build
the claim with its evidence context (previous producer, its posting status, the target's signature
on the predecessor — which forfeits the extra time) and escalate.

### Stage 2 — Construction and submission (disputer role)

1. **State proof** for the fork's latest committed height, built as a compact milestone proof
   from the node's local view of the walk start ([state-proofs.md §4](./state-proofs.md)): one
   milestone at each participant-set change point above the start, the latest threshold-proven
   milestone, and the unfinal tail; or one run from the block at the start height when no
   threshold point lies above the start. A requested height below the start, or a missing or
   unlinked required block, is a construction error
   ([`REQ-DISPUTE-PIPE-13-W73B2F`](dispute-processing.md#req-dispute-pipe-13-w73b2f)).
2. **Slash set:** the on-chain set intersected with participants, plus — for offenders the node
   holds unapplied evidence against — the fraud proofs themselves, ordered _before_ the upload in
   one atomic submission, so the dispute's claimed slashes are a subset of the on-chain set when it
   executes (fraud enforcement stays separate from reduction, [fraud-proofs.md](./fraud-proofs.md)).
3. **Timeout claim** if held; **auditing data** (genesis snapshot data, per-milestone snapshots,
   latest state and finalized encoded state, linking stream ranges) — construction aborts rather
   than submitting partial data.
4. **Pre-committed outcome:** compute the successor-fork genesis via the mirrored reduction logic
   ([`REQ-MIRROR-1-XCY9CB` (Constrained equivalence)](../enforcement/local-mirror.md#req-mirror-1-xcy9cb)) and embed its hash — the dispute commits to
   its own reduction result.
5. **Data availability decision:** post the auditing data as calldata unless the proof's final
   anchor is provably final to everyone ([`REQ-DIS-*` upload rules](./disputes.md)). Posting is
   always admissible, only costlier, so a mirror answer of "not final" posts without asking the
   chain; omitting the data is slashable when the anchor is not final, so it follows only a
   chain-confirmed "final" ([`REQ-MIRROR-4-H9C4YS` (Local-first evaluation, adverse answer confirmed)](../enforcement/local-mirror.md#req-mirror-4-h9c4ys)).
6. **Sign and submit atomically** (evidence applications + upload). Classify races: ineligibility
   (the node was slashed), a window opened too early for the timeout, or an expired evidence
   window; roll back the once-per-fork guard on failure. The finished proof is not checked
   against the chain before signing: the chain walks it from its own start, which accepts a proof
   built from an older local view of the start
   ([`REQ-DISPUTE-PIPE-13-W73B2F`](dispute-processing.md#req-dispute-pipe-13-w73b2f)).

### Stage 3 — Chain intake (auditor role)

Disputes never arrive over peer communication; the chain is the sole intake
([`REQ-IX-7-A004VZ` (Chain observation)](../interactions.md#req-ix-7-a004vz)). For each observed dispute event: replicate into the
local mirror, deduplicate by dispute identity, and gate by relevance (the disputed fork is the
node's current fork, or a decided dispute for a fork with in-progress recovery — late events for
resolved forks are ignored). Relevant disputes purge the dead fork's queued blocks and trigger the
one-round [dispute acknowledgment](../peer-communication/dispute-acknowledgment.md).

### Stage 4 — Audit (auditor role)

The audit runs the ordered checks below; the first failure stores **exactly one** dispute fraud
proof identifying the violation and stops — audit-invalid without stored evidence is an internal
error, never a silent kill. Every predicate with an on-chain twin is evaluated through the mirrored
canonical logic so the auditor can never disagree with the chain's own apply-handler
([`REQ-DISPUTE-PIPE-5-RZZB48`](dispute-processing.md#req-dispute-pipe-5-rzzb48)); checks whose staleness could cause a wrong kill re-verify against the
chain. Stateful predicates run on the mirror first: an answer that clears the dispute is accepted
locally, and an answer that would produce a fraud proof is re-evaluated by the chain before the
proof is stored ([`REQ-MIRROR-4-H9C4YS` (Local-first evaluation, adverse answer confirmed)](../enforcement/local-mirror.md#req-mirror-4-h9c4ys)). Pure predicates (the proof-header match and the
input-only block-structure check) compute the same answer on the mirror as on the chain and need no
confirmation. State-proof verification follows the three-tier order of
[`REQ-SP-9-7MWKY8`](state-proofs.md#req-sp-9-7mwky8): a valid local walk is final, only the chain
answers invalid, and a verification error propagates with no verdict.

**Full audit, no abstention.** An honest auditor audits every dispute in full; it never skips a
dispute as valid and never abstains. It persists the verified material it lacks (blocks,
snapshots, states) so that it can reduce later, and it recovers missing chain events through
event recovery ([`REQ-IX-7-A004VZ` (Chain observation)](../interactions.md#req-ix-7-a004vz)). Data still missing after recovery is an internal failure: the
audit ends with an error, with no verdict and no fraud proof. A missing local baseline is never
grounds for a kill ([`REQ-DISPUTE-PIPE-5-RZZB48`](dispute-processing.md#req-dispute-pipe-5-rzzb48)).

1. The claimed inbound tip is a real on-chain inbound tip.
2. The state proof is judged as given: an undecodable block of the last milestone is a structure
   violation (item 4), and an undecodable block elsewhere is judged by the proof verification;
   neither makes the dispute unjudgeable.
3. The proof header matches the dispute's claims; 4. every block of the last milestone is
   structurally valid (the first invalid position is the evidence). This check is input-only and
   reads no replicated state ([`REQ-SP-10-AM67R2`](state-proofs.md#req-sp-10-am67r2)).
4. Without posted data, the last milestone must be final by everyone (the data obligation comes
   before any proof verification); otherwise `DisputeLastMilestoneNotFinalAndNoAuditingData`.
   Then a claim strictly below the chain's same-fork non-genesis snapshot, including an empty
   proof, yields the below-anchor counter; this check reads the chain's start, never the mirror's
   ([state-proofs.md §7](./state-proofs.md)); this check applies with and without posted data.
   Then the proof is verified
   ([`REQ-SP-9-7MWKY8`](state-proofs.md#req-sp-9-7mwky8)); a verification error propagates out of
   the audit with no verdict and no counter. With posted data an invalid answer yields
   `DisputeInvalidStateProof`; the node then persists only material the walk verified at or above
   its start, never a dropped milestone. Without posted data `DisputeInvalidStateProof` follows only
   from a broken link or a wrong latest state; a failed finality check alone yields no counter. A
   last milestone the node does not hold locally is no reason to skip the dispute: the replay
   below rebuilds it.
5. **Replay the unfinal tail** — the last milestone from the first block that the chain's own
   block-challenge eligibility admits — through the block pipeline in its dispute-replay context
   ([block-processing.md](../block-progression/block-processing.md)). Each block is judged from its
   predecessor on the dispute's own chain; tail blocks the node already validated and holds are
   not replayed again. Deviations become dispute fraud proofs that name the block by its index in
   the last milestone; a discovered double-sign stores ordinary fraud evidence and continues (the
   dispute may still be honest); local gaps alone must not kill an honest dispute — only canonical
   structural failure does. Nothing before the tail start is replayed. The replayed snapshots and
   states are persisted, so the node can reduce the dispute even when its head lies on a history
   other than the node's own ([`REQ-DISPUTE-PIPE-5-RZZB48`](dispute-processing.md#req-dispute-pipe-5-rzzb48)).
6. The claimed latest state is consistent with the replayed proof; 8. claimed slashes are a subset
   of the on-chain set (re-checked against the chain before proving); 9. the balance invariant
   holds on the dispute's latest state ([cross-layer-messages.md](../settlement/cross-layer-messages.md),
   [`REQ-SP-10-AM67R2`](state-proofs.md#req-sp-10-am67r2)); 10. the disputer used its own latest known state (a withheld newer signed block is evidence).
7. Timeout claims: linked to the proof tip; the target is the scheduled next author; not too
   early (strict inequality; extra time forfeited only when the target's posted signature on the
   predecessor verifies); the target's block is not threshold-signed; and not posted as timely
   calldata — this last proof is **preflighted** through the mirror because an incorrect
   submission self-slashes ([`REQ-DISPUTE-PIPE-5-RZZB48`](dispute-processing.md#req-dispute-pipe-5-rzzb48)).
8. The dispute states a valid reason ([`REQ-DIS-1-XAJ1VA`](disputes.md#req-dis-1-xaj1va)); 13. the pre-committed output
   is correct: the claimed successor genesis must equal the mirrored recomputation.

### Stage 5 — Outcome handling (auditor role)

- **Decided dispute** (the window finalized at upload): no audit — persist, derive the auditing
  data locally if unposted, and adopt the pre-committed outcome. Only participants and pending
  participants handle this case; a non-participant aborts on the event, as on every dispute event.
- **Kill period already expired:** challenging is forbidden, but the node still audits the
  dispute in full (the replay stores the dispute's tail by content), records an invalid verdict and
  never kills; it then persists the dispute and schedules reduction at the window's end.
- **Audit-invalid:** submit the stored dispute fraud proof to kill (guarded by a fresh window
  read; kill races tolerated). The kill lands before any counter-dispute so the killed disputer's
  slash gives the replacement its stated reason; when a kill empties the window, honest nodes
  upload replacement evidence — first wins, the race is convergence.
- **Audit-valid:** persist; then the **evidence-improvement rule** ([`REQ-DISPUTE-PIPE-6-6FZB9M`](dispute-processing.md#req-dispute-pipe-6-6fzb9m)): compare
  the reduction of the observed dispute set with and without the node's own constructible dispute —
  upload only when the outcome differs (a no-op when the node already holds a commitment in the
  window), and schedule reduction at the window's end in every case, so a window whose only new
  evidence is the node's own never stalls without a reducer. An upload that the chain refuses
  because the window's evidence period has ended is not a failure of the audit: no evidence can
  join the window any more, so the node still schedules the reduction. A node that already disputed the
  fork never runs the comparison; this check comes first. Otherwise the comparison runs once per
  disputed fork: reduction merges evidence monotonically, so evidence that adds nothing to the
  first audited dispute adds nothing once more disputes land. That argument holds only while the
  compared dispute stays in the window, so a kill of any dispute on the fork drops the stored
  answer and the next audit of the fork compares again. Concurrent audits share one comparison; a
  comparison that fails is retried by the next audit; a comparison that cannot complete because the
  node's own auditing data is only partly recoverable is no answer and is not stored, so the next
  audit retries it once the data may be back; a positive answer stands, so a failed upload is
  retried by the next audit. The stored answer ends with the fork's reduced result. This rule only
  decides whether the node joins another participant's dispute: the node's own evidence of a new
  fault (fraud, a timeout, a leave) is disputed through that fault's own path and never waits on
  this comparison.

### Stage 6 — Reduction and successor installation (reducer role)

1. At the window's kill-period end (re-checked, not assumed): the fork must still be relevant, the
   window must exist on-chain, and the period must be expired.
2. **Load the committed dispute set from chain-synchronized records only** — a reducer never
   reduces a window its own replicated evidence cannot back; missing events are recovered by
   bounded targeted queries first. An empty window becomes an own-dispute escalation instead.
3. **Compute** the reduction and the successor genesis through the mirrored canonical logic; the
   successor fork id is the hash of the reduced genesis data.
4. **Simulate the on-chain finalization first**; classify races as convergence (another reducer
   committed the identical deterministic result → adopt) or supersession (a decided dispute's
   outcome won → stand down).
5. **Install locally, then submit**: adopt the successor genesis (the fork-transition point —
   queues drain, membership status recomputes, author-timeout scheduling restarts), then submit
   the finalization and snapshot advance detached. A completed reduction that resolves to a
   different successor than computed is a fatal inconsistency, not a retry.
6. **Foreign reductions observed on-chain:** recompute; a mismatch is challenged within the
   challenge period and the dishonest reducer penalized; a match with an expired period is adopted.

Valid non-final transitions from the disputed fork are carried forward _inside_ the reduction
output ([`REQ-DIS-6-Y92H1M`](disputes.md#req-dis-6-y92h1m)); the pipeline never replays them onto the successor.

## Requirements and invariants

**<a id="inv-dispute-pipe-1-bn0k81"></a>`INV-DISPUTE-PIPE-1-BN0K81` — Equivalent audit.** Every auditor given the same chain state and complete evidence
MUST reach the same validity, offender, reduction, and successor-fork result.

**<a id="req-dispute-pipe-1-hrbfp7"></a>`REQ-DISPUTE-PIPE-1-HRBFP7` — Bound intake.** Local escalation and chain-observed intake MUST bind the dispute,
proofs, acknowledgements, and evidence to the exact manager, channel, fork, and dispute instance.

**<a id="req-dispute-pipe-2-mjrjv1"></a>`REQ-DISPUTE-PIPE-2-MJRJV1` — Ordered complete verification.** Audit MUST verify authenticity, authorization,
commitment linkage, final/unfinalized boundaries, replayed transitions, messages, time, and claimed outcome
before accepting or reducing a dispute. Only participants and pending participants audit: data availability is guaranteed to them.
Any other observer (a spectator) does not audit or follow a dispute and builds no counter; for now it aborts
its runtime on every dispute event of its fork, new, final or expired ([`OQ-SPEC-SPECTATOR-DISPUTE-1-Y1FNMM` (What a spectator does during a dispute)](../open-questions.md#oq-spec-spectator-dispute-1-y1fnmm)).

**<a id="req-dispute-pipe-3-phe3sq"></a>`REQ-DISPUTE-PIPE-3-PHE3SQ` — Deterministic reduction.** Proven fraud, unavailable peers, and valid survivors MUST
be treated according to distinct specified rules; removal order or evidence arrival order MUST NOT alter the
canonical successor state. Runtime disposal is terminal for reduction: a disposed peer settles every pending
reduction without an outcome for every caller, without waiting for an in-flight attempt's chain or VM calls, creates no new attempt, and commits no reduction-owned state (genesis, fork,
status, timers, hooks, transaction), apart from the deterministic terminal outbound block persisted during
candidate preparation. A failed state-machine read after the canonical genesis write aborts the live runtime
instead of committing. A pending leave re-homed by a direct final-dispute reduction settles exactly once.

**<a id="req-dispute-pipe-4-3yvdsa"></a>`REQ-DISPUTE-PIPE-4-3YVDSA` — Atomic recovery.** Evidence persistence, chain action, local fork replacement, queue
reset, and resumed execution MUST either converge on the accepted successor or remain safely retryable.
Sync-payload verification remains separate from the normal reduction workflow. After verified
synchronization installs a different fork, the previous fork's pending shared reduction operation
MUST settle without an outcome for every awaiting caller, cancel its timer and cease to be pending.
An already-completed reduction retains its actual result. In-flight obsolete work MUST not write,
reschedule or recreate its operation after an awaited read. Synchronization does not supply a
reduction result to that operation.

**<a id="req-dispute-pipe-5-rzzb48"></a>`REQ-DISPUTE-PIPE-5-RZZB48` — Mirrored canonical audit.** Every audit predicate with an on-chain twin is
evaluated through the same canonical logic ([`INV-MIRROR-1-VAF778` (Single implementation)](../enforcement/local-mirror.md#inv-mirror-1-vaf778)); an
audit verdict of invalid stores exactly one dispute fraud proof before any kill attempt;
self-slashing proof types are preflighted before submission; and the auditor never skips or
abstains: it audits every dispute in full, persists the verified material it lacks, recovers
missing chain events through event recovery, and treats data still missing after recovery as an
internal failure (an error, no verdict, no fraud proof), never as grounds for a kill.
The block-structure predicate is input-only: it reads no replicated state, so its local verdict is
the chain's verdict and is acted on with no chain read; it covers only the last milestone
([`REQ-SP-10-AM67R2`](state-proofs.md#req-sp-10-am67r2)). State-proof verification follows
[`REQ-SP-9-7MWKY8`](state-proofs.md#req-sp-9-7mwky8): only the chain answers invalid, and a
verification error is never grounds for a fraud proof. The below-anchor check reads the
chain's walk start, never the mirror's.

Replay judges only the unfinal tail of the last milestone: from the first block of the last
milestone that the chain's block-challenge eligibility admits (the tail start), never a block the
chain treats as final. Replay does not repeat the structure check. Each replayed block is judged
from its predecessor on the dispute's own chain: the block before it in the last milestone with
that block's snapshot and state, or, for the tail start, the block before it (the fork genesis for
index 0) with its held snapshot and state. Tail blocks the auditor already validated and holds
with their snapshot and state are not replayed again. A transition or author fraud proof is built
from that same predecessor, so it names the block the judged block links to and the state it was
judged from. The auditor persists every replayed snapshot and state by content, so a dispute head
on a history other than the auditor's own stays reducible. A replay base the auditor does not hold,
or a replayed block refused without a fraud proof, is an internal failure with no verdict.

**<a id="req-dispute-pipe-13-w73b2f"></a>`REQ-DISPUTE-PIPE-13-W73B2F` — Proof construction from the local start.** A
node builds every state proof it submits or serves — its own dispute, a same-fork snapshot post, a
synchronization response — from its own local view of the walk start of
<a id="req-sp-8-9pk9ts"></a>`REQ-SP-8-9PK9TS`. The proof is compact: one milestone at each
participant-set change point above the start, the latest threshold-proven milestone, and then the
unfinal tail up to the requested height; without any threshold point above the start it is one run
from the block at the start height (block 0 for a genesis start). History between two threshold
points with an unchanged set is not included. Milestones may overlap or share a first block. A
snapshot post stops at the last threshold point and adds no tail. A request for height −1 is the
empty proof. A requested height below a non-genesis start, a missing participant-change block, and
a missing or unlinked block of a required run are construction errors, not abstention: the
operation fails and its caller handles the failure as for any failed construction (an escalation
uploads nothing and rolls back its signing marker and once-per-fork guard as after a failed upload).
The finished proof is not checked against the chain and not rebuilt before submission: the chain
walks it from its own start, so a proof built from a lagging local start stays acceptable
(milestones that a newer chain start makes wholly lower are dropped).

**<a id="req-dispute-pipe-6-6fzb9m"></a>`REQ-DISPUTE-PIPE-6-6FZB9M` — Minimal intervention and convergence.** A node uploads its own dispute in
response to a valid observed one only when its evidence changes the reduced outcome; concurrent
reducers' identical deterministic results classify as convergence, not conflict; and replacement
evidence after a kill follows first-wins semantics. Redundant on-chain actions MUST NOT occur when
the outcome is already determined.

**<a id="req-dispute-pipe-7-76n72x"></a>`REQ-DISPUTE-PIPE-7-76N72X` — Combined membership intent.** When one
dispute carries a pending force join and self-removal, replay MUST apply the newest inbound join message before
self-removal. This holds whether the pending join is the leaver's own or another signer's: a leaver whose exit waits
on another signer's unconsumed join replays that join first, which seats that joiner. Omitting that required inbound message anchors the dispute below the chain's inbound head, so upload
refuses it ([`REQ-DIS-2-PKVZ7E`](disputes.md#req-dis-2-pkvz7e)). A leave requested after a force-join dispute was already submitted MUST wait for that fork to settle;
it completes if absent or retries self-removal only on the next active fork if still present.

**<a id="req-dispute-pipe-8-bvr8xv"></a>`REQ-DISPUTE-PIPE-8-BVR8XV` — Dispute admission orders block signatures.**
Dispute admission and block signing/storage MUST share one ordering boundary. Work already admitted to
that boundary finishes signing and stores its signed state before the dispute sets its single local
"I disputed" marker. Setting that marker is the linearization point: construction follows it and
includes the completed admitted work; later work MUST NOT author or counter-sign on that fork.
Callers already holding the state boundary request dispute work without awaiting reacquisition.
Construction and network submission MUST run after releasing the state boundary. A failed upload rolls
the marker back and permits block work on the same fork again. After a successful upload, block work
resumes only on a successor fork. The live ingest dead-fork gate rejects arrivals under the marker.

**<a id="req-dispute-pipe-9-tdwqpv"></a>`REQ-DISPUTE-PIPE-9-TDWQPV` — Existing-window state contributions.**
`DisputeInput.requireExistingDisputeWindow` is a signed boolean. False adds neither an admission
precondition nor a dispute reason. True requires an existing unfinalized evidence window for the same
channel and fork before submission changes any window, throttle, or commitment state. The window is
closed at its evidence deadline; zero surviving commitments do not close a window before that deadline.
An absent, expired, or finalized window MUST reject with `RaceConditionDisputeWindowNotOpen(channelId,
forkId)`. Both upload methods and their use through multicall obey this rule. False retains admission
for a new window and an expired window whose commitments were all killed.

Once accepted, true is sufficient reason for the off-chain auditor and on-chain invalid-reason
validator, even after other disputes are killed. It does not imply self-removal and does not bypass
any state, signature, auditing-data, eligibility, or attribution check. Honest construction uses true
for a state contribution with no other valid reason; a valid independent reason permits false.

On this specific submission refusal, the node rolls back its signing marker, releases its dispute
lock, recovers authoritative on-chain slashes through the ordinary timestamped event recovery owners,
and re-enters normal construction/submission when observation has changed since construction. A slash
already delivered after construction also counts as new observation. Unchanged observations stop
without spinning; normal construction decides whether an observed slash is eligible. Recovery failure
remains visible. Expected errors remain handled by the ordinary dispute and recovery paths. Any
unexpected error escaping those paths MUST reach existing top-level error handling: direct awaited
callers receive the rejection; background attempts use the existing detached-error route. There is
no swallowing or log-only exception. Such an unaccounted failure is fatal to the application/test
operation. Disposal or a changed fork prevents obsolete re-entry. No surviving original dispute is
required.

**<a id="req-dispute-pipe-10-bt8yar"></a>`REQ-DISPUTE-PIPE-10-BT8YAR` — Recheck an early timeout submission.** When a timeout submission is refused
because the executing chain timestamp is below its minimum timestamp, clear the failed attempt's
signing marker and schedule a fresh timeout check after `max(1, minimum - chainTimestamp)` seconds.
Release the dispute serialization boundary before scheduling. The check must use current evidence and
ordinary construction, not resend the signed transaction. Recheck fork relevance, disposal, membership,
block arrival, calldata and window eligibility. A changed fork, disposed runtime or accepted target
block stops obsolete work. A window created before the timeout minimum remains ineligible; waiting
cannot change its creation time. Another early refusal may schedule another check. No earlier admission,
new time threshold, or general error retry is introduced; other errors retain their existing policy.
A refusal because the target already posted calldata for that height is not a recheck case: it is
owned by [`REQ-DISPUTE-PIPE-11-HRGJ43`](dispute-processing.md#req-dispute-pipe-11-hrgj43).

**<a id="req-dispute-pipe-11-hrgj43"></a>`REQ-DISPUTE-PIPE-11-HRGJ43` — Release a timeout refused for posted calldata.** When a timeout
submission is refused because the target already posted calldata for the timed-out height, the
refusal is base-layer proof that the target did produce a block for that slot. The node MUST drop
its stored timeout candidate for that slot, and it MUST drop only that candidate: the deletion
matches the refused height and participant and never removes a forced candidate stored since. It
MUST then deliver the posted block for that slot from its own calldata observations back to the
block pipeline exactly once, after the signing marker is released, because the node's own
provisional dispute marker is what withheld that block from judgment. The delivery uses ordinary
ingest and ordinary validation; the pipeline's verdict on that block, not the refusal, decides what
follows. No timeout check is re-armed, no transaction is resent, and no delay is derived from the
refusal. If the block is not in local observations yet, the ordinary chain-event path delivers it.
Any other failed dispute submission (another refusal or a failed send) MUST likewise deliver the
posted block for the fork's next slot from local observations back to the pipeline exactly once after
the marker is released, because the same marker withheld it; only the posted-calldata refusal drops a
stored timeout candidate.

**<a id="req-dispute-pipe-12-f85kf2"></a>`REQ-DISPUTE-PIPE-12-F85KF2` — Force a timeout only over a rejected posted block.** A timeout check
that finds a posted commitment for the slot it is judging MUST NOT submit a forced timeout on that
observation alone: while the block pipeline owns that block, the timeout is unproven and killable.
Such a check MUST instead deliver the posted block back to the pipeline once and return. Only the
chain-committed validation context, on rejecting that posted block for a fault it cannot prove on
chain — failed author authentication, or a block not linked to the latest proved state — MAY
request a forced check for that block's author and height. A forced check keeps every ordinary
eligibility rule: the deadline MUST have passed, a window created before the timeout minimum stays
ineligible, and the forced submission is made only while the target is still the next writer at the
next unfilled height, decided atomically against local state. A provable fault needs no timeout: its
fraud-proof dispute is the response, and it slashes the author. A check for a height whose
predecessor is not stored locally returns without submitting or rescheduling; the check armed for
that predecessor's slot judges it instead.

## Assumptions and constraints

- Base-layer ordering and finality are authoritative for dispute state.
- Required calldata, signed history, messages, and state encodings remain available during the evidence window.
- Replay uses the same deterministic application semantics as ordinary validation.
- Multiple observers and participants may process the same dispute concurrently or after restart.
- Audit deadlines inherit the chain-observation freshness assumption
  ([`REQ-IX-7-A004VZ` (Chain observation)](../interactions.md#req-ix-7-a004vz)); the windows come from the chain's configuration —
  the pipeline reads them, it never computes its own authority over them.
- Participants and pending participants hold the data an audit needs
  ([data-availability.md](../security/data-availability.md)); missing chain events are recovered
  through event recovery, and data still missing after recovery is an internal failure, not an
  abstention.

## Security considerations

Threats include false dispute claims, cross-channel/fork evidence, truncated proof suffixes, forged
acknowledgements, inconsistent off-chain/on-chain validators, evidence withholding, replay divergence,
order-dependent reduction, duplicate chain actions, and restart races. Audit must fail closed without
destroying evidence required for another honest participant to complete recovery. Two asymmetries
deserve emphasis: killing is a staked act (an invalid kill self-slashes — hence mirrored predicates
and preflight, [`REQ-DISPUTE-PIPE-5-RZZB48`](dispute-processing.md#req-dispute-pipe-5-rzzb48)), and a lack of local data is never grounds for a kill: the
auditor recovers the data or fails with an internal error and no verdict, so a false kill cannot
come from local ignorance.

A lagging local copy of the on-chain snapshot cannot cause a false kill: the structure check is
input-only, a local proof verdict of invalid is never acted on until the chain answers invalid
([`REQ-SP-9-7MWKY8`](state-proofs.md#req-sp-9-7mwky8)), and the below-anchor check reads the chain's
start. The same lag on the disputer side is harmless: the chain walks a proof built from an older
local start from its own start ([`REQ-DISPUTE-PIPE-13-W73B2F`](dispute-processing.md#req-dispute-pipe-13-w73b2f)).

A Byzantine disputer can put blocks at or below the start height into its proof that link to
nothing (the chain accepts them, [`REQ-SP-8-9PK9TS`](dispute-processing.md#req-sp-8-9pk9ts)). An honest auditor with full history that replayed
such a block would build a transition fraud proof from its own predecessor, which the chain refuses,
and would be slashed. Auditors therefore judge only the unfinal tail of the last milestone that the
chain's own eligibility admits, each block from its predecessor on the dispute's own chain, and they
build a fraud proof from that same predecessor. A claim that ends below the start is killed by the
below-anchor counter. Residual: an auditor whose audit fails with an internal error gives no verdict
and leaves the dispute to the other auditors; if every honest auditor fails, an invalid tail survives
the kill period and the longest valid proved history decides the reduction. The start height and the chain tier read the
auditor's own chain view; a dishonest chain view is outside the trust model.

A forced timeout is the only answer to calldata whose fault cannot be proved on chain, and it is
exactly as strong as the on-chain check of that calldata's validity: if the base layer treats any
timely, state-transition-consistent posting as defeating the claim, a participant who crafts such a
posting can overturn a justified forced timeout and penalize the honest claimant. The off-chain
rules therefore keep forcing as narrow as possible — never on an unjudged posting, never away from
the target's own turn, never before the deadline ([`REQ-DISPUTE-PIPE-12-F85KF2`](dispute-processing.md#req-dispute-pipe-12-f85kf2)) —
and releasing a refused claim ([`REQ-DISPUTE-PIPE-11-HRGJ43`](dispute-processing.md#req-dispute-pipe-11-hrgj43))
keeps a moot claim from being carried into later escalations on the same fork.

The once-per-fork evidence comparison ([`REQ-DISPUTE-PIPE-6-6FZB9M`](dispute-processing.md#req-dispute-pipe-6-6fzb9m)) trades repeated work for a stored answer, so the
stored answer must never outlive its premise. A Byzantine disputer could otherwise post a weak dispute
first, let honest nodes store "no more evidence" against it, and then have that dispute killed so the
window keeps only weaker evidence. Dropping the stored answer on every kill of the fork, and never
storing an incomplete comparison, keeps the answer tied to a dispute that is still in the window.
The comparison still runs only when an audit of the fork happens, as it did before the answer was
stored; the reducer's empty-window escalation covers a window whose every dispute was killed.
