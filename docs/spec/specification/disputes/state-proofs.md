## 1. Purpose & observable contract

A **state proof** convinces the chain — which stores only the current snapshot — that a claimed
state belongs to a fork's canonical history. It is the evidence a dispute submits with its claim
and the core of a same-fork snapshot update.

Data model:

```solidity
struct MilestoneProof { BlockConfirmation[] blockConfirmations; }
struct StateProof { MilestoneProof[] milestones; }
```

A proof is only milestones. The claimed latest block is the last block of the last milestone. An
**empty** proof (no milestones) claims the fork genesis. The heavy backing data (genesis snapshot
data, one snapshot per milestone, latest snapshot, message blocks) is carried in
`DisputeAuditingData` and referenced from the dispute by hash.

**What the proof guarantees:** a path from the proof's **walk start** — the same-fork on-chain
snapshot, or the fork genesis (§4) — through threshold-proven milestones to the last proven
point, and a cryptographic link from that point, inside the last milestone, to the claimed latest
block. **What it does not guarantee:** that the latest state is final, or that its transitions
were semantically valid — invalid transitions inside a proof are handled by the dispute fraud
proofs ([fraud-proofs.md](./fraud-proofs.md)), and non-finality is resolved by reduction (§10).

## 2. A milestone is a finality anchor

**<a id="req-sp-1-9yaby1"></a>`REQ-SP-1-9YABY1`.** A milestone is not merely a list of independently threshold-signed blocks. It is a
**finality anchor**: a consecutive, hash-linked run of block confirmations whose accumulated
signatures finalize the run's **first** block. That first block's confirmation is final either
directly — it carries the required threshold signatures itself — or **virtually**, because later,
cryptographically linked confirmations inside the milestone carry their signatures back through
the ancestry ([finality.md §4](../protocol-model/finality.md)).

## 3. Anchors chain to the latest state

**<a id="req-sp-2-st4jj4"></a>`REQ-SP-2-ST4JJ4`.** A state proof establishes a path from one final point to the next, and finally to
the **latest state** the dispute transition operates on. Milestones are ordered by nondecreasing
first-block height; milestones may overlap and may repeat a block, and two consecutive milestones
need no hash link between them, because each later milestone proves its own first block by
threshold (§5). The latest state itself need **not** be final; it MUST be a cryptographically
linked descendant, inside the last milestone, of the last proven point. That linkage is what
places it on the canonical chain before the dispute game applies its transition. The blocks of the
last milestone after its last proven point form the **unfinal tail**.

**<a id="req-sp-5-mte4rv"></a>`REQ-SP-5-MTE4RV`.** The final block of the proved path supplies the state commitment
(`stateSnapshotHash` → `latestStateSnapshotHash`) that the dispute game and the reduction operate
on (`the corresponding state-proof verification operation`).

```mermaid

    S(("walk start<br/>(on-chain snapshot<br/>or fork genesis)")) --> M1["Milestone 1<br/>first block proven<br/>by union threshold"]
    M1 --> M2["Milestone 2<br/>membership hop 4→5<br/>(union set signs)"]
    M2 --> T["rest of the last milestone<br/>(unfinal tail)"]
    T --> L["latest state<br/>= dispute input commitment"]

```

## 4. The walk start and the walk

**[`REQ-SP-8-9PK9TS`](dispute-processing.md#req-sp-8-9pk9ts).** Every state proof is checked by one canonical walk from one start.

- **Walk start.** The chain's current snapshot is final. When it lies on the proof's fork and is
  not that fork's genesis, it is the walk start. Otherwise — it lies on another fork, or it is the
  fork genesis — the fork genesis is the walk start (§6). The genesis MUST be recognized by its
  data — the fork ID is the hash of the genesis snapshot data — not by its height: the genesis and
  a snapshot that block 0 commits both have height 0, and only the second is a normal start. A
  peer that installed the fork from the on-chain snapshot holds no history below it and MUST still
  be able to prove and dispute.
- **Dropped milestones.** A milestone whose last block is below the start height lies wholly
  below the start. The walk drops it: it reads only its first and last block heights, checks
  nothing else in it, reads no snapshot entry for it, and awards it no finality. A proof whose
  every milestone is dropped is valid and proves only the start.
- **The run that holds the start.** When the start is the on-chain snapshot, a kept milestone
  whose first block is at or below the start height holds the start. Its block at exactly the start
  height MUST exist, MUST have that height, and MUST commit the start: its state commitment equals
  the start snapshot's hash. From that block on, the run's blocks MUST be linked, height + 1 and
  author-signed. The run needs no threshold: the start is already final and supplies its own
  participant set. Blocks of that run below the start height are not checked. The rule binds the
  state after that block, not the block's identity: enforcement stores no hash of the block that
  committed the start, so any block at that height that commits the start passes. This is
  sufficient because the state after such a block is the on-chain snapshot itself, so the next
  block is judged from on-chain truth.
- **Threshold milestones.** Every other kept milestone MUST prove its first block by the union
  threshold of the last verified set (§5), and its first block MUST commit the snapshot supplied
  for that milestone. A proven milestone advances the finalized snapshot and the verified set to
  that snapshot. Within the milestone, every block MUST be linked by hash, height + 1, and signed
  by its declared author. A milestone that fails its threshold makes the whole proof invalid,
  except the single genesis case of §6.
- **Every kept block** MUST decode and MUST name the proof's channel and fork.
- **Result.** The walk returns whether the proof is valid; the finalized snapshot (the start, the
  last threshold-proven snapshot, or the fork genesis for an empty proof); and the block index in
  the last milestone where its unfinal tail starts. An index equal to the last milestone's length
  means the proof has no tail. When the walk is invalid, no other result is usable.
- **Linkage-only walk.** The same walk MAY run without finality: it then reads no milestone
  snapshot and checks the start commitment, the genesis link, and the linkage of every kept run.
  Only its valid/invalid answer is usable.
- **One owner.** Dispute verification, snapshot advance, and spectator synchronization MUST use
  this one walk and the same start rule. Block-challenge eligibility uses the same start rule
  without the walk (§9).
- **Fixed during a dispute.** The on-chain snapshot cannot change on a disputed fork
  ([`REQ-ENFSNAP-4-ESP98F` (Disputed-fork advance rule)](../enforcement/snapshot-adoption.md#req-enfsnap-4-esp98f)), so the start stays fixed for
  the whole dispute game.

The start is derived from the dispute's channel and fork. A proof block whose header names a
different channel or fork than the dispute is already a slashable header mismatch, so it cannot
choose a more convenient start.

Whether a peer that has moved ahead on a fork still needs that fork's genesis snapshot at all is open
([`OQ-SPEC-GENESIS-1-TKNMPM` (Fork genesis dependency after a peer moves ahead)](../open-questions.md#oq-spec-genesis-1-tknmpm)).

**Construction.** A prover builds a compact proof from its own local view of the walk start: one
milestone at each participant-set change point above the start, the latest threshold-proven
milestone, and the unfinal tail; or, without any threshold point above the start, one run from the
block at the start height (block 0 for a genesis start) to the requested height. History between
two threshold points with an unchanged set is not needed. The construction rules and their error
outcomes are owned by [`REQ-DISPUTE-PIPE-13-W73B2F` (Proof construction from the local start)](dispute-processing.md#req-dispute-pipe-13-w73b2f).

## 5. Membership hops are required at participant-set changes

**<a id="req-sp-3-sp1jg4"></a>`REQ-SP-3-SP1JG4`.** A join or removal changes the threshold set, so a proof crossing a membership change
MUST establish the old-set → new-set transition at the relevant block with a milestone hop; it
cannot simply assert the new membership. The hop's threshold is the **union** of the last verified
set (the start's set, or the resulting set of the last proven milestone), the milestone's resulting
set, and the pending joiners: a 4→5 join is final only when the four original participants _and_
the joiner have (directly or virtually) signed — proof that both the original set and the joiner
authorized the change. A removal requires the corresponding proof in the other direction (the
pre-removal set covers the leaving member). Only a proven hop advances the verified set used by
the next milestone. Each signer counts once, and only signers in the union count.

The hop threshold is historical evidence of the one peer-to-peer agreement threshold
([finality.md §6](../protocol-model/finality.md)), with two consequences:

- **Pending joiners come from the committed inbound interval.** The joiners added to the union
  are those whose `JOIN` messages lie in the inbound-message interval committed between the last
  verified snapshot and the milestone's resulting snapshot — not the chain's live pending set. In
  an honest transition they already appear in the resulting set; the explicit derivation lets the
  verifier reject a proof that consumes a recorded join while omitting the joiner from its
  participant snapshot.
- **On-chain slashes are never subtracted.** The threshold binds the signatures the past
  transition required, so a proof MUST keep the same validity before and after any later slash.
  Excluding slashed signers here would make historical proof validity depend on later
  adjudication; slash-based exclusion exists only for current dispute eligibility
  ([finality.md §6](../protocol-model/finality.md)).

Between two hops with an unchanged set, the threshold evidence may jump over any length of
history: the later milestone needs no link to the earlier one.

## 6. Genesis start

**<a id="req-sp-4-ncsex4"></a>`REQ-SP-4-NCSEX4`.** When the walk start is the fork genesis, the genesis is the **implicit final
anchor** for that fork; no milestone is needed for it. The genesis has no block of its own.
Concretely:

- An **empty** proof is the fork genesis, whatever the on-chain snapshot is. The latest-state
  check reconstructs the genesis snapshot — the fork ID must equal the hash of the supplied genesis
  snapshot data, with the genesis timestamp derived on-chain (the origin fork's dispute-window
  kill-period end, or the stored snapshot's timestamp when the stored snapshot is the genesis) —
  and compares its hash to the claim.
- **Genesis data.** When the on-chain snapshot is the fork genesis, the walk takes the genesis from
  the chain and reads no supplied genesis data. Supplied genesis data is needed only when the fork
  genesis is not on chain (the on-chain snapshot lies on another fork, or an empty proof is walked
  while a normal start is on chain), and then it MUST hash to the fork ID. Dispute verification
  needs no genesis data beyond what the walk and the latest-state check of an empty proof use.
- **Block 0** links to the genesis through its previous-block hash, which MUST equal the genesis
  snapshot's hash. That link alone does not finalize it: block 0 is final only with the union
  threshold of the genesis set and block 0's resulting set (§5).
- An **unfinal block 0** is allowed only when its milestone is the proof's only milestone. The
  whole run is then the unfinal tail, replayed from block 0, and the finalized state is the
  genesis. An unfinal block 0 beside any other milestone makes the proof invalid.
- A first milestone that starts above height 0 needs no link to the genesis: it proves its first
  block by the union threshold of the genesis set.
- A fork reached by a reduction that the chain has not adopted yet dates its genesis through its
  authenticated origin fork's dispute window.

## 7. Claims below the on-chain snapshot

A proof whose milestones all end below the walk start passes dispute verification: the walk drops
them and proves only the start, and the latest-state check binds the claim to the last block of
the proof. Such a claim is obsolete, because the on-chain snapshot is final and newer. A dedicated
dispute fraud proof answers it (part of [`REQ-SP-8-9PK9TS`](dispute-processing.md#req-sp-8-9pk9ts)):

- It holds when the chain's snapshot is on the dispute's fork, is not that fork's genesis, and the
  dispute's latest claimed block height is **strictly below** that snapshot's height. An empty
  proof claims the genesis and is therefore also below such a snapshot.
- It does not hold when the claimed height equals or exceeds the snapshot height, when the chain's
  snapshot lies on another fork, or when it is the fork's genesis.
- It needs no payload beyond the dispute, slashes the disputer, and kills the dispute like every
  dispute fraud proof ([fraud-proofs.md §3](./fraud-proofs.md)). No separate admission rule
  rejects such a claim at upload.

## 8. Verification by a node

**<a id="req-sp-9-7mwky8"></a>`REQ-SP-9-7MWKY8`.** Any node that verifies a state proof (an auditor, a
synchronizing spectator, a prover checking its own proof) MUST use the same walk, tried from up to
three starts in this order:

1. its latest local threshold-final point of the fork — a state every required participant
   signed, which the node holds;
2. the start its local copy of the chain state reports;
3. the start the chain reports.

A valid walk at any tier is final: the node accepts the proof and does not re-check it at a later
tier or against a newer chain read. A local tier that answers invalid falls through to the next
tier. Only the chain tier can answer invalid. Verification has no "unavailable" result: a tier
that fails — the local execution reverts or fails, the worker connection fails, another internal
component fails, or the chain read fails — does not fall through and is not retried; the error
propagates to the caller. An error is never a verdict: no node builds a counter, kills a dispute,
or penalizes a peer on an error.

## 9. Challenge region and finalized state

**<a id="req-sp-10-am67r2"></a>`REQ-SP-10-AM67R2`.** A dispute submitter is liable only for the
blocks it adds after the last proven point; finalized history and dropped material stay with their
original signers.

- **Coordinates.** Only the last milestone is challengeable. A block challenge against a dispute
  names the block by its index in the last milestone of the submitted proof, and the challenged
  block MUST be the block at that index.
- **Region.** A transition, timestamp, genesis, or forged-message challenge and an
  author-not-participant challenge are eligible when the proof has a milestone, the index lies in
  the last milestone, the last milestone's first block and the challenged block decode, the index is
  at or after the tail start, and — when the walk can start from the on-chain snapshot — the
  challenged block's height is above that snapshot's height. Eligibility needs no walk: the
  validity of earlier milestones is the subject of the invalid-state-proof counter, not of a block
  challenge.
- **Tail start.** When the walk can start from the on-chain snapshot and the last milestone's first
  block is at or below its height, the tail starts right after the block at the on-chain height.
  Otherwise, when the proof has one milestone and it starts at block 0, the tail starts at block 0.
  Otherwise the tail starts at the last milestone's second block: its first block is
  threshold-final. A block before the tail start and an out-of-range index are not eligible.
- **Structure.** A structure challenge is input-only and needs no valid walk: a malformed block is
  never honest history. It is limited to the last milestone. A block is structurally invalid when it
  does not decode or its author signature is not authentic, or — after the run's first block — when
  it does not link to its predecessor in the same run by hash and height + 1. The first block of a
  run has no predecessor offense.
- **Balance state.** The balance-invariant check of a dispute judges the dispute's latest state:
  the snapshot whose hash the dispute commits as its latest state, with state bytes that match that
  snapshot's state-machine-state hash, linked to the proof's latest block. It needs no walk. A
  challenge that supplies another snapshot, or state bytes that do not match it, is rejected. The
  latest state is never below the on-chain snapshot, because a claim below it is killed by the
  below-anchor counter (§7); the disputer answers for the unfinal tail, and a finalized state
  carries the signatures of every participant, the disputer's included.
- **Posted finalized state.** A dispute that posts auditing data also posts the state bytes of its
  finalized state, the state from which every auditor replays the unfinal tail. Those bytes MUST hash
  to the state-machine-state commitment of the walk's finalized snapshot: the snapshot where the walk
  from the chain's own start ends (§4), that is the on-chain snapshot when no milestone above it is
  proven, else the last threshold-proven snapshot, or the fork genesis. The bytes of any other state,
  an earlier proven state of the same fork included, and empty bytes make the state proof invalid:
  the invalid-state-proof counter kills the dispute and slashes its disputer. A counter against a
  dispute whose posted bytes are the walk's finalized state is an invalid submission. An honest posting
  built before a same-fork snapshot lands inside the last milestone can stop matching; this race is the
  deferred [`OQ-SPEC-POSTED-STATE-RACE-1-1ZM6XN`](../open-questions.md#oq-spec-posted-state-race-1-1zm6xn).

## 10. Why the non-final suffix is safe

**<a id="inv-sp-6-gnw74h"></a>`INV-SP-6-GNW74H`.** Extending the proved anchor with unfinalized blocks is safe because signing is a
non-equivocating commitment ([finality.md §3](../protocol-model/finality.md)): a participant cannot commit to
conflicting histories without exposing a slashable double-sign. Different participants MAY still
present different valid latest states during a dispute (they saw different suffix lengths). The
reduction MUST consider all validly proved views and choose the **longest valid proved history**
as canonical — this is how the latest non-final state joins canonical reality instead of being
discarded. A double sign alone does not make a dispute invalid: a dispute whose proof and balance
are valid survives the kill period although its blocks prove a double sign, and the reduction
compares it with the other committed disputes. The choice is made among the disputes committed
while the window is open: a threshold-final dispute ends the window at once
([finality.md](../protocol-model/finality.md)), and its own latest state is then the result, also
when a posted alternate history is longer.

**Open question (shared with [finality.md §5](../protocol-model/finality.md)):** this safety argument currently
depends on round-robin leader election. Other policies may allow a valid suffix to be reverted and
need explicit attribution and penalty rules; long-lived channels and long-range milestone chains
need bounded proofs. Mirrored in [open-questions.md](../open-questions.md).

## Assumptions and constraints

State proofs assume authentic domain-separated signatures, collision-resistant canonical commitments,
available snapshots and auditing data, deterministic membership derivation, and bounded proof length/gas. A
proof establishes linkage and finality anchors, not semantic validity of every transition; fraud-proof and
dispute mechanisms own those checks. Membership changes require explicit hops, the genesis has one canonical
link from block 0, and an unfinal tail is accepted only inside the last milestone.

With a normal walk start ([`REQ-SP-8-9PK9TS`](dispute-processing.md#req-sp-8-9pk9ts)) the walk relies on the
chain's current snapshot being final and unchanged while a dispute on its fork runs. A node's local
copy of the on-chain snapshot can lag the chain; a prover builds from its local view, and the chain
walks the same proof from its own start: milestones that the newer chain start makes wholly lower
are dropped, and a run that holds the newer start passes when its block at that height commits it.

The genesis is recognized by its snapshot data, which the fork ID hashes. A later snapshot of the
same fork whose data equals the genesis data is not a practical case: every snapshot advance needs
a valid state proof, so no one can post arbitrary snapshot data, and the inbound and outbound message
heads and heights that the snapshot data carries never go back along a fork; equal hashes for
different snapshot data are negligible.

Local success is final ([`REQ-SP-9-7MWKY8`](state-proofs.md#req-sp-9-7mwky8)) under the premise that a
local threshold-final point carries the signature of every required participant, including the
node's own. Because signing does not equivocate, no other final state of the same fork can exist at
that height unless a participant double-signed, which is slashable. Verification gas is not bounded
by the protocol yet (Future Work).

## Security considerations

An unsound proof can advance or dispute the wrong state and therefore endanger all channel funds. Threats
include missing/reordered milestones, skipped membership changes, wrong-genesis linkage, duplicate signatures,
threshold off-by-one errors, malformed tails, hash-only unavailable data, proof-size exhaustion, and
predicate drift between validation paths. Verification needs positive and negative cases at every structural
boundary plus adversarial combinations; a proof rejection must leave canonical state unchanged.

The walk start adds these threats. A block at the start height that commits a different state would
graft a different history onto the final snapshot: the start-commitment rule rejects it. A Byzantine
disputer can put a run into its proof that starts below the start height with blocks that link to
nothing, or a self-signed block at the start height that commits the start but is not the block the
participants signed: the walk accepts both, because the blocks below the start are not checked and
enforcement stores no identity of the block that committed the start. It gains nothing: no
transition challenge reaches those blocks, a malformed one in the last milestone is itself a
structure offense of the disputer ([`REQ-SP-10-AM67R2`](state-proofs.md#req-sp-10-am67r2)), and the
first block above the start is judged from the start state. Dropped milestones award no finality and
their snapshot entries are never read, so forged material below the start cannot install a state.
A claim that ends below the start, including an empty proof after a same-fork advance, is killed by
the dedicated below-anchor counter (§7), not by a counter-dispute on a newer state.

A threshold jump skips unchanged-set history; a proof cannot skip a set change, because the next hop
is checked against the union of the last verified set and the resulting set, and the departed or
joining participant's signature is then missing. An unfinal block 0 is refused beside any other
milestone, so a weakly signed genesis block cannot hide in front of a stronger one.

Block-challenge eligibility does not walk the proof. A tail block of a proof whose earlier
milestones are invalid is still eligible: the disputer submitted both, and the invalid-state-proof
counter answers the earlier milestones. With one milestone that starts at genesis block 0, block 0 is
eligible even when it is threshold-final, so a disputer that puts a fraudulent block 0 into such a
proof answers for it although every participant signed it. A threshold-final first block of any other
last milestone and every block at or below the on-chain snapshot stay out of reach.

The posted finalized state is the base from which every auditor replays the unfinal tail. Because it
must be the state that the walk's finalized snapshot commits, a disputer cannot make the auditors
replay from a state of its choice, and the same posting is judged the same way by every auditor and
by the chain. The rule follows the chain's start at verification time, not the start the prover saw.

The balance check judges the dispute's latest state, not a finalized state. That state is never
below the on-chain snapshot (a lower claim is killed by the below-anchor counter), and the disputer
answers for its own unfinal tail, so an old snapshot cannot be used to fake a balance violation.

Residual risks: local success is final, so a node that holds a forged local threshold-final point
(only possible after a slashable double-sign) accepts what the chain would refuse; a node whose
verification fails with an error leaves the dispute to other nodes; the below-anchor counter depends on one honest
participant observing the dispute within the kill period.

## Requirements and invariants

**[`REQ-SP-1-9YABY1`](state-proofs.md#req-sp-1-9yaby1).** A milestone is a finality anchor: its first block is final directly or via virtual votes from later linked confirmations within the milestone.

**[`REQ-SP-2-ST4JJ4`](state-proofs.md#req-sp-2-st4jj4).** Milestones are ordered by nondecreasing first-block height, may overlap, and need no link between them; the latest state need not be final but must be a linked descendant, inside the last milestone, of the last proven point.

**[`REQ-SP-3-SP1JG4`](state-proofs.md#req-sp-3-sp1jg4).** Membership changes require milestone hops proven under the union of the last verified set, the resulting set, and the pending inbound joiners; only a proven hop advances the verified set.

**[`REQ-SP-4-NCSEX4`](state-proofs.md#req-sp-4-ncsex4).** With a genesis walk start the genesis is the implicit final anchor: an empty proof is the genesis; block 0 links to it by its previous-block hash and is final only by the union threshold; an unfinal block 0 is allowed only as the sole milestone; supplied genesis data is needed, and authenticated, only when the fork genesis is not on chain.

**[`REQ-SP-5-MTE4RV`](state-proofs.md#req-sp-5-mte4rv).** The final block of the proved path supplies the state commitment the dispute game operates on.

**[`REQ-SP-8-9PK9TS`](dispute-processing.md#req-sp-8-9pk9ts).** One walk from one start: the same-fork non-genesis on-chain snapshot (recognized by data), else the fork genesis; milestones wholly below the start are dropped; the run holding the start commits it at its height with no threshold; every other kept milestone proves its first block by the union threshold and advances the finalized set; a claim strictly below the same-fork non-genesis on-chain snapshot (an empty proof included) is killed by a dedicated dispute fraud proof.

**[`INV-SP-6-GNW74H`](state-proofs.md#inv-sp-6-gnw74h).** Non-final suffixes are safe: conflicting commitments expose slashable double-signs, and reduction selects the longest valid proved history.

**<a id="req-sp-7-70emat"></a>`REQ-SP-7-70EMAT`.** Linkage checks: every kept block decodes, names the proof's channel and fork, links to its predecessor by hash and height + 1 within its run, carries its author's authentic signature, and the threshold milestones and latest-state commitment hold, exactly as listed in §4–§6.

**[`REQ-SP-9-7MWKY8`](state-proofs.md#req-sp-9-7mwky8).** A node verifies a proof from its latest local threshold-final point, then its local copy's start, then the chain's start; a valid walk at any tier is final, only the chain answers invalid, tiers fall through only on an invalid answer, and every error propagates with no verdict.

**[`REQ-SP-10-AM67R2`](state-proofs.md#req-sp-10-am67r2).** Block challenges name a block index of the last milestone and reach only its unfinal tail, decided without a walk; structure challenges are input-only and limited to the last milestone; the balance check judges the dispute's latest state; posted auditing data's finalized state must be the state the walk's finalized snapshot commits, else the state proof is invalid.

## Future Work

_Non-normative._

- Bound proof size and verification gas: per-call gas ceilings, proof-size limits as a function
  of participant count, or incremental verification across transactions.
- Long-range proofs for long-lived channels: the on-chain snapshot already bounds a proof from below
  on its own fork ([`REQ-SP-8-9PK9TS`](dispute-processing.md#req-sp-8-9pk9ts)); a fork reached through disputes still proves from its
  genesis until a snapshot lands on it.
- Signature aggregation inside `MilestoneProof` to compress hops in large channels.
