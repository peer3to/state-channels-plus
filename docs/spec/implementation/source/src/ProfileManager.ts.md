## Responsibility and observable boundary

Peer registry and policy owner: an addressless profile is created for every transport, then the same
profile gains a checksummed identity index after authentication. It also owns transport replacement,
address-to-live-transport resolution, and all Holepunch ban/unban policy. It also owns the weaker
reconnect ban, which refuses an identity at admission without recording a fault and without touching
discovery.

## Key design decisions

Registration, authentication refusals, transport retirement and upgrade-ban release use the existing owner logger and shared metadata. Replacing a transport still attaches the replacement before retiring the old transport. See [ProfileManager.ts](../../../../../src/ProfileManager.ts#L19).

1. **Identity outlives connection.** Profiles and exclusion state key by normalized address ([`REQ-ID-2-F3Y8J4`](../../../specification/protocol-model/identity.md#req-id-2-f3y8j4)); `updateTransport` keeps profile object identity across upgrades ([`REQ-UPG-2-WH7BC7`](../../../specification/peer-communication/transport-upgrade.md#req-upg-2-wh7bc7)).
2. **Removal is transport-specific.** Every live transport attaches to its profile. Removing one
   pipe promotes another live fallback when available and emits profile loss only after the last
   transport detaches.
3. **Every transport has a profile immediately.** The Holepunch handle is stored on that profile
   before authentication; verification adds the address and identity index without a raw-handle map.
4. **Fallback release has two lifecycle inputs.** Ordinary close follows current-transport ownership,
   so a stale WebRTC close is inert. Explicit policy release checks the full live transport set, so a
   non-preferred WebRTC transport waiting through upgrade grace keeps Holepunch banned.
5. **Authentication is the final fallback admission boundary.** An in-flight Holepunch connection
   is closed if its identity is excluded or still owns a healthy WebRTC transport. A fallback may
   replace WebRTC only after the current direct transport closes. The suspension is rechecked here
   too ([#L60](../../../../../src/ProfileManager.ts#L60)): a suspension placed after the response was
   already accepted still refuses the attempt at this boundary, closing the transport and returning
   no profile. Unlike the exclusion branch it records nothing — a suspension refusal must never
   escalate into a blacklist ([`REQ-AUTH-4-JWCF71`](../../../specification/peer-communication/handshake.md#req-auth-4-jwcf71)).
6. **The transport address is the authentication fact.** Identity profiles may span replacements,
   but `authenticateTransport` is the only writer that gives a network transport its verified address.
7. **A reconnect ban is a second, weaker reason to be refused — never an exclusion, and never a
   discovery change.** `banReconnect`/`allowReconnect`/`isReconnectBanned`
   ([#L233](../../../../../src/ProfileManager.ts#L233)) set and clear one profile flag. They write no
   blacklist mark and do not ban the discovery handle, so a caller can stop admitting a peer without
   claiming a proven fault and without deciding the pair's reachability: the peer keeps being
   discovered and dialed, and every attempt is refused at admission until the flag clears
   ([`REQ-AUTH-4-JWCF71`](../../../specification/peer-communication/handshake.md#req-auth-4-jwcf71)).
   Because nothing was suppressed, `allowReconnect` has nothing to restore either.
   `banTransportReconnect` ([#L266](../../../../../src/ProfileManager.ts#L266)) bans the handle a given
   transport arrived on; it belongs to the exclusion path, which is what stops a rotated discovery key
   from bypassing a blacklist.
8. **One release predicate, so no path can unban an excluded identity.**
   `restoreHolepunchReachability` ([#L290](../../../../../src/ProfileManager.ts#L290)) is the only unban
   site: it refuses while the profile is blacklisted, and its callers first refuse while a live WebRTC
   transport still owns the fallback suppression. All three release paths — `unblacklistPeer`
   ([#L214](../../../../../src/ProfileManager.ts#L214)), the current-WebRTC close
   (`releaseHolepunchBanOnWebRtcClose`, [#L272](../../../../../src/ProfileManager.ts#L272)) and the
   WebRTC→Holepunch downgrade in `applyUpgradeBanPolicy`
   ([#L303](../../../../../src/ProfileManager.ts#L303)) — go through it, so none can lift a blacklist.
   A reconnect ban is not part of this predicate: it never bans a handle, so it has nothing to hold
   ([`REQ-UPG-4-M2XDBA`](../../../specification/peer-communication/transport-upgrade.md#req-upg-4-m2xdba)).
9. **One owner for "this identity still has another route".** `hasOtherLiveTransport`
   ([#L254](../../../../../src/ProfileManager.ts#L254)) answers that question for callers that must
   tell a route replacement apart from a fresh admission; it excludes the transport being decided on
   and reads the profile's live set rather than a second parallel predicate
   ([`REQ-UPG-7-KQPXRE`](../../../specification/peer-communication/transport-upgrade.md#req-upg-7-kqpxre)).

## Assumptions, dependencies, trust boundaries, and limits

- Operates inside the participant runtime; untrusted input arrives only through the documented ingress paths.
- The provisional-profile blacklist transfer in `attachTransportProfile` is defensive-only. The
  normal handshake path refuses and closes an explicitly blacklisted identity before merge.
- The component harness drives the public handshake-finalization path with typed socket and peer-info
  edges. It proves SDK-facing admission, ownership, close, authentication, and traffic behavior, but
  not Hyperswarm's internal network ban. The distributed harness uses `LocalTransport`, and the
  browser WebRTC rig disables Holepunch relay.

## Specification adherence

- Normalized-address keying; churn-surviving exclusion ([`REQ-AUTH-4-JWCF71`](../../../specification/peer-communication/handshake.md#req-auth-4-jwcf71) consequence store).
- The reconnect ban is kept structurally distinct from exclusion: separate flag, separate lift, no
  blacklist mark, and no discovery effect at all — only the exclusion reaches the handle ban.

## Specification contradictions

None demonstrated.

## Missing behavior

Blacklist persistence across restarts is undefined (in-memory) — ban-persistence question in [`OQ-34-FY08V2`](../../../specification/open-questions.md#oq-34-fy08v2).
