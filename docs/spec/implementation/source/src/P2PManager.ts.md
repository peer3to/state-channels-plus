## Responsibility and observable boundary

Owns connections, discovery, profiles, peer penalties and post-handshake promotion. Each manager constructs one [NetworkRpcRouter](rpc/router/NetworkRpcRouter.ts.md) before constructing its services. That router owns ingress, broadcast and network timeout/response hooks; its [ARpcRouter](rpc/router/ARpcRouter.ts.md) base owns the only pending-request registry. RPC callers use this router directly; the manager exposes no routing delegates. Completed handshakes are routed from the local lifecycle: `DISCOVERING`
hands authenticated transports to lobby matching without ordinary promotion or connection notification;
commitment later promotes only the selected profile. A replacement authenticated for that profile during
negotiation handoff is promoted through the same path instead of being rejected as late lobby traffic. An
opened channel performs the participant read and sync.

## Key design decisions

Cleanup delegates to [runCleanup.ts](utils/runCleanup.ts.md), which attempts all ordered steps before reporting the first failure. Caller-owned disposal promises and acknowledgement rules remain in this owner.

Disposal closes registered transports through ProfileManager once, then clears openConnections. The live disconnectAll operation remains available to leave and dispute callers; it is not a second disposal pass.

`resetChannel()` is the non-terminal counterpart ([#L155](../../../../../src/P2PManager.ts#L156)): it leaves the channel's discovery topic through `leaveChannelDiscovery()`, calls `localRpc.resetChannel()` so the custom RPC root drops channel-scoped state, disconnects every peer (`disconnectAll`, which rejects each transport's pending RPCs), and calls `ProfileManager.releaseChannelPeers()` ([#L164](../../../../../src/P2PManager.ts#L164)) so the teardown also reaches transports registered but never opened (lobby, handoff). It does not re-arm the initial-sync latch: the latch settles on any status change out of `OPENED`, and the reset's own `OPENED` → `NOT_OPENED` transition happens later, in `StateManager`, so a latch re-armed here would take that transition as the next channel's outcome. Blacklists deliberately do _not_ go with the profiles, which is why the release is a distinct call and not `dispose()`: an exclusion rests on proof of an attributable fault by that identity, so it is identity-scoped for the runtime's lifetime and follows the peer into the next channel ([`REQ-AUTH-4-JWCF71` (Penalty requires proof)](../../../specification/peer-communication/handshake.md#req-auth-4-jwcf71), engineer decision 2026-09-19, PR #494). The transports of an excluded peer are still closed here; only the verdict survives. The swarm and the custom RPC root instance survive, so the manager keeps serving the next channel. `runCleanup` sequences the steps for the same reason disposal does: an early failure must not skip the later releases.

The manager remembers the selected channel's topic itself: `joinChannelDiscovery(discoveryKey)` ([#L170](../../../../../src/P2PManager.ts#L169)) records the key in `channelDiscoveryKey` ([#L47](../../../../../src/P2PManager.ts#L47)) and joins it, and `leaveChannelDiscovery()` ([#L175](../../../../../src/P2PManager.ts#L174)) leaves and forgets it (a no-op when none is recorded), so the reset takes no argument and the signer does not have to hand the key back.

`rearmInitialSync()` ([#L187](../../../../../src/P2PManager.ts#L186)) is public so that `StateManager.resetChannel()` can call it as the reset's last step, after the status change. It settles a wait created for the old channel as failed (`settleInitialSync(false)`) before re-arming the latch. Leaving it unresolved would hang a connect that belonged to the channel just given up, and re-arming without settling would leak that resolver.

`syncConnectedParticipant()` captures `stateManager.channelGeneration` before it awaits the participant sync ([#L270](../../../../../src/P2PManager.ts#L270)) and returns without settling anything when the generation has moved on ([#L281](../../../../../src/P2PManager.ts#L281)). A leave from a non-committed runtime resets at once, even while that sync is still waiting on its peer; its late result belongs to no current wait, and settling the re-armed latch with it would let the next channel's `connectToChannel` return before any sync of its own ran. The old channel's wait needs nothing from it: the reset already settled that wait as failed.

- The router receives the manager (including its optional debug proxy) after logger initialization and before service construction. Its constructor does no active work. The manager dependency remains explicit because routing uses its live connections, root, logger, timeout manager and peer-policy operations. See [constructor](../../../../../src/P2PManager.ts#L76).

Both blacklist entry points ([address](../../../../../src/P2PManager.ts#L477), [transport](../../../../../src/P2PManager.ts#L452)) log the target before mutation. Existing logger call stacks identify the caller; blacklist policy and method parameters are unchanged. See [P2PManager.ts](../../../../../src/P2PManager.ts#L452).

Both engagement checks use the status predicate that includes SYNCED as well as committed membership. See [P2PManager.ts](../../../../../src/P2PManager.ts#L119).

The network router parses inbound frames once with response-first precedence after the byte-size gate. Connected peer projection remains transport-first with profile fallback and insertion-order deduplication. See [P2PManager.ts](../../../../../src/P2PManager.ts#L327).

1. **Response-first classification** keeps response frames out of service dispatch entirely ([`REQ-RPC-6-E60S4J` (Ordered ingress verification)](../../../specification/peer-communication/rpc.md#req-rpc-6-e60s4j)).
2. **Settlement by peer identity, not transport identity** — a WebRTC upgrade cannot orphan pending requests; a response from any _other_ peer penalizes the responder ([`REQ-RPC-2-SZDTTM` (Request lifecycle)](../../../specification/peer-communication/rpc.md#req-rpc-2-szdttm)).
3. **Unknown/late responses are penalty-free by design** (must therefore stay cheap; bounded by the frame gate).
4. **Service resolution uses the shared public-shape predicate.** A valid custom root loaded from a separate application module graph reaches the same guard and dispatch pipeline; constructor identity is not part of the wire contract ([#L226](../../../../../src/P2PManager.ts#L226)).
5. **Handshake promotion has one owner.** The handshake hook reads local status once. Lobby transports
   enter the session-local matching set, while ordinary statuses promote directly. Lobby commitment calls
   the same promotion primitive only for the selected profile. Opened-channel participant lookup and sync
   failures stay confined without relying on peer-supplied membership.
6. **Disposal is visible to detached work.** `isDisposed` exposes the manager lifetime so guards and
   other pending callbacks can stop without replaying or applying late consequences.
7. **One discovery-key boundary is transport-only.** Channel callers use the exact bytes32 channel ID as
   their canonical key and lobby
   callers pass their exact topic into the same validated join/leave primitive. It establishes connectivity
   but does not set lifecycle, select a peer, or start negotiation.
8. **Lobby admission is session-bound.** The lobby service owns the active caller topic and validates
   it on every lobby payload. Transports own authenticated identity and connection lifecycle, not a
   second copy of the lobby topic.
9. **Discovery is self-contained.** Public lobby and channel joins call the same complete
   local-discovery adapter from `P2PManager`; it exposes no harness-only mode. Node fixtures implement
   `autoConnect: false` by selecting channel state without invoking the public join. Leaving a
   rendezvous stops discovery without closing an established channel transport.
10. **Peer penalties require attributable faults, and none is recorded while the channel is being
    released.** Invalid frames, envelopes, services, and
    endpoints from an authenticated peer blacklist that address and close both the reporting
    transport and any current transport for the same profile. Transport loss, timeouts, send
    failures, cleanup, and unclassified local handler failures remain disconnect-only. Both
    blacklist entry points first read `stateManager.isResettingChannel` and, while it is true,
    only disconnect ([transport](../../../../../src/P2PManager.ts#L452), [address](../../../../../src/P2PManager.ts#L477)). The window is the
    reason rather than the caller: every peer of the channel being given up is on its way out, so
    the release itself tears down transports and pending RPCs, and any consequence observed there
    is an artefact of the teardown rather than evidence about the identity. Since the decision of
    2026-09-19 (PR #494) a verdict is identity-scoped and survives the reset, so one recorded in
    that window would follow the peer into the next channel while belonging to no channel this
    runtime served ([`REQ-AUTH-4-JWCF71` (Penalty requires proof)](../../../specification/peer-communication/handshake.md#req-auth-4-jwcf71), [`REQ-LIF-10-QR8NQ9` (Runtime departure and channel reuse)](../../../specification/settlement/lifecycle.md#req-lif-10-qr8nq9)). A generation comparison would not do: during the
    release the generation has already moved, but what has to be suppressed is the verdict, not a
    write, and the flag is what says the release is still running.
11. **The initial sync wait is bounded before a request exists.** The one initial sync request carries a
    two-agreement-window timeout, but an uncommitted observer could previously wait forever for the first
    participant handshake that produces that request. `joinDiscoveryKey` now arms the same two-window
    deadline; if no participant completes a handshake in time, the observer aborts and its connect settles
    as `false`, exactly as a timed-out request would. A cooperating peer must arrive within the window; the
    runtime never waits for a later one.
12. **The initial sync wait settles on any exit from `OPENED`.** One private settlement helper cancels the
    deadline, records the outcome, and resolves the wait once; nothing else touches the resolver. The
    manager subscribes once to the status hook: a real `OPENED → other` transition settles `true` for
    `SYNCED`, `PENDING_PARTICIPANT`, or `PARTICIPATING` and `false` otherwise, whether or not the sync
    request has started. `dispose` and the abort hook settle `false`. `joinDiscoveryKey` re-checks the
    status after the discovery join, the deadline task settles instead of returning when the status has
    left `OPENED`, and `syncConnectedParticipant` ignores a false remote result once the wait is settled
    or the status has moved, so chain genesis landing during the join or during an active request can
    neither hang the connect nor abort an already synced runtime.

Disposal shares one promise. It attempts Holepunch cleanup even when profile transport cleanup fails, then preserves the first failure.

## Assumptions, dependencies, trust boundaries, and limits

- Operates inside the participant runtime; untrusted input arrives only through the documented ingress paths.

## Specification adherence

- Stages 1–4 with authenticated wire-fault exclusion, neutral local-failure disconnects, and
  correlation single-settlement.
- `resetChannel` releases exactly the channel-scoped half of what disposal releases — the recorded
  channel topic, peers, the non-excluded profiles, and the custom root's channel state — and leaves the
  manager, its swarm, and its router alive, which is the peer-and-transport half of the ordered non-terminal
  release in [`REQ-SDK-ARCH-2-QBZAT8` (Ordered lifecycle)](../../../specification/runtime/sdk.md#req-sdk-arch-2-qbzat8) ([#L155](../../../../../src/P2PManager.ts#L156)).
- Re-arming the initial-sync latch means the next channel waits for its own first participant handshake
  rather than inheriting the previous channel's settled outcome ([#L187](../../../../../src/P2PManager.ts#L186)).
- A participant sync that settles after the runtime left its channel settles no initial-sync wait
  ([#L281](../../../../../src/P2PManager.ts#L281)), so work begun for the channel left cannot complete the next channel's
  initial synchronization ([`REQ-LIF-10-QR8NQ9` (Runtime departure and channel reuse)](../../../specification/settlement/lifecycle.md#req-lif-10-qr8nq9)).
- No exclusion is recorded while the runtime is releasing a channel: both blacklist entry points
  disconnect and return while `stateManager.isResettingChannel` is true ([#L452](../../../../../src/P2PManager.ts#L452),
  [#L477](../../../../../src/P2PManager.ts#L477)), so a fault observed during the release leaves the identity admissible in the
  next channel, which is what keeps an identity-scoped verdict from outliving a channel it was never
  about ([`REQ-LIF-10-QR8NQ9` (Runtime departure and channel reuse)](../../../specification/settlement/lifecycle.md#req-lif-10-qr8nq9), [`REQ-AUTH-4-JWCF71` (Penalty requires proof)](../../../specification/peer-communication/handshake.md#req-auth-4-jwcf71)).

## Targeted connect contribution

Handshake routing recognizes an active matcher attempt without requiring `DISCOVERING`. While the runtime
is uncommitted, the first connected peer proven by authoritative chain state to be a participant starts one
ordinary sync call with a two-window timeout. `P2PManager` aborts on a false result.
Successful matched opening promotes and preserves the participant transport for first sync; observed-open
loser handling joins only the selected raw topic and does not promote the loser. Pending RPC records retain
their original transport; retiring it rejects the request. A response from a foreign peer is rejected.

[`UNIT-TEST-P2P-MANAGER-1-9DNSRZ.P25`](P2PManager.ts.md#unit-test-p2p-manager-1-9dnsrz.p25) means original-transport retirement rejects its pending request even when a replacement exists; `.P3` remains foreign-responder rejection.

Shared operation owners: [errorMessage.ts.md](utils/errorMessage.ts.md), [bytes32.ts.md](utils/bytes32.ts.md).

Runtime disposal also invokes the profile manager cleanup inventory, so unauthenticated connections are closed before logger teardown. Loopback close remains a no-op so disposal invoked through it can return its response.
