## Responsibility and observable boundary

Both halves of verifiable sync. The responder proves the latest provable state or an optional pinned
fork and minimum height. The requester exposes one `sync` entry with an optional timeout, defaulting to one
agreement window. It returns a Boolean and leaves abort or recovery policy to its caller. No
response-age field or second RTT gate exists. A latest request (no fork) is served from the latest
fork the responder derives from the chain walk, not from its own installed fork. The responder builds
the state proof with `AgreementManager.buildStateProof`; the requester verifies it with
`AgreementManager.verifyStateProof`, which answers `valid` or `invalid` and throws on any read
error. Every verification failure cuts the responder: `invalid`, every other payload fault, a
served state that does not reach the walk's final point (a stale proof), and an error thrown
during verification.

## Key design decisions

Source admission reuses this existing sync method unchanged. The request pins channel, optional fork and minimum height; the service returns its existing boolean and a concurrent same-peer request waits for the one in flight (decision 8). Verification, state application and peer-failure behavior remain ordinary sync behavior. BlockQueueManager awaits this call and ends intake without retaining the triggering copy. No admission-specific behavior is added here. See [public async sync](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L64).

Reduction admission to the chain simulation reads finality from the chain contract before fetching and persisting dispute windows. A reduction landing between the reads leaves a conservative false decision: reduction stays in the multicall and safely early-returns if already present. A true decision precedes a window fetch that includes the finalized result. Concurrent proof verification can finalize the shared local EVM window without posting a transaction; that local result cannot justify omitting reduction calldata. One static multicall reads finality for all supplied dispute windows. A successful local reduction already checks the expected successor in Solidity. The chain-final branch checks this request’s fetched chain window. Neither branch re-reads mutable shared local window state after reduction.

Decision (Luka, 2026-09-07): retain this independent per-sync verification and calldata assembly for now. Each request must simulate a complete snapshot update against chain state, even if another request has already proven the same reduction locally. Sharing that proof is a separate optimization: it must not make local completion stand in for chain finality. The extra reads and local reduction calls are accepted pending a design for safe reuse; see [the performance question](../../../../../../open-questions.md#oq-impl-sync-1-hjc60d).

Every pinned request accepts the requested fork or a verified successor whose reduction lineage contains it. On the same fork, the height is a minimum; a verified successor omits the old-fork height requirement. A known successor without an installed genesis uses the computed reduction snapshot and encoded state, an empty state proof, and the outbound block persisted through the existing outbound-chain owner. The genesis timestamp comes from the reduction manager’s cached kill-period observation. See [SpectateService.ts](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L765-L772).

Verified proof suffixes use SpectatingValidationStrategy through the existing ingest option. In-flight sync keys use ChecksumAddress. Pinned sync accepts the requested fork or a successor whose verified reduction lineage contains it; only a same-fork result must meet the pinned height. See [SpectateService.ts](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L598-L614).

Error text delegates to the dependency-free errorMessage helper. Existing catch policy, stack fields, log messages and error propagation remain at this call site. See [SpectateService.ts](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L14).

1. **Nothing trusted on receipt.** Every payload element is re-established against the requester's own chain reads and the mirrored canonical predicates — the file is the reference implementation of [`INV-SYNC-1-XCQZ28` (Nothing trusted on receipt)](../../../../../../../specification/peer-communication/synchronization.md#inv-sync-1-xcqz28).
2. **Validated against the requester's own request.** The request lives in the `sync` closure; the responder's echo is never consulted ([`INV-SYNC-2-AT3RXE` (Requester-anchored validation)](../../../../../../../specification/peer-communication/synchronization.md#inv-sync-2-at3rxe)).
3. **Read-only trust establishment.** All contract checks are local-mirror or simulated calls; no step transacts ([`INV-SYNC-4-Z6HER7` (Read-only trust establishment)](../../../../../../../specification/peer-communication/synchronization.md#inv-sync-4-z6her7), [`REQ-MIRROR-1-XCY9CB` (Constrained equivalence)](../../../../../../../specification/enforcement/local-mirror.md#req-mirror-1-xcy9cb)).
4. **Fail-closed service boundary.** Validation failure cuts the offending peer and returns `false`;
   the caller owns whether that means initial-load abort or exact-recovery queue handling
   ([`INV-SYNC-3-A7A2ED` (Fail-closed with caller-owned consequence)](../../../../../../../specification/peer-communication/synchronization.md#inv-sync-3-a7a2ed)).
5. **Malformed heights rejected before any chain walk** so a hostile target cannot buy expensive traversal.
6. **The pre-genesis outbound segment exists only across forks.** Same-fork payloads encode an
   empty `outboundMessageBlocksUpToLatestGenesis` segment and the requester requires it to be
   empty; successor-fork payloads still collect and contract-verify the linked range.
7. **Verification is historic; no adoption is simulated.** Step 2.9 asks the one proof owner,
   `AgreementManager.verifyStateProof`, to walk the served milestones with the served milestone
   snapshots and the payload's fork genesis ([#L420-L430](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L420-L430)). The walk starts at the latest trusted final
   point it can find (a local threshold-final point, else the local diamond's proof start, else the
   chain's), so history below the proof start is never needed. A milestone wholly below the walk start
   is dropped by the walk and also skipped by persistence ([#L531](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L531)). For a pinned request a dispute
   landing after the proof was served does not change what it proves; a latest-mode request still
   aborts at step 2.8.1 ([`FIND-SYNC-2-VV16K8`](../../../../../../../audit/open-findings.md#find-sync-2-vv16k8)). Reductions are verified on the local diamond (step 2.3) and
   the balance invariant against chain totals (step 2.11, [#L511-L519](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L511-L519)); nothing simulates an adoption
   against the live chain. There is no separate regression check: a proof that ends below the walk
   start verifies (its milestones are dropped) but its served state lies below the walk's start, so
   the sync is rejected as "served state below the proof start" (or, from a genesis start, "served
   state does not reach the final point"): a fresh spectator stops and a participant cuts the
   responder (decision 14; engineer decision, 2026-10-04).
8. **A concurrent sync toward the same peer waits for the one in flight.** `sync` keeps one
   attempt per peer ([#L83-L111](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L83-L111)). A second caller awaits that attempt and returns its result when the
   attempt failed or when it covers the request (same channel and fork, and the same height or an
   in-flight height at or above the requested one). Otherwise it loops and runs its own attempt once
   the earlier one settles.
9. **Every rejection names its reason.** `rejectSync` logs the failed verification step before cutting
   the responder, so a refused sync is diagnosable from the requester's log alone.
10. **The replayed suffix is history.** Each verified block confirmation enters ingest with SpectatingValidationStrategy, which accepts its historical subjective timing. Objective validation is unchanged and any replay failure still rejects the responder.
11. **The unfinal tail enters storage only through its own replay.** The tail is the last
    milestone's blocks above the installed state's height ([#L483-L486](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L483-L486)). Persistence stores the other
    kept blocks but never a tail block ([#L527-L538](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L527-L538)); each tail block then goes through the ingest
    pipeline with SpectatingValidationStrategy ([#L576-L594](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L576-L594)). A replay refusal rejects the sync as
    "block confirmation rejected" ([#L589-L593](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L589-L593)); a replay that throws is a local failure and propagates.
12. **The dispute windows form one chain from the on-chain fork.** At the top of the dispute-window
    loop each window's fork must equal `currentForkId` ([#L274-L280](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L274-L280)), which starts at the step-1
    snapshot's fork ([#L213](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L213)) and becomes each window's reduced fork ([#L331](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L331)).
    Otherwise the sync rejects with "dispute window not linked". Windows are not checked one by one
    in isolation, so a payload cannot skip, repeat, or start from an unrelated fork.
    One exception serves an honest responder whose local snapshot lags the chain: it serves windows
    the chain already adopted. Before the loop, a leading prefix is skipped (`adoptedWindowCount`,
    [#L246-L269](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L246-L269)) only when each window in it is chain-final, its chain-recorded
    `reducedResult.forkId` equals its `reducedForkId`, it starts at the previous window's
    `reducedForkId`, and the last one reduces into the on-chain fork ([#L265-L267](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L265-L267)). Otherwise nothing
    is skipped and the link check above still rejects. The loop runs over the rest,
    `linkedDisputeWindows` ([#L270-L271](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L270-L271)). When a prefix was skipped, the pre-genesis outbound blocks
    are pruned to the on-chain outbound tip with `pruneOutboundMessageBlocks` before step 2.7
    ([#L364-L371](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L364-L371)). The skipped prefix is not persisted: `persistSyncPayload` gets
    `linkedDisputeWindows` and the pruned outbound blocks ([#L553-L558](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L553-L558)). The pinned-mode lineage check
    (step 2.8.2, [#L407-L418](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L407-L418)) still reads the full window list, because the skipped prefix is
    chain-verified.
13. **A latest request targets the derived fork, not the responder's own fork.** In
    `generateSyncPayload` the target starts as the requested fork or the responder's own fork
    ([#L649](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L649)); a request without a fork then targets `currentForkId`, the latest fork
    derived from the chain walk ([#L798](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L798)). A responder whose own state is not installed
    (status `OPENED`, no fork) or whose own fork is behind the derived fork serves the derived fork,
    or throws when it holds no genesis for that fork ([#L837-L839](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L837-L839)). The throw is an explicit
    refusal, not a verdict: the RPC handler answers with an error reply and does not exclude the
    requester; the requester only spends its retry bound
    ([`REQ-SYNC-1-T2589H` (Minimum-target proving)](../../../../../../../specification/peer-communication/synchronization.md#req-sync-1-t2589h)).
14. **One proof owner on both sides; every verification failure cuts the responder.** The responder builds
    the proof with `AgreementManager.buildStateProof(forkId, latest height)` when it holds the fork's
    genesis ([#L879-L893](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L879-L893)); a computed successor that is not installed yet serves the empty proof. A
    build throw returns `undefined`, so the RPC handler cuts the requester ([#L887-L893](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L887-L893)). The served
    state is the built proof's own walked finalized snapshot; a missing milestone snapshot or a
    finalized snapshot the builder's walk did not produce throws, which is a refusal, not an exclusion
    ([#L894-L906](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L894-L906)). The requester calls `verifyStateProof` ([#L423-L430](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L423-L430)) and acts on its two answers:

    - `invalid` (only the chain tier answers it): `rejectSync("milestones invalid")` disconnects and
      blacklists the responder and returns `false` ([#L431-L432](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L431-L432), [#L1158-L1168](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L1158-L1168)).
    - `valid`: the walk's start (or the fork genesis) and finalized snapshot drive everything after
      ([#L433-L435](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L433-L435)). The served encoded state must hash to the finalized snapshot, a served milestone
      snapshot, or the genesis, else the sync is rejected as "finalized state hash mismatch"
      ([#L446-L455](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L446-L455)). When that state is not the finalized snapshot and the last run cannot replay it
      up to the finalized snapshot, the sync is rejected as "served state does not reach the final
      point" ([#L472-L482](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L472-L482)): a stale proof is a verification failure, so a fresh spectator's sync
      fails (its caller stops) and a participant cuts the responder. The latest-fork outbound blocks are
      verified from the walk start ([#L488-L509](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L488-L509)), and persistence stores the kept blocks and the final
      points the walk proved ([#L521-L552](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L521-L552)): each milestone's first snapshot, and for the
      last milestone only when the walk's `replayBlockIndex` is above 0, so the unfinal genesis block 0
      is never a final point ([#L545-L551](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L545-L551)). A run that holds the walk start is stored
      only from the start height up, because the walk checks it only from there ([#L527-L538](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L527-L538)).
      A served state below the walk's start (when the start is not the fork genesis) is rejected as
      "served state below the proof start" before anything is stored: its replay would run through
      blocks the walk never checked ([#L461-L470](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L461-L470)). Such a run adds no final point; the start itself is
      stored on its own, so a later sync that replays it as an on-chain snapshot event finds it known
      ([#L541](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L541), [#L1053-L1056](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L1053-L1056)). A participant-change point is stored at a final point
      whose participant set (lower-case addresses, compared as sets) differs from the previous one,
      starting from the start's set ([#L29-L34](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L29-L34), [#L1060-L1073](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L1060-L1073)).

    `verifyStateProof` has no third answer, and `applySyncResponse` has no catch-all. Only peer data
    rejects the responder: a payload or dispute that does not decode ("payload undecodable",
    [#L174-L176](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L174-L176)), a proof block that does not decode, checked before any EVM work ("proof block
    undecodable", [#L178-L185](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L178-L185)), a window reduction that reverts in the local EVM ("dispute window
    reduction reverted", [#L302-L307](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L302-L307); any other error rethrows), and each failed verification step.
    Every other error (a local revert or executor or worker failure inside `verifyStateProof`, a
    storage invariant, a chain RPC failure) propagates out of the sync and does not cut the responder;
    `runSync` no longer catches it ([#L137-L141](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L137-L141)). Why: one owner decides proof validity for dispute
    verification, fraud proofs and sync ([`REQ-SP-8-9PK9TS`](../../../../../../../specification/disputes/dispute-processing.md#req-sp-8-9pk9ts)), a stale proof proves nothing the chain does
    not already hold ([`INV-SYNC-3-A7A2ED` (Fail-closed with caller-owned consequence)](../../../../../../../specification/peer-communication/synchronization.md#inv-sync-3-a7a2ed)), and an
    internal failure of this node is never a verdict on the responder
    ([`REQ-SP-9-7MWKY8`](../../../../../../../specification/disputes/state-proofs.md#req-sp-9-7mwky8)).

15. **A responder that cannot serve a disputed window yet refuses; it never excludes the
    requester.** While walking dispute windows, `generateSyncPayload` throws in three cases, each a
    limit of the responder, not a fault of the requester:

    - the window's commitments are on chain but cannot be loaded locally ("Dispute window
      unavailable", [#L686-L699](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L686-L699));
    - the window's kill period has not expired by the responder's cached chain reading ("Kill period
      not expired", [#L700-L720](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L700-L720)). The requester accepts a window only after its kill
      period (step 2.2, [#L281-L288](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L281-L288)), and until then evidence can still change the
      reduction, so serving it early would get an honest responder rejected;
    - the reduce data of a disputed window cannot be rebuilt ("Reduce data unavailable for disputed
      fork <forkId>", [#L731-L762](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L731-L762)); a rebuild that throws because a reduce
      input is missing from storage (for a window that synced chain-final) is logged and refused with the
      same text.

    Each throw leaves the RPC handler as an error reply, which the requester sees as an explicit
    refusal. Only an `undefined` payload makes the handler blacklist the requester, and that is
    kept for a target the requester should not have asked for (malformed height, a fork that is not
    the derived latest fork, a height above the latest block) and for a proof `buildStateProof` cannot
    build (decision 14). The cached kill-period reading also supplies the computed successor's
    genesis timestamp ([#L765](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L765)), so both use one observation.

16. **The served genesis equals the trusted genesis in full, timestamp included.** Step 2.6
    compares the payload genesis with the genesis the chain's own timestamp rule defines
    ([#L349-L358](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L349-L358),
    [#L1090-L1125](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L1090-L1125)):
    a reduced fork's genesis carries the kill-period end of the last served window, read from the
    local mirror that holds that window; a fork whose genesis is the on-chain snapshot must hash to
    it. A mismatch rejects the sync as "genesis snapshot invalid" and cuts the responder. Why: the
    requester's first block commits to the genesis hash, so a moved timestamp would make an honest
    first block slashable. When the chain holds neither (the opening fork after a later on-chain
    snapshot), there is no genesis to compare and the walk from the on-chain anchor does not use it.

## Specification adherence

- Minimum-height proving with above-latest refusal and height-zero support ([`REQ-SYNC-1-T2589H` (Minimum-target proving)](../../../../../../../specification/peer-communication/synchronization.md#req-sync-1-t2589h)).
- Client-side balance-invariant check defeating colluding undercollateralized snapshots ([`REQ-SYNC-2-TNT4F4` (Economic soundness before adoption)](../../../../../../../specification/peer-communication/synchronization.md#req-sync-2-tnt4f4)).
- Suffix replay through the standard pipeline in the spectating context ([`REQ-SYNC-3-1P5ZHT` (Suffix through the standard pipeline)](../../../../../../../specification/peer-communication/synchronization.md#req-sync-3-1p5zht)).
- Same-fork payloads carry no cross-fork outbound segment; cross-fork payloads retain the linked
  range and its contract verification.
- A same-fork target that lands after proof creation remains usable for local synchronization when
  its exact snapshot is now on-chain: the walk starts at that snapshot, the run holding it commits it
  at its height, and the served state is the walk's finalized snapshot. A proof that ends below the
  walk start verifies but its served state does not reach the final point, so the sync is rejected
  and the responder is cut (decision 14). No
  fallback re-simulates reductions.
- Proof validity has one owner: the responder builds with `buildStateProof` and the requester
  verifies with `verifyStateProof`; every verification failure, a stale proof included, cuts the responder
  ([`REQ-SP-8-9PK9TS`](../../../../../../../specification/disputes/dispute-processing.md#req-sp-8-9pk9ts), [`INV-SYNC-3-A7A2ED` (Fail-closed with caller-owned consequence)](../../../../../../../specification/peer-communication/synchronization.md#inv-sync-3-a7a2ed)).

## Specification contradictions

The responder algorithm also describes the on-chain-tip-to-genesis outbound range as unconditional.
This implementation now defines that segment as cross-fork evidence: it is empty when the on-chain
snapshot and target genesis share a fork, and linked and verified when they differ.

A chain-final window runs no local reduction, so its reduction input (`latestStateSnapshot`,
`latestEncodedStateMachineState` and `inboundMessageBlocksAppliedInReduce`) is unverified;
`persistSyncPayload` stores only its dispute confirmations (`VerifiedSync.chainFinalForkIds`), so a
re-timed genesis copy cannot replace a stored fork genesis, and the inbound-message events load the
real blocks ([`FIND-SECURITY-5-1KP5YX`](../../../../../../../audit/open-findings.md#find-security-5-1kp5yx),
resolved).

## Missing behavior

A sync request that fails — transport failure, timeout, or refusal — is a counted close on the selected peer (`allowRetry()` at the request catch), keeping the 2026-09-07 liability assumption that honest peers observe the same reality within `agreementTime` without recording a verdict below the bound; a payload that fails verification remains an exclusion with a stated reason, as does an unprovable target refused by the responder's own rules. A latest request is served from the derived latest fork; a responder that cannot serve it (no genesis for that fork, an unavailable dispute window, a window still in its kill period, or missing reduce data) throws, which the requester sees as an explicit refusal and takes as a counted close, not an exclusion. An initial load that is refused waits for another participant under a fresh two-window deadline ([P2PManager](../../../../P2PManager.ts.md)). A stale proof (a served state that does not reach the final point) is a verification failure: this service cuts the responder ([#L472-L482](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L472-L482)); what follows the `false` belongs to the caller. The initial-load owner sees no explicit refusal there and aborts the uncommitted runtime ([P2PManager.ts#L349-L350](../../../../../../../../../src/P2PManager.ts#L358-L359)), and the block-queue admission path still blacklists a source that is not eligible after the sync ([BlockQueueManager.ts#L127-L141](../../../../../../../../../src/stateManager/ingest/BlockQueueManager.ts#L127-L141)). An error thrown during verification, a failed chain read included, is caught by this service and cuts the responder (see Specification contradictions). Kill-period expiry is judged on each side's own clock with no tolerance: a requester whose clock lags the responder's by about a second can still reject a just-expired window as "kill period not expired" and blacklist an honest responder (residual risk). Computed successor proof serving removes the local installation gap. Other local-fault classification remains tracked by [`DEF-5-E8TP9N`](../../../../../../../audit/open-findings.md#def-5-e8tp9n) and [`DEF-10-199C7F`](../../../../../../../audit/open-findings.md#def-10-199c7f). Proof-serving rate limiting remains [`OQ-6-4JPNE5` (P2P gossip rate limiting)](../../../../../../../specification/open-questions.md#oq-6-4jpne5).

## Targeted connect contribution

One `sync` method accepts optional fork, height, and timeout arguments. The default timeout is one
agreement window; `P2PManager` supplies two windows for initial loading. The service returns a Boolean.
`P2PManager` owns initial-load abort, while `BlockQueueManager` owns exact-recovery failure. The sync
service owns no participant selection, responder-readiness queue, or lifecycle transition.

Shared operation owners: [errorMessage.ts.md](../../../../utils/errorMessage.ts.md).

The batching permutation uses identical windows to isolate the RPC count and exact rejection reason. It does not distinguish swapped result indexes. Result-to-fork mapping is exercised by distinct-window lineage verification; do not credit this batching case with that oracle.
