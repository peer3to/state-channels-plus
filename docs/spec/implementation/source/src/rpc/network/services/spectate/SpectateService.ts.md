## Responsibility and observable boundary

Both halves of verifiable sync. The responder proves the latest provable state or an optional pinned
fork and minimum height. The requester exposes one `sync` entry with an optional timeout, defaulting to one
agreement window. It returns a Boolean and leaves abort or recovery policy to its caller. No
response-age field or second RTT gate exists.

## Key design decisions

Source admission reuses this existing sync method unchanged. The request pins channel, optional fork and minimum height; the service returns its existing boolean and treats a concurrent same-peer request as busy. Verification, state application and peer-failure behavior remain ordinary sync behavior. BlockQueueManager awaits this call and ends intake without retaining the triggering copy. No admission-specific behavior is added here. See [public async sync](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L51).

Reduction admission to the chain simulation reads finality from the chain contract before fetching and persisting dispute windows. A reduction landing between the reads leaves a conservative false decision: reduction stays in the multicall and safely early-returns if already present. A true decision precedes a window fetch that includes the finalized result. Concurrent proof verification can finalize the shared local EVM window without posting a transaction; that local result cannot justify omitting reduction calldata. One static multicall reads finality for all supplied dispute windows. A successful local reduction already checks the expected successor in Solidity. The chain-final branch checks this request’s fetched chain window. Neither branch re-reads mutable shared local window state after reduction.

Decision (Luka, 2026-09-07): retain this independent per-sync verification and calldata assembly for now. Each request must simulate a complete snapshot update against chain state, even if another request has already proven the same reduction locally. Sharing that proof is a separate optimization: it must not make local completion stand in for chain finality. The extra reads and local reduction calls are accepted pending a design for safe reuse; see [the performance question](../../../../../../open-questions.md#oq-impl-sync-1-hjc60d).

Every pinned request accepts the requested fork or a verified successor whose reduction lineage contains it. On the same fork, the height is a minimum; a verified successor omits the old-fork height requirement. A known successor without an installed genesis uses the computed reduction snapshot and encoded state, an empty state proof, and the outbound block persisted through the existing outbound-chain owner. The genesis timestamp comes from the reduction manager’s cached kill-period observation. See [SpectateService.ts](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L540).

Verified proof suffixes use SpectatingValidationStrategy through the existing ingest option. In-flight sync keys use ChecksumAddress. Pinned sync accepts the requested fork or a successor whose verified reduction lineage contains it; only a same-fork result must meet the pinned height. See [SpectateService.ts](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L460).

Error text delegates to the dependency-free errorMessage helper. Existing catch policy, stack fields, log messages and error propagation remain at this call site. See [SpectateService.ts](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L17).

1. **Nothing trusted on receipt.** Every payload element is re-established against the requester's own chain reads and the mirrored canonical predicates — the file is the reference implementation of [`INV-SYNC-1-XCQZ28` (Nothing trusted on receipt)](../../../../../../../specification/peer-communication/synchronization.md#inv-sync-1-xcqz28).
2. **Validated against the requester's own request.** The request lives in the `sync` closure; the responder's echo is never consulted ([`INV-SYNC-2-AT3RXE` (Requester-anchored validation)](../../../../../../../specification/peer-communication/synchronization.md#inv-sync-2-at3rxe)).
3. **Read-only trust establishment.** All contract checks are local-mirror or simulated calls; no step transacts ([`INV-SYNC-4-Z6HER7` (Read-only trust establishment)](../../../../../../../specification/peer-communication/synchronization.md#inv-sync-4-z6her7), [`REQ-MIRROR-1-XCY9CB` (Constrained equivalence)](../../../../../../../specification/enforcement/local-mirror.md#req-mirror-1-xcy9cb)).
4. **Fail-closed service boundary.** Validation failure cuts the offending peer and returns `false`;
   the caller owns whether that means initial-load abort or exact-recovery queue handling
   ([`INV-SYNC-3-A7A2ED` (Fail-closed with caller-owned consequence)](../../../../../../../specification/peer-communication/synchronization.md#inv-sync-3-a7a2ed)).
5. **Malformed heights rejected before any chain walk** so a hostile target cannot buy expensive traversal.
6. **The pre-genesis outbound segment exists only across forks.** Same-fork payloads encode an
   empty `outboundMessageBlocksUpToLatestGenesis` segment and the requester requires it to be
   empty; successor-fork payloads still collect and contract-verify the linked range.
7. **Exact-target races are benign, not blanket stale acceptance.** If multicall simulation reports
   `RaceConditionBlockHeightTooOld`, the requester rereads the chain and accepts only when the
   latest on-chain snapshot hash equals the payload's final milestone. Any pending reduction calls
   must still simulate successfully by themselves.
8. **In-flight collisions answer `false` without cutting the peer; probes wait instead.** `sync` keeps
   one attempt per peer and answers a second caller `false` at once. `syncAfterInFlight` waits for the
   in-flight attempt and then runs its own, for a caller whose `false` must mean "peer cut" (the block
   queue's expiry probe), because the earlier attempt need not cover its target.
9. **Every rejection names its reason, and a rejection from a channel the runtime has left costs the
   responder nothing.** `rejectSync` logs the failed verification step before cutting the responder
   ([#L1178](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L1178)), so a refused sync is diagnosable from the requester's log alone. It takes the
   sync's captured generation as a required third argument and, when the runtime's generation has moved
   on, logs "dropping stale sync" and returns `false` without the disconnect-and-blacklist
   ([#L1183](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L1183)): the outcome says nothing about the peer as a member of whatever channel the
   runtime is in now, and the peer answered a request that was valid when it was made. Every reject inside
   `applySyncResponse` passes that generation, and so does the apply-failure path in `runSync`
   ([#L152](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L152)). A request that fails outright (silence, refusal, lost transport) is not a
   verdict: it takes one `allowRetry` strike through the disconnect policy, and that strike is skipped
   when the generation has moved ([#L130](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L130)) — a network error for a channel already left
   is exactly the case the fence exists for. The argument is required, so a new reject path cannot skip
   the stale check by leaving it out.
10. **The replayed suffix is history.** Each verified block confirmation enters ingest with SpectatingValidationStrategy, which accepts its historical subjective timing. Objective validation is unchanged and any replay failure still rejects the responder.
11. **A sync outlived by its channel persists nothing.** `runSync()` captures `stateManager.channelGeneration`
    before the network request ([#L115](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L115)) and passes it to `applySyncResponse()` as an optional fourth
    argument whose default is the current generation, so existing three-argument callers are unchanged
    ([#L172](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L172)). The fence is then read at three points inside
    `applySyncResponse()`, because the response does not reach persistence in one step. First, at the very
    top of the method ([#L178](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L178)), above the payload decode rather than below it: step 1 is
    `fetchAndPersistOnChainSnapshot()`, which writes the on-chain snapshot into the local EVM before any
    of the payload has been verified, so a check placed only at persistence would already be too late,
    and a stale response's decode is work whose only outcome is to be discarded. Second, `persistSyncPayload()` compares it inside the state mutex
    ([#L1025](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L1025)) — the same mutex the channel reset clears storage under — so a payload
    lands either before that clear, and is wiped by it, or not at all. Third, once per block in the replay
    loop ([#L492](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L492)), because each ingest awaits the state mutex and a
    reset can take it between two blocks; one check before the loop would let the rest of the suffix
    through. Fourth, inside each of the two chain-reading helpers the method calls, after their read and
    before their write: `fetchAndPersistOnChainSnapshot()` ([#L844](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L844)) and
    `fetchAndPersistOnChainDisputeWindows()` ([#L871](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L871)). Both now take the generation as a **required**
    parameter and return `undefined` instead of writing, and `applySyncResponse()` returns `false` on
    either. The caller's fence is upstream of their chain reads, which are the awaits a leave settles
    under, and the writes that follow are keyed by the channel id the sync was requested for: a runtime
    that reconnects to that same channel restores the id the event handler checks, so the generation is
    the only thing left that tells the old sync's snapshot from the new channel's. Making the parameter
    required rather than defaulted is deliberate — a default would silently re-read the current
    generation and fence nothing. A changed generation returns
    `{ shouldAbort: false, stale: true }`, and `applySyncResponse()` then returns `false` without rejecting or
    blacklisting the responder ([#L468](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L468)): the peer answered a request that was valid when it was made.
    Fifth, between the local writes that follow: the dispute-window helper re-reads the fence before
    each window it persists ([#L876](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L876)), and `applySyncResponse()` re-reads it before each
    local reduction of an expired window ([#L295](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L295)), because every one of those writes is
    an await a reset can land in and one check ahead of the first would let the rest through.
    The replay loop's own check is a fence, not a duplicate of `ValidationService`'s channel-id rejection:
    that rejection is a refusal with a consequence attached, while the generation check simply stops the
    loop and returns `false`, and it also holds in the window where the id has not been replaced yet.

## Inputs, outputs, state, and side effects

| Inputs       | Sync requests (responder); encoded payloads (requester).                                                                                                                                                                                                                                                  |
| Outputs      | Encoded payloads or refusal; persisted verified state + replayed suffix; a stale `false` for a channel left mid-sync.                                                                                                                                                                                     |

## Assumptions, dependencies, trust boundaries, and limits

- Requester-side chain view honesty anchors every check (../../../../../../specification/security/trust-model.md); proof generation cost is the [`OQ-6-4JPNE5` (P2P gossip rate limiting)](../../../../../../../specification/open-questions.md#oq-6-4jpne5) surface.

## Specification adherence

- Minimum-height proving with above-latest refusal and height-zero support ([`REQ-SYNC-1-T2589H` (Minimum-target proving)](../../../../../../../specification/peer-communication/synchronization.md#req-sync-1-t2589h)).
- Client-side balance-invariant check defeating colluding undercollateralized snapshots ([`REQ-SYNC-2-TNT4F4` (Economic soundness before adoption)](../../../../../../../specification/peer-communication/synchronization.md#req-sync-2-tnt4f4)).
- Suffix replay through the standard pipeline in the spectating context ([`REQ-SYNC-3-1P5ZHT` (Suffix through the standard pipeline)](../../../../../../../specification/peer-communication/synchronization.md#req-sync-3-1p5zht)).
- Same-fork payloads carry no cross-fork outbound segment; cross-fork payloads retain the linked
  range and its contract verification.
- A same-fork target that lands after proof creation remains usable for local synchronization when
  its exact snapshot hash is now on-chain. The height-race fallback rechecks pending reductions and
  never treats a different snapshot at the same or greater height as success.

- `reset()` clears the in-flight sync dedupe keyed by peer address ([#L53](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L53)), so a peer that was mid-sync on the old channel is not refused a fresh sync on the next one. Contributes to [`REQ-SDK-ARCH-2-QBZAT8` (Ordered lifecycle)](../../../../../../../specification/runtime/sdk.md#req-sdk-arch-2-qbzat8).
- The dedupe entry (a `{ request, result }` object) is removed only when that same object still belongs to the attempt that is finishing ([#L102](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L102)). The old unconditional `delete` was a cross-channel hazard once `reset()` could clear the map mid-flight: the next channel may already have registered its own sync to the same peer, and the earlier attempt's `finally` would have deleted that live entry, leaving two concurrent syncs to one peer. Contributes to [`REQ-SDK-ARCH-2-QBZAT8` (Ordered lifecycle)](../../../../../../../specification/runtime/sdk.md#req-sdk-arch-2-qbzat8).
- A sync response applied after the runtime left the channel it was requested for writes nothing and
  cuts no peer ([#L178](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L178), [#L1025](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L1025), [#L492](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L492), [#L468](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L468)), which is this file's part of
  [`REQ-LIF-10-QR8NQ9` (Runtime departure and channel reuse)](../../../../../../../specification/settlement/lifecycle.md#req-lif-10-qr8nq9).
  The no-penalty half now covers every exit, not only the persistence one: every rejection inside
  `applySyncResponse` goes through one local `reject` bound to the peer and the captured generation
  ([#L181](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L181)), the apply-failure path in `runSync` passes the generation to `rejectSync` itself
  ([#L1183](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L1183), [#L152](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L152)), and the request-failure path skips its retry strike on the same check
  ([#L130](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L130)), so a verification failure, a decode failure, or a transport
  failure observed for a channel already left leaves the responder connected, unexcluded and without a strike. The no-write
  half reaches every write, not only the payload persistence: the entry check above the payload decode
  covers the local-EVM write the method makes before it has verified anything, the per-block check in the
  replay loop covers a reset that lands between two ingests, and each chain-reading helper re-reads the
  generation between its own read and its own write ([#L844](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L844), [#L871](../../../../../../../../../src/rpc/network/services/spectate/SpectateService.ts#L871)), which is what a reconnect to the same
  channel would otherwise slip past, since the restored channel id satisfies every id-keyed check the
  write passes through.

## Specification contradictions

The synchronization specification's requester step 6 says to abort when the on-chain snapshot is
"at or past" the proved position. This implementation aborts only when it is strictly past and
accepts the exact-target case so the requester can still persist the proven local state. The
architecture view already describes the check as "past". The stable `INV-SYNC-*` and `REQ-SYNC-*`
statements do not require equal-height abort behavior.

The responder algorithm also describes the on-chain-tip-to-genesis outbound range as unconditional.
This implementation now defines that segment as cross-fork evidence: it is empty when the on-chain
snapshot and target genesis share a fork, and linked and verified when they differ.

## Missing behavior

A sync request that fails — transport failure, timeout, or refusal — is a counted close on the selected peer (`allowRetry()` at the request catch), keeping the 2026-09-07 liability assumption that honest peers observe the same reality within `agreementTime` without recording a verdict below the bound; a payload that fails verification remains an exclusion with a stated reason, as does an unprovable target refused by the responder's own rules. Computed successor proof serving removes the local installation gap. Other local-fault classification remains tracked by [`DEF-5-E8TP9N`](../../../../../../../audit/open-findings.md#def-5-e8tp9n) and [`DEF-10-199C7F`](../../../../../../../audit/open-findings.md#def-10-199c7f). Proof-serving rate limiting remains [`OQ-6-4JPNE5` (P2P gossip rate limiting)](../../../../../../../specification/open-questions.md#oq-6-4jpne5).

## Targeted connect contribution

One `sync` method accepts optional fork, height, and timeout arguments. The default timeout is one
agreement window; `P2PManager` supplies two windows for initial loading. The service returns a Boolean.
`P2PManager` owns initial-load abort, while `BlockQueueManager` owns exact-recovery failure. The sync
service owns no participant selection, responder-readiness queue, or lifecycle transition.

Shared operation owners: [errorMessage.ts.md](../../../../utils/errorMessage.ts.md).

The batching permutation uses identical windows to isolate the RPC count and exact rejection reason. It does not distinguish swapped result indexes. Result-to-fork mapping is exercised by distinct-window lineage verification; do not credit this batching case with that oracle.
