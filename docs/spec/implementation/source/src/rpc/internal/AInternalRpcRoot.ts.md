# AInternalRpcRoot.ts — Source Report

> **Source:** [src/rpc/internal/AInternalRpcRoot.ts](../../../../../../../src/rpc/internal/AInternalRpcRoot.ts) > **Status:** Authored — engineer verification pending.
> **Design views:** [Runtime and concurrency](../../../../views/architecture/sdk/runtime-and-concurrency.md)

## Responsibility and observable boundary

Owns one parent, its children, registered connections and the common logger, error and lifecycle services. A concrete root must implement dispose. The shared disposal operation awaits preparation, recursive child cleanup and final local cleanup once, retaining the first failure while still releasing resources.

## Key design decisions

Cleanup delegates to [runCleanup.ts](../../utils/runCleanup.ts.md), which attempts all ordered steps before reporting the first failure. Caller-owned disposal promises and acknowledgement rules remain in this owner.

Common construction creates LoggerService and rootLogger before start. A new logger uses the concrete constructor name; a supplied owned child keeps its family and existing service attachment. Common disposal releases the root logger and disposes the service even if logger cleanup throws. Worker-only monitoring remains in common start/dispose.

Shared startRuntime awaits the concrete start, then starts monitoring only for worker placement. Shared disposal, directly after domain cleanup and while logging is still alive, drains the request handlers still running for the parent connection (bounded by `IN_FLIGHT_REPLY_DRAIN_MS`), so a reply such as an abort-interrupted connect's `false` is queued ahead of the disposal notification that makes the parent close the connection. Shared disposal stops thread monitoring before releasing the local logger, even after child cleanup failure. Inline roots leave the active thread monitor unchanged. After local cleanup, every root disposes its attached owned logger before completing connection disposal. Logger cleanup still runs after earlier failures.

Shared disposal first yields one turn of the event loop, so work that was already failing when disposal began (an abort's own cause) surfaces as before, then adopts the realm's remaining detached work; it adopts again after domain cleanup and the in-flight reply drain, right before logging is released, for work the cleanup itself started. Adopted origins are logged at debug at adoption, and a failure of adopted work is noted on the root logger while it lives; it never becomes a runtime error, an unhandled rejection, or a drain failure. The registry is realm-wide, so in inline placement a sibling root's in-flight work at that moment settles the same way. See [AInternalRpcRoot.ts](../../../../../../src/rpc/internal/AInternalRpcRoot.ts#L194).

Every concrete root implements abstract start() and dispose(). Common creation installs parent attachment before start. A concrete root can specify its parent type and read the inherited parent reference without a duplicate field. Domain arguments are constructor inputs; the base instance defines the lifecycle contract used by common creation and worker bootstrap.

The root owns topology and recursive disposal; lifecycle owns readiness and quiescence. Each concrete dispose implementation calls disposeRoot with its domain cleanup. The host additionally stops and drains work before descendants are disposed. A leaf follows the same operation with no child calls. Common final cleanup disposes the root logger and all its child loggers; no concrete root must wire that cascade.

RuntimeConnection describes the RPC surface. RemoteRoot owns that surface and its private transport; the connection registry stores those same handles directly with base-root service typing. connect creates one typed remote handle per connection, records its parent or child relation and removes that relation on closure. A second parent is rejected before allocating a transport. Common services and application callers use the same handle, with no separate connection registration object. No connection-established event, manual logger announcement or second local-child registry is needed.

Common construction creates the services and root logger. Shared-store attachment belongs to the logger family. Error reporting flows to the parent and reaches the application handler at the top root. RuntimeConnection keeps concrete service keys and endpoint argument/result types. HostHandlerExecutionContext remains the existing error attribution boundary.

The connection map is the single relationship inventory. Parent and child views filter its handles by relation. Handler execution context comes from the start context supplied during construction; the root passes it explicitly to the internal router constructor, and the service boundary reads that same context. The root does not replace router methods.

## Assumptions, dependencies, trust boundaries, and limits

Factories must label same-realm versus cross-realm connections; MessagePort cannot reveal placement. The root supplies ownership, not logger traversal or peer admission. Local endpoint pairing supports existing same-realm context propagation; ordinary domain calls still cross ports. Construction hooks remain internal and install no test service by default.
