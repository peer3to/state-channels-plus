# createRoot.ts — Source Report

> **Replaces:** `src/evm/contractExecutor/types.ts`

Both disposal directions await final acknowledgement. Parent-requested cleanup first posts its domain response; if the parent closes after that response, closure also confirms shutdown. A child disposal acknowledgement confirms domain cleanup. For an inline child, shared finalization awaits both cached domain disposal and final reply closure before notifying parent close observers, so the acknowledgement can arrive and local connections finish closing.

## Responsibility and observable boundary

Creates an initialized local top-level root or a complete typed remote handle for a parented root. Worker placement requires a parent and an entry URL. The handle owns RPC access, readiness, disposal, quiescence, error observation and closure without exposing its transport.

## Key design decisions

The owned parent port calls `worker.expectShutdown()` synchronously before closing the raw port. This covers explicit closure, startup failure and fatal cleanup paths even when the later `shutdown()` step is delayed. Both disposal directions retain their acknowledgement ordering.

Cleanup delegates to [runCleanup.ts](../../utils/runCleanup.ts.md), which attempts all ordered steps before reporting the first failure. Caller-owned disposal promises and acknowledgement rules remain in this owner.

Creation installs platform cleanup through setAfterDispose; the callback is private. Both local disposal and a child-confirmed disposal invoke completeDisposal. Remote handle variables use the remoteRoot suffix to distinguish them from transports and local roots.

connect returns the RemoteRoot stored in the parent registry. Creation installs cleanup on that handle and awaits its readiness directly; it does not unwrap a registration or extract a transport. Inline counterparts link through the handle.

Worker creation has no workerData override. Bootstrap posts satisfy the shared generic WorkerBootstrapMessage contract; test-specific worker data is supplied by test-owned worker infrastructure.

The common logger option travels in RootStartContext to base construction. There is no lazy inherited logger or conditional attach during initialization. Top-level and child creation retain their existing readiness and failure boundary; logging is already available before concrete start.

Common initialization invokes startRuntime before readiness. Base-root construction creates its logger before initialization, or owns the explicitly supplied component logger directly. Initial context transfer is separate from construction. Scripted monitor inputs belong to test-owned logger wrappers; common initialization uses runtime configuration.

The constructor type describes construction only. Startup is the abstract instance start() contract on AInternalRpcRoot. Creation stores the new instance before awaiting start so startup failures can dispose partial resources. Common initialization attaches the parent before calling start(), installs parent-close disposal and response-before-close cleanup, and signals readiness after start() completes. Concrete roots receive constructor dependencies but no attachment or completion callbacks.

Worker entry modules explicitly call startRootWorker. Root modules have no automatic startup calls or name-based registration. Worker names use the entry constructor. Built-in worker entries establish the diagnostic thread label before initialization; inline roots retain their realm label.

Every concrete root supplies start. Parentage selects attachment; placement selects inline or the single platform worker creator. Common creation waits for required initialization and readiness, reports startup errors before closing the reply path, and cleans partial resources while preserving the original error. rootStartContext installs parent-close observation before start(). A parent lost during initialization rejects creation; after startup the same observation disposes the root.

Forwarded ports use the same registration and root startup: the sender registers an attached child and the receiver creates the root with parentPort. The worker-side bridge retains that pending broker handle in its children collection. Its own readiness does not await external installation. Disposal closes an unattached child without waiting for an acknowledgement from an absent receiver.

There are no per-root worker launchers or definition wrappers. The first side-effect import initializes worker globals before domain imports. Built-in factories supply fixed internal asset URLs; application-defined manifests remain separate.

Worker names come from the entry constructor. Handler execution context is carried by RootStartContext. Monitor startup follows worker mode and runtime configuration; scripted monitor inputs belong to test-owned logger wrappers.

## Inputs, outputs, state, and side effects

The public entry signatures define the startup values and platform handles. Domain roots own services; the common router owns pending requests. Startup and cleanup may allocate or release ports and workers. No separate readiness registry is introduced here.

## Assumptions, dependencies, trust boundaries, and limits

Child startup arguments must be cloneable. Local dependencies do not cross worker boundaries. Built-in SDK and executor entries use internal platform URL modules; generic root creation still accepts an explicit entry URL. Browser builds use the bundler's worker asset imports. Inline placement needs no worker URL. Attached port ownership must form an acyclic tree; the forwarded bridge port represents a child of the worker-side bridge.

## Specification adherence

Creation uses an explicit parent option for children; top-level creation has no parent and allocates no connection. Initialization and child readiness complete before return. The client root completes communication startup; application setup then performs its two deployments through the usable host connection. Platform bootstrap shares the transferred-port boundary.

## Removed declaration or barrel

The removed `src/evm/contractExecutor/types.ts` only re-exported the old executor worker protocol and declared its worker callbacks. RootWorker and the shared bootstrap/error services now own worker delivery, shutdown and failure observation. Domain executor calls use the executor service.

Common wiring takes one options object. Shutdown defaults from placement; an explicit close callback supports test worker entries that report cleanup before exiting. The attachment hook runs once with the allocated parent transport. The concrete root still writes only domain startup.
