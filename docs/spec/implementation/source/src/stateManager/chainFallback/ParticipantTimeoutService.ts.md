# ParticipantTimeoutService.ts — Source Report

> **Design views:** [Dispute pipeline](../../../../views/architecture/sdk/dispute-pipeline.md)

## Responsibility and observable boundary

Schedules checks for a silent writer, recovers relevant calldata and constructs a timeout only while its evidence remains valid. The existing scheduler also owns the fresh check after a chain-time refusal.

## Key design decisions

1. [scheduleCheck](../../../../../../../src/stateManager/chainFallback/ParticipantTimeoutService.ts#L32) refuses disposed runtimes and obsolete forks before allocating a timer. Every scheduled callback enters the same timeout check.
2. [tryTimeoutParticipant](../../../../../../../src/stateManager/chainFallback/ParticipantTimeoutService.ts#L54) checks current membership, accepted blocks, local deadline, window creation and predecessor/target calldata. A local deadline or pending validation causes a scheduled recheck; an older dispute window stops the claim.
3. [createTimeOutDispute](../../../../../../../src/stateManager/chainFallback/ParticipantTimeoutService.ts#L312) builds the timeout from stored predecessor evidence and rechecks fork/disposal and accepted-block state after awaited reads, before storing the claim and calling the normal dispute owner.
4. DisputeManager owns decoding the refused transaction, clearing its marker and releasing its mutex. It passes the attempted slot and the chain timestamp difference to this existing scheduler. This service reconstructs evidence on wake-up; it never resends an old transaction.

## Inputs, outputs, state, and side effects

Constructor: StateManager and child logger. scheduleCheck takes fork, height, participant, delay and reason. tryTimeoutParticipant reads membership, block/snapshot storage, Clock, timeout configuration, calldata recovery and mirror commitments. scheduleTimeoutParticipantRetry delegates the existing one-second validation retry. createTimeOutDispute stores a TimeoutStruct and awaits dispute submission. Timer ownership remains TimeoutManager; the service adds no retry counter or second queue.

## Assumptions, dependencies, trust boundaries, and limits

The chain remains authoritative for timestamp and window admission. Local Clock is an estimate; repeated refusals may need repeated checks. A retry is not guaranteed to succeed after one second. Membership, calldata and stored-block checks remain the ordinary timeout path. The scheduler does not change protocol timing or make an old window eligible.

## Specification adherence

A timestamp refusal re-enters the ordinary timeout decision with current state. Completed block arrival, disposal and fork replacement stop obsolete work.
