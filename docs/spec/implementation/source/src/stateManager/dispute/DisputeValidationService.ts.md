## Responsibility and observable boundary

The auditor. `validateDispute` audits every dispute it is given in full and ends in exactly one of
three ways: `true` (valid, no proof stored), `false` (exactly one dispute fraud proof stored), or a
thrown error (an internal failure: no verdict and no proof). There is no abstain or skip result. An
honest auditor holds the data an audit needs or recovers it; data still missing after recovery is
an internal failure ([#L47-L155](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L47-L155)).

The order is: inbound-tip reality, proof header match, block structure of the last milestone, the
data obligation (posted auditing data must be present when the dispute says it was posted; without
posted data the last milestone must be final by everyone), the below-anchor check, the walk
evidence, state-proof verification (posted data: the chain's `verifyStateProof` alone, then
persistence of the verified material; no data: the latest state and the linkage), the slash subset,
the replay of the last milestone's tail on the dispute's own chain, the pinned inbound anchor, and
then the checks on the audit inputs: balance invariant, disputer-latest-state, the timeout checks,
the stated reason, and the dispute output ([#L555-L781](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L555-L781)).

The service also exposes `isBlockChallengeEligible` ([#L350-L358](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L350-L358)): one chain read of the
contract's own predicate, used by the replay's tail-start search and by each block allegation of
the replay strategy.

## Key design decisions

1. **Every predicate with an on-chain twin runs by staticCall against the canonical logic** so the
   auditor can never disagree with the apply-handler ([`REQ-DISPUTE-PIPE-5-RZZB48` (Mirrored canonical audit)](../../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-5-rzzb48)). The stateful predicates
   (inbound hash, last milestone final by everyone, correct latest state, linkage, slash subset,
   balance invariant, timeout-calldata-posted proof) go through `localFirst` ([#L787-L796](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L787-L796)): a
   local answer that clears the dispute is final, and an answer that would make this node act
   against the disputer is confirmed on chain ([`REQ-MIRROR-4-H9C4YS` (Local-first evaluation, adverse answer confirmed)](../../../../../specification/enforcement/local-mirror.md#req-mirror-4-h9c4ys); helpers [#L798-L885](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L798-L885)). The header check
   `hasStateProofHeaderMismatch` ([#L61-L76](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L61-L76)) and `findFirstInvalidBlockStructureInStateProof`
   ([#L78-L92](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L78-L92)) are pure: they read only the dispute, so the local diamond computes exactly what
   the chain would and no chain read follows. An undecodable block is no header mismatch; the
   structure check judges it.
2. **The data obligation comes before any proof verification.** Posted data must be present when
   the dispute says it was posted, else the audit throws ([#L94-L98](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L94-L98)). Without posted data the last
   milestone must be final by everyone, else `DisputeLastMilestoneNotFinalAndNoAuditingData` is
   stored ([#L100-L101](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L100-L101), [#L242-L250](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L242-L250)). There is no stored-history gate before the audit: the
   former `isLastMilestoneStoredLocally` check, which skipped an audit whose replay start was not
   stored, is deleted. The replay now finds its own base on the dispute's chain (decision 8). Why:
   an honest auditor never abstains (engineer decision, 2026-10-04).
3. **A claim below the chain's proof start is a dedicated fraud.** `tryCreateBelowOnChainAnchorProof`
   reads `getAnchorSnapshot` from the chain contract, not the mirror ([#L257-L265](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L257-L265)). When
   `canUseOnChainSnapshot` is true (a same-fork non-genesis on-chain snapshot) and the proof's latest
   block has a height strictly below that snapshot's height, or the proof is empty, it stores
   `DisputeStateProofBelowOnChainAnchor` ([#L266-L279](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L266-L279)). A last block at or above the height, an
   undecodable last block, or a start that is the fork genesis store nothing here. Why: the walk
   drops milestones wholly below the start, so without this check a forged run below it could never
   be proven invalid ([`REQ-SP-8-9PK9TS`](../../../../../specification/disputes/dispute-processing.md#req-sp-8-9pk9ts)).
4. **The walk evidence needs the fork genesis; a missing genesis throws.** The evidence is the posted
   data, or without data the fork genesis and each milestone's snapshot from storage (the genesis
   fills entries the walk never reads) ([#L301-L332](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L301-L332)). Without a stored genesis the audit throws
   ([#L313-L316](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L313-L316)). Why: an auditor audits only its current fork, whose genesis it holds, so a
   missing genesis is an internal failure, not a reason to skip the dispute.
5. **Posted data is judged by the chain alone (design deviation from local-first).**
   `isPostedStateProofValid` is one `verifyStateProof.staticCall` on the chain contract
   ([#L339-L347](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L339-L347), used at [#L106-L108](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L106-L108)). The chain checks the auditing-data commitment, the walk,
   the latest state, and (D1) that the posted finalized state is the state of the walk's finalized
   snapshot. A `false` answer stores `DisputeInvalidStateProof` with the posted data
   ([#L282-L294](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L282-L294)); a read error throws out of the audit with no proof. No local tier runs first.
   Why: a lagging mirror accepted a posted run whose block at the chain's start does not commit
   that start; the replay then started at the chain's tail start with a base the auditor did not
   hold, and an honest auditor threw. The chain's verdict avoids this. Cost: one chain read per
   posted audit. This deviates from the local-first order ([`REQ-MIRROR-4-H9C4YS`](../../../../../specification/enforcement/local-mirror.md#req-mirror-4-h9c4ys), the three-tier order of
   [`REQ-SP-9-7MWKY8`](../../../../../specification/disputes/state-proofs.md#req-sp-9-7mwky8)); it is recorded as a flagged design deviation pending engineer decision. The D1
   race (a same-fork snapshot post that lands inside the last milestone between construction and
   upload makes an honest posting fail D1) is a deferred open question (engineer decision 12).
6. **Without posted data only the latest state and the linkage are judged.** `isCorrectLatestState`
   and `isStateProofLinked` run local-first with the stored evidence; either one false stores
   `DisputeInvalidStateProof` built from the genesis data only ([#L110-L133](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L110-L133)). No walk runs. Why:
   without data the chain's handler proves only a broken link or a wrong latest state; a failed
   finality check alone is not provable.
7. **Verified posted material is persisted.** `persistVerifiedProof` ([#L164-L240](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L164-L240)) runs only after
   the chain accepted the posted proof. It stores the posted finalized state by its own keccak256
   (D1 binds it, so it is stored unconditionally, [#L169-L173](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L169-L173)) and the posted message blocks
   ([#L175-L185](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L175-L185)). It then runs `AgreementManager.verifyStateProof` for the walk; that walk must be
   valid, else the audit throws ([#L187-L195](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L187-L195)). From the walk it stores the blocks and the
   committed threshold snapshots at or above the walk's start, drops milestones wholly below the
   start, and keeps the last milestone's replay tail out of storage by block hash, also where the
   proof repeats a tail block earlier ([#L196-L239](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L196-L239)). Why: the auditor persists what it lacks so it
   can reduce later; a tail block enters storage only through its own replay, so an unjudged block
   is never stored.
8. **Replay runs the last milestone's tail on the dispute's own chain.** `replayLastMilestoneTail`
   ([#L368-L440](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L368-L440)):

    - **Tail start.** `findTailStart` ([#L443-L456](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L443-L456)) is a binary search over
      `isBlockChallengeEligible`, which is monotone in the block index. The replay never judges a
      block the chain treats as final, and it needs no walk.
    - **Base.** `storage.getPredecessor(forkId, tail[start - 1])`: that block (or, for start 0, the
      fork genesis) with its snapshot and state, read by hash. A missing base throws
      ([#L379-L387](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L379-L387)).
    - **Fast-forward.** Tail blocks already stored by hash with a held snapshot and state are not
      replayed again; the last of them becomes the base ([#L388-L395](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L388-L395)).
    - **Explicit predecessor.** Each replayed block goes through
      `BlockIngestService.onBlockConfirmationStruct` with a `DisputeValidationStrategy` and the
      explicit predecessor `{block, snapshot, state}` ([#L396-L411](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L396-L411)). After a success the next
      predecessor is the replayed block read back by hash; a missing snapshot or state throws
      ([#L426-L434](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L426-L434)). A refused block with a stored dispute fraud proof returns `false`; a refusal
      without a stored proof throws ([#L412-L425](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L412-L425)).

    Why: reading predecessors by coordinates judged a block of an alternate history from the
    auditor's own history at that height. With explicit predecessors every judgment comes from the
    dispute's own chain, and every replayed snapshot and state is stored by hash, so a dispute head
    on an alternate history stays reducible. The former walk-based `replayBlockIndex` start and the
    abstaining replay are gone.

9. **A block allegation is eligible only by the chain's own predicate.** `isBlockChallengeEligible`
   is one chain read of `isBlockChallengeEligible(dispute, blockIndex)` ([#L350-L358](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L350-L358)). The replay
   strategy asks it again right before it stores an allegation; an ineligible allegation now throws
   in the strategy and is unreachable, because the replay starts at the chain's tail start. Why: the
   chain handler runs the same predicate; an ineligible allegation would slash this auditor.
10. **The slash subset is checked before the replay** ([#L135-L136](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L135-L136), [#L535-L553](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L535-L553)). Why: it reads
    only the dispute and the chain's slash set, so it needs no replayed state.
11. **The pinned inbound anchor is checked on the latest snapshot by hash.** After the replay, the
    latest snapshot comes from the proof's latest block by hash
    (`getLatestSnapshotFromStateProof`; a missing snapshot throws) and
    `isDisputeInboundAnchorBehindLatestState` runs on it
    ([#L140-L152](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L140-L152), [#L479-L502](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L479-L502)).
12. **Audit inputs are read by hash; missing chain events are recovered.** `getAuditInputs`
    ([#L508-L532](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L508-L532)) takes the latest snapshot and its state by hash (a missing state throws,
    [#L887-L900](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L887-L900)) and loads the inbound run the dispute names through
    `EventSyncService.loadSynchronizedInboundRun` (the dispute's latest inbound hash down to the
    snapshot's inbound tip, from chain logs when local delivery missed them). A run that is still
    unavailable after recovery throws ([#L519-L522](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L519-L522)). Posted message blocks never replace this
    rebuild. Why: engineer decision 11 — chain events are fetched through the event service, and a
    gap that survives recovery is an internal failure.
13. **The balance invariant uses the dispute's latest state.** `tryCreateBalanceInvariantProof`
    checks the latest snapshot with its state by one local-first read ([#L566-L573](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L566-L573),
    [#L839-L875](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L839-L875)). It needs no walk.
14. **Disputer-latest-state runs after the replay** ([#L459-L477](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L459-L477), used at [#L576-L582](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L576-L582)). The former
    partial-rebuild shortcut is deleted: a stale claim is judged on the full audit inputs.
15. **Self-slashing proof types are checked before they are stored.** The timeout-calldata-posted
    proof is built and checked with `validateTimeoutCalldataPostedProof`: a local "invalid" is kept
    with no chain read, a local "valid" is confirmed on chain before the proof is stored
    ([#L700-L736](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L700-L736)).
16. **Every former abstain path now gives a verdict or throws.** No genesis → throw (decision 4).
    Last milestone not stored → full replay with fast-forward; base not held → throw (decision 8).
    A replay that refused without a proof → throw. A partial rebuild → inputs by hash plus event
    recovery; still missing → throw (decision 12). The "output not linked" skip is deleted
    (unreachable). A missing pinned snapshot → the latest snapshot by hash, missing → throw.
    Deleted with these paths: `isLastMilestoneStoredLocally`, `persistDisputeDataWithoutAudit`
    (with `includeUnfinalizedBlocks`), `runStateProofBlocksThroughPipeline`, `isAuditingEnvelopeValid`,
    `isDataLinkedToDisputeInput`, `isLatestStateLinkedToLatestBlock`, `verifyInboundMessageBlocks`,
    `verifyDisputeOutput`, and `VerifiedWalk`. The expired-kill-period path of [EventHandler](../../eventHandlers/EventHandler.ts.md) now calls
    `validateDispute` (verdict logged, no kill) instead of persisting without an audit.

## Assumptions, dependencies, trust boundaries, and limits

- Only participants and pending participants audit; data availability is guaranteed to them. All
  audit data except chain events is assumed held; chain events are recovered through the event
  service. Data still missing after recovery throws (no verdict, no proof).
- Kill-window deadlines inherit chain-observation freshness; staleness-sensitive checks re-verify
  against the chain.
- A local answer that clears the dispute is accepted without a chain read. A lagging mirror that
  wrongly clears a fraudulent dispute makes this auditor miss the challenge; every other honest
  auditor still audits it (the residual stated in [`REQ-MIRROR-4-H9C4YS` (Local-first evaluation, adverse answer confirmed)](../../../../../specification/enforcement/local-mirror.md#req-mirror-4-h9c4ys)).
- A failed read in any local-first predicate, the chain's `verifyStateProof`, the persistence walk
  or the eligibility read (EVM revert or out-of-gas, executor or worker failure, chain RPC failure,
  programming error) throws out of the audit with no proof. An explicit repeat audit reads again;
  no failure is cached.
- The below-anchor check, the posted-data verification and the block-challenge eligibility read the
  chain directly.
- Residual edge: on an alternate history with a lagging mirror, a replay base that is only the
  chain's anchor snapshot (not posted, not held) makes the audit throw.
- The replay runs the block pipeline in its dispute context; [BlockCommitService](../block/BlockCommitService.ts.md) skips its membership step
  (pending → participating, force-join dispute) during a dispute replay.

## Specification adherence

- Ordered complete verification with no later-step legitimization ([`REQ-DISPUTE-PIPE-2-MJRJV1` (Ordered complete verification)](../../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-2-mjrjv1)); auditor
  equivalence by construction ([`INV-DISPUTE-PIPE-1-BN0K81` (Equivalent audit)](../../../../../specification/disputes/dispute-processing.md#inv-dispute-pipe-1-bn0k81)).
- Every dispute is audited in full: each path ends in a verdict with exactly one stored proof, a
  valid verdict, or an internal failure with no verdict ([`REQ-DISPUTE-PIPE-5-RZZB48` (Mirrored canonical audit)](../../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-5-rzzb48)).
- The contract-owned inbound-anchor predicate runs on the latest snapshot by hash before the
  remaining checks, so linked auditing data cannot hide a stale claimed anchor.
- Every stateful audit predicate reads the local diamond first, accepts only the answer that clears
  the dispute, and lets the chain decide the answer that would produce a fraud proof; only the
  chain's `false` on posted data becomes `DisputeInvalidStateProof`, and a failed read throws with
  no verdict ([`REQ-MIRROR-4-H9C4YS` (Local-first evaluation, adverse answer confirmed)](../../../../../specification/enforcement/local-mirror.md#req-mirror-4-h9c4ys)).

## Specification contradictions

- Posted-data verification is chain-only ([#L339-L347](../../../../../../../src/stateManager/dispute/DisputeValidationService.ts#L339-L347)): the auditor does not run the local tiers
  of [`REQ-SP-9-7MWKY8`](../../../../../specification/disputes/state-proofs.md#req-sp-9-7mwky8) before the chain's verdict, which the specification's audit stage names for
  state-proof verification. The safety property (only the chain answers invalid) holds; the cost is
  one chain read per posted audit. Flagged design deviation, pending engineer decision
  ([`OQ-IMPL-POSTED-VERIFY-1-N00BC3`](../../../../open-questions.md#oq-impl-posted-verify-1-n00bc3)).

## Missing behavior

The cross-audit race where calldata is posted after a kill decision (code TODO) remains an open
sequencing question in the view. The specification has no requirement yet that names the
below-anchor dispute fraud proof (`DisputeStateProofBelowOnChainAnchor`) or the order "data
obligation before proof verification"; this file links them to [`REQ-SP-8-9PK9TS`](../../../../../specification/disputes/dispute-processing.md#req-sp-8-9pk9ts) and [`REQ-DISPUTE-PIPE-2-MJRJV1` (Ordered complete verification)](../../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-2-mjrjv1) until it
does. The D1 race (engineer decision 12) is a deferred open question.
