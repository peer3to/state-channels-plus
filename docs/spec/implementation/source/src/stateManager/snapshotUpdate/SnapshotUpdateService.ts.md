## Responsibility and observable boundary

Snapshot advancement: walks the on-chain snapshot's fork through expired reduced-result links to
the first undisputed fork, builds the successor-fork update with the unprocessed outbound range,
chains a same-fork milestone update for newer finalized state, and multicalls both. Preparation
stands down before submission while reduction is unresolved or the local same-fork snapshot has
not consumed the on-chain inbound head. This is also the N/N exit path.

## Key design decisions

Error text delegates to the dependency-free errorMessage helper. Existing catch policy, stack fields, log messages and error propagation remain at this call site. See [SnapshotUpdateService.ts](../../../../../../../src/stateManager/snapshotUpdate/SnapshotUpdateService.ts#L6).

1. **Multi-generation walking in one submission** — several dispute generations cross in one update because each link is verified on-chain anyway ([`REQ-DIS-9-64WHCD`](../../../../../specification/disputes/disputes.md#req-dis-9-64whcd)).
2. **A disputed-fork refusal resolves the wait `false`.** `RaceConditionSnapshotUpdateDisputedFork`, raised by a same-fork advance on a disputed fork, is logged once as a warning and resolves the submission `false` instead of rejecting ([#L187-L193](../../../../../../../src/stateManager/snapshotUpdate/SnapshotUpdateService.ts#L187-L193)). `RaceConditionSnapshotUpdateNotLatestFork`, raised when a later reduction became the latest fork between preparation and send, is a handled race logged as a warning ([#L181-L186](../../../../../../../src/stateManager/snapshotUpdate/SnapshotUpdateService.ts#L181-L186)); the next post adopts the latest fork. `postStateSnapshotWait` returns that value; it resolves `true` when the post landed, lost a handled race, or had nothing to post, and every other failure still rejects (decision 3 adds the one stand-down that resolves `false`). The leave exit falls back to its self-removal dispute on `false` ([`REQ-ENFSNAP-4-ESP98F` (Disputed-fork advance rule)](../../../../../specification/enforcement/snapshot-adoption.md#req-enfsnap-4-esp98f)). The refusal is not retried: preparation already skips posting onto a disputed fork, so it only meets a post that raced a new dispute, and the next post targets the reduced fork.
3. **One typed result for every preparation and submission.** Both preparations and `submitStateSnapshot` return a discriminated result: `ready` (preparation) or `posted` (submission, with the expected snapshot and the completion), `nothing` when no update is needed, or `blocked` with one reason: `reduction` (the fork's reduction has not landed), `challenge-period` (the reduction's challenge period runs), `inbound` (the chain holds an inbound message the latest local snapshot has not consumed) or `fork-not-posted` (the requested fork's snapshot is not on chain and no fork update precedes it) ([#L15-L52](../../../../../../../src/stateManager/snapshotUpdate/SnapshotUpdateService.ts#L15-L52)). `submitStateSnapshot` returns the first `blocked` result and otherwise posts the `ready` calls in order, the fork update first ([#L105-L124](../../../../../../../src/stateManager/snapshotUpdate/SnapshotUpdateService.ts#L105-L124)); `postStateSnapshot` and `postStateSnapshotWait` are a plain switch on the kind ([#L69-L76](../../../../../../../src/stateManager/snapshotUpdate/SnapshotUpdateService.ts#L69-L76), [#L90-L97](../../../../../../../src/stateManager/snapshotUpdate/SnapshotUpdateService.ts#L90-L97)). Only `inbound` resolves the wait `false`: only a dispute, whose replay applies that message, can move such a fork on, so the leave exit must start its self-removal dispute fallback ([`REQ-LIF-10-QR8NQ9` (Terminal runtime departure)](../../../../../specification/settlement/lifecycle.md#req-lif-10-qr8nq9)). The other blocked reasons resolve `true`, and `postStateSnapshot` returns no snapshot for any of them. A fork-adoption-only post skips same-fork preparation. Why: one result type names every outcome, so no caller decodes flags or sentinels.
4. **A same-fork post proves final state only.** Same-fork preparation asks
   `agreementManager.buildStateProof(forkId, latestHeight, { stopAtThresholdCompletion: true })`
   ([#L440-L445](../../../../../../../src/stateManager/snapshotUpdate/SnapshotUpdateService.ts#L440-L445)): the proof holds the participant-change milestones and the latest
   threshold milestone from the local proof start, and no unfinal tail. It takes each milestone's
   snapshot from the builder's walk evidence and keeps only the milestones whose snapshot is newer
   than the base, by the chain's own `isSnapshotNewer` rule run on the local diamond, so no chain
   call is made per milestone ([#L448-L462](../../../../../../../src/stateManager/snapshotUpdate/SnapshotUpdateService.ts#L448-L462)). The run that holds a non-genesis
   on-chain start maps to its first block's snapshot, at or below the start, so it is never newer.
   With no newer milestone, preparation returns `nothing` ([#L464-L465](../../../../../../../src/stateManager/snapshotUpdate/SnapshotUpdateService.ts#L464-L465)). A builder failure (for example a missing participant-change
   block) is logged and rethrown ([#L519-L527](../../../../../../../src/stateManager/snapshotUpdate/SnapshotUpdateService.ts#L519-L527)), so
   nothing is submitted and a later call retries with repaired storage. Why: the chain adopts only a
   strictly newer final snapshot, and an unfinal tail block would claim a snapshot no threshold
   signed ([`INV-ENFSNAP-1-9VZ2HE` (Single monotone snapshot)](../../../../../specification/enforcement/snapshot-adoption.md#inv-enfsnap-1-9vz2he), [`REQ-SP-8-9PK9TS`](../../../../../specification/disputes/dispute-processing.md#req-sp-8-9pk9ts)).

## Assumptions, dependencies, trust boundaries, and limits

- Ranges built from local stores must match on-chain verification exactly — divergence reverts harmlessly.

## Specification adherence

- Advance-only-along-uncontestable-links with incremental outbound processing ([`REQ-DIS-9-64WHCD`](../../../../../specification/disputes/disputes.md#req-dis-9-64whcd), [`REQ-MSG-5-5XB7DB`](../../../../../specification/settlement/cross-layer-messages.md#req-msg-5-5xb7db)).
- Same-fork preparation compares the local snapshot's inbound tip with the on-chain inbound head
  and returns no calldata while the local state has not consumed it.
- A same-fork update that waits on unconsumed inbound resolves the awaited post `false`, so the terminal
  leave falls back to its self-removal dispute ([`REQ-LIF-10-QR8NQ9` (Terminal runtime departure)](../../../../../specification/settlement/lifecycle.md#req-lif-10-qr8nq9)).

# Terminal leave contribution

`postStateSnapshotWait` is an explicit internal awaitable boundary used by terminal leave so a refused post or a same-fork update blocked by unconsumed inbound (both resolved `false`), or a transaction failure, can fall back to dispute. This contributes to [`REQ-LIF-10-QR8NQ9` (Terminal runtime departure)](../../../../../specification/settlement/lifecycle.md#req-lif-10-qr8nq9).

Shared operation owners: [errorMessage.ts.md](../../utils/errorMessage.ts.md).
