## Responsibility and observable boundary

The reduction attempt: serialized attempts, re-checked preconditions (fork current, window
exists, kill period expired — memoized), the chain-synchronized dispute set (never a window local
records cannot back; empty window → own dispute), mirrored compute of ReduceOutput + successor
genesis, simulate-first submission with race classification (already-reduced/superseded as
convergence), install-locally-then-submit-detached.

## Key design decisions

After checking candidate staleness, preparation delegates reduced genesis construction and outbound persistence to `ReductionManager.prepareReducedGenesis`. The executor supplies the fresh kill-period end and keeps its existing simulation and installation order.

Staleness delegates to the state manager live-fork predicate. A leaving signer already at SYNCED skips chain submission after installation; the chain-result reader returns the ForkId domain alias. See [ReductionExecutor.ts](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L137).

Error text delegates to the dependency-free errorMessage helper. Existing catch policy, stack fields, log messages and error propagation remain at this call site. See [ReductionExecutor.ts](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L1).

1. **Install before submit.** The local fork transition happens once the deterministic result is known; the transaction is detached — another reducer's identical result is convergence, not conflict ([`REQ-DISPUTE-PIPE-6-6FZB9M` (Minimal intervention and convergence)](../../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-6-6fzb9m)).
2. **Chain-backed dispute set only:** missing events are recovered by bounded targeted queries before any reduce ([`REQ-DISPUTE-PIPE-3-PHE3SQ` (Deterministic reduction)](../../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-3-phe3sq) input discipline).
3. **Kill-period memoization is one-directional:** 'expired' is terminal; 'not yet' rechecks.
4. **One staleness guard after every await.** `isStale(forkId)` ("fork changed or manager disposed") replaces the scattered fork comparisons and runs at every boundary that precedes a reduction-owned effect: after the cached and the fresh kill-period reads, after the synced dispute read and after candidate preparation (before their reschedule branches), inside candidate preparation after the computation resolves and before the terminal outbound block is persisted, and before submission preparation, simulation, and completion; the post-install submit is guarded by disposal only and re-checks it after the gas limit resolves, right before the chain write. Apart from the terminal outbound block below, no reduction-owned write happens after disposal.
5. **Storage contract for the early outbound write.** `prepareLocalCandidate` persists the deterministic terminal outbound block through `justPersist` before building the fork calldata, because the calldata builder walks the persisted outbound chain. That write stays: it is idempotent and deterministic for its fork, does not move the outbound head, and `Storage` has no delete, so on a disposed runtime the orphan block stays readable by hash until the runtime object is collected and cannot affect the head or any later protocol action.
6. **A result the chain already records is convergence without a write.** A full-threshold final dispute records the window's reduced fork at upload, and the ordinary attempt that fires at the kill period's end computes the same result. Its simulation would succeed (the contract accepts the repeated finalization and the fork update), so the race classifier never sees it; the attempt now reads the recorded reduced fork before simulating and completes locally with `already-reduced` when it matches the candidate. The fork's snapshot moves with the next snapshot post's walk, which is the path the snapshot service already owns.
7. **The last chain-owned effect is fenced by the channel generation, not only by disposal.**
   `submitDetached` captures `stateManager.channelGeneration` before it awaits the gas limit
   ([#L405](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L405)) and, in the continuation that would send the transaction, returns without writing
   when the runtime was disposed **or** the shared `isStaleChannelWork` predicate says the channel work is stale ([#L420](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L420)). Disposal alone was
   not enough once a leave stopped retiring the runtime: a reset leaves `isDisposed` false, so a submit
   parked on its gas-limit read would have resumed after the reset and written a reduction for the channel
   the runtime had left. The check sits at the same place as the disposal check — immediately before the
   `multicall`, the last effect this component owns — rather than earlier, because the gas-limit read is
   the await the reset actually lands in. A resubmission of the reduce alone after a refused send
   keeps the generation of the submission it replaces and is skipped outright once that work is stale
   ([#L461](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L461)), so a refusal that arrives after the reset sends nothing. Contributes to
   [`REQ-LIF-10-QR8NQ9` (Runtime departure and channel reuse)](../../../../../specification/settlement/lifecycle.md#req-lif-10-qr8nq9).

8. **A frozen adoption does not hold back the reduce.** The chain refuses a successor-fork update onto a fork whose kill period is open ([`REQ-ENFSNAP-4-ESP98F` (Disputed-fork freeze)](../../../../../specification/enforcement/snapshot-adoption.md#req-enfsnap-4-esp98f)). When the bundled simulation reverts `RaceConditionSnapshotUpdateDisputedFork`, which only the adoption call raises, the reduce call before it passed, so the attempt drops the fork update and simulates the reduce alone ([#L366](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L366)); when the detached send meets the same revert because a dispute reached the reduced fork after the simulation, it resubmits the reduce alone ([#L453](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L453)). The simulation path logs at info; the fork's chain adoption waits for a later post.

## Assumptions, dependencies, trust boundaries, and limits

- Provider failure during reduction is fatal by design (the executor cannot guess).

## Specification adherence

- Deterministic order-independent reduction via the mirrored fold; races classified as convergence ([`REQ-DISPUTE-PIPE-6-6FZB9M` (Minimal intervention and convergence)](../../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-6-6fzb9m)).

- A reduction submit already in flight when the channel is left never reaches the chain: the generation captured before the gas-limit read is re-checked in the continuation that would send ([#L405](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L405), [#L420](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L420)), so work begun for the channel left changes nothing on-chain for it ([`REQ-LIF-10-QR8NQ9` (Runtime departure and channel reuse)](../../../../../specification/settlement/lifecycle.md#req-lif-10-qr8nq9)).

- `dispose()` only drops the per-(channel, fork) kill-period memo ([#L79](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L79)); it sets no terminal flag and leaves the attempt mutex in place, so `ReductionManager.reset()` calls it on a channel reset as well as on disposal. The memo is channel-scoped and would answer the next channel with the previous one's expiry, whereas the mutex is the component's own serializer and keeps working afterwards. Contributes to [`REQ-SDK-ARCH-2-QBZAT8` (Ordered lifecycle)](../../../../../specification/runtime/sdk.md#req-sdk-arch-2-qbzat8).

# Channel leave contribution

After a settled self-removal reduction installs a successor where the leaving signer is `SYNCED`, the removed runtime does not submit a redundant reduction transaction. This prevents the channel reset that follows a settled leave from interrupting an obsolete provider transaction, while remaining participants retain normal reduction submission. This contributes to [`REQ-LIF-10-QR8NQ9` (Runtime departure and channel reuse)](../../../../../specification/settlement/lifecycle.md#req-lif-10-qr8nq9).

The reset itself is fenced separately, because a submit can already be past that decision when the leave
settles. `submitDetached` captures the channel generation before its gas-limit read and drops the chain
write when it has moved ([#L405](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L405), [#L420](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L420)), so a transaction in flight for the channel
left is abandoned rather than sent into the runtime's next channel.
