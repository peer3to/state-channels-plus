## Responsibility and observable boundary

The reduction attempt: serialized attempts, re-checked preconditions (fork current, window
exists, kill period expired — memoized), the chain-synchronized dispute set (never a window local
records cannot back; empty window → own dispute), mirrored compute of ReduceOutput + successor
genesis, simulate-first submission with race classification (already-reduced/superseded as
convergence), install-locally-then-submit-detached.

## Key design decisions

After checking candidate staleness, preparation delegates reduced genesis construction and outbound persistence to `ReductionManager.prepareReducedGenesis`. The executor supplies the fresh kill-period end and keeps its existing simulation and installation order.

Staleness delegates to the state manager live-fork predicate. A leaving signer already at SYNCED skips chain submission after installation; the chain-result reader returns the ForkId domain alias. See [ReductionExecutor.ts](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L137).

Error text delegates to the dependency-free errorMessage helper. Existing catch policy, stack fields, log messages and error propagation remain at this call site. See [ReductionExecutor.ts](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L9).

1. **Install before submit.** The local fork transition happens once the deterministic result is known; the transaction is detached — another reducer's identical result is convergence, not conflict ([`REQ-DISPUTE-PIPE-6-6FZB9M` (Minimal intervention and convergence)](../../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-6-6fzb9m)).
2. **Chain-backed dispute set only:** missing events are recovered by bounded targeted queries before any reduce ([`REQ-DISPUTE-PIPE-3-PHE3SQ` (Deterministic reduction)](../../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-3-phe3sq) input discipline).
3. **Kill-period memoization is one-directional:** 'expired' is terminal; 'not yet' rechecks.
4. **One staleness guard after every await.** `isStale(forkId)` ("fork changed or manager disposed") replaces the scattered fork comparisons and runs at every boundary that precedes a reduction-owned effect: after the cached and the fresh kill-period reads, after the synced dispute read and after candidate preparation (before their reschedule branches), inside candidate preparation after the computation resolves and before the terminal outbound block is persisted, and before submission preparation, simulation, and completion; the post-install submit is guarded by disposal only: the check runs before `submitDetached` ([#L275](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L275)). The send itself is an async signer call (nonce, estimate, signing and broadcast), and a disposal during the signer's send is not intercepted: the reduce still goes out, and only the adoption after it is skipped ([#L412-L415](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L412-L415)). Engineer decision (Luka, review 1 FO1): no pre-send disposal guard. Apart from the terminal outbound block below and that started send, no reduction-owned write happens after disposal.
5. **Storage contract for the early outbound write.** `prepareLocalCandidate` persists the deterministic terminal outbound block through `justPersist` before the follow-up post builds the fork calldata, because the calldata builder walks the persisted outbound chain. That write stays: it is idempotent and deterministic for its fork, does not move the outbound head, and `Storage` has no delete, so on a disposed runtime the orphan block stays readable by hash until the runtime object is collected and cannot affect the head or any later protocol action.
6. **A result the chain already records is convergence without a write.** A full-threshold final dispute records the window's reduced fork at upload, and the ordinary attempt that fires at the kill period's end computes the same result. Its simulation would succeed (the contract accepts the repeated finalization), so the race classifier never sees it; the attempt now reads the recorded reduced fork before simulating and completes locally with `already-reduced` when it matches the candidate. The fork's snapshot moves with the next snapshot post's walk, which is the path the snapshot service already owns.
7. **The reduce lands alone; adoption is a separate post.** `prepareSubmission` submits only `reduceAndFinalize` ([#L334](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L334)); once it is mined the executor posts the fork adoption alone through `SnapshotUpdateService.postStateSnapshotWait(..., { forkAdoptionOnly: true })` ([#L349](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L349)), which adopts the latest undisputed fork and never advances the same fork. A post that fails is retried once after `chainFallbackTime` ([#L362](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L362)); a refusal on chain is final. A reduced fork disputed while its reduce was pending is not adoptable, so that post is a no-op and the chain stays on the ancestor until a later reduction's post adopts the latest fork ([`REQ-ENFSNAP-4-ESP98F` (Disputed-fork advance rule)](../../../../../specification/enforcement/snapshot-adoption.md#req-enfsnap-4-esp98f)).
8. **The reduce is sent at the signer's estimate, and a mined resend counts as mined.** `submitDetached` sends the reduce multicall with no gas limit ([#L422-L423](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L422-L423)), so the chain signer sends it at a fresh estimate plus headroom ([`REQ-SDK-ARCH-5-AAM7YK` (Chain submissions survive concurrent inclusion)](../../../../../specification/runtime/sdk.md#req-sdk-arch-5-aam7yk)). The dispute execution gas limit (`getGasLimit`) bounds one gas-capped dispute computation, not the reduce transaction, whose calldata and on-chain checks grow with the disputes it carries; sending the reduce at that fixed limit let a large reduce run out of gas on chain. When the first send is mined and reverts (receipt status 0, for example out of gas) and `tryHandleEvmError` handles it without a race error, the handler has preflighted the same call, resent the reduce and waited for the resend to be mined (receipt status 1), so the executor adopts the reduced fork exactly as for a first send that was mined ([#L444-L448](../../../../../../../src/stateManager/reduction/ReductionExecutor.ts#L444-L448)) and reports nothing. A handled race error keeps the race classification, and an unhandled failure is still logged and rethrown. The disposal check runs before `submitDetached`; a disposal during the signer's send does not stop the broadcast, only the adoption after it (decision 4). The permutations that staged a disposal before the chain write (former P7 and P14) were deleted with the guard they proved.

## Assumptions, dependencies, trust boundaries, and limits

- Provider failure during reduction is fatal by design (the executor cannot guess).
- **Limit (send after teardown):** a reduce send that is still in the signer when the host is torn
  down completely never settles: the destroyed ethers `WebSocketProvider` hangs at populate or
  estimate, so the detached promise stays pending until `DetachedPromises.awaitAllAndClear` times
  out. A disposal that leaves the provider alive lets the send finish and settle with no rejection.
  Open in the audit register; no code change (engineer decision FO1).

# Terminal leave contribution

After a settled self-removal reduction installs a successor where the leaving signer is `SYNCED`, the removed runtime does not submit a redundant reduction transaction. This prevents terminal disposal from interrupting an obsolete provider transaction while remaining participants retain normal reduction submission. This contributes to [`REQ-LIF-10-QR8NQ9` (Terminal runtime departure)](../../../../../specification/settlement/lifecycle.md#req-lif-10-qr8nq9).
