## Responsibility and observable boundary

The chain-intake brain: per-event handlers that first replicate into the mirror, then act —
`onBlockCalldataPosted` (store record before first await, then hand the posted block to the block pipeline's posted-block entry point, which carries the chain commitment on the work item),
`onDisputeCommitted` (dedup by dispute hash, relevance gate, queue purge, ack round, audit
dispatch, final/expired/auditable branches, the upload decided by DisputeManager's evidence comparison),
`onDisputeKilled` (record slash, exclude disputer, replacement evidence when the window empties),
`onChainSlashed`, `onDisputeReducedResultCommitted` (adopt-or-challenge), snapshot-update
convergence. Snapshot updates for a channel that is no longer selected are ignored before mirror
replication or lifecycle mutation, so an old subscription cannot disturb a fresh lobby session.
The runtime publishes each completed handler invocation on its typed internal event bus. Protocol
services can observe accepted chain events there without creating another ethers subscription.

## Key design decisions

Channel-open and snapshot handlers push the supplied snapshot into the fast membership mirror. Delivered inbound messages push their JOIN participants. These updates use event data and retained inbound storage without membership reads; LocalDiamond receives the same events.

Observed slashes immediately override both eligibility caches without a membership read. Storage clearing resets the sets directly without a membership read. Relevant join/snapshot events push authoritative knowledge, while verified state adoption publishes current local membership. Calldata intake explicitly names its chain origin and carries trusted time without inventing a peer or starting sender-admission sync. See [observeOnChainSlash](../../../../../../src/eventHandlers/EventHandler.ts#L673).

Final-dispute completion supplies the prepared height-zero snapshot to `completeWithGenesis`. Its event timestamp equals the kill-period end: a threshold-final upload backdates the last evidence timestamp by `evidenceTime`, making the window expire at the upload block timestamp. Ordinary reductions obtain the kill-period end from the window observation.

Pending leave delegates local signer membership to MembershipService, matching other state-application callers. See [EventHandler.ts](../../../../../../src/eventHandlers/EventHandler.ts#L177-L178).

Signer comparisons delegate to membership ownership while pending-only chain queries retain their narrower participant set. See [EventHandler.ts](../../../../../../src/eventHandlers/EventHandler.ts#L126-L136).

Only exact pending-participant/participating pairs use the shared status predicate. Synced and engaged policies remain separate. See [EventHandler.ts](../../../../../../src/eventHandlers/EventHandler.ts#L165).

1. **Mirror-first, act-second** in every handler — replication is unconditional ([`REQ-MIRROR-2-E9F3TM` (Unconditional replication)](../../../../specification/enforcement/local-mirror.md#req-mirror-2-e9f3tm)), decisions follow.
2. **Kill before counter-dispute, sequentially:** the kill must mine so the replacement has its stated reason; atomic multicall folding is the flagged TODO.
3. **Evidence improvement by comparative reduction, reduction scheduled regardless:** upload own dispute only when DisputeManager's comparison finds that `reduce([ours,theirs])` differs from `reduce([theirs])` (decision 7); the upload is a no-op when this node already holds a commitment in the window, and the reduction is scheduled from the commit in every case (an early return into the skipped upload stalled the window). An upload that the chain refuses with `RaceConditionDisputeEvidencePeriodExpired` (the evidence period closed before it landed) is contained: no evidence can join the window any more, so the handler logs it at info level and still schedules the reduction ([#L627-L643](../../../../../../src/eventHandlers/EventHandler.ts#L627-L643), [#L646-L649](../../../../../../src/eventHandlers/EventHandler.ts#L646-L649)), the same containment as the replacement race in `onDisputeKilled`. Any other upload error still escapes the audit ([`REQ-DISPUTE-PIPE-6-6FZB9M` (Minimal intervention and convergence)](../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-6-6fzb9m)).
4. **Selected-channel gate before snapshot handling.** A delayed close event from a previous role
   cannot clear `DISCOVERING`, leave its rendezvous topic, or write unrelated state.
5. **One ethers-backed intake, typed internal fan-out.** `StateChannelEventListener` and
   `EventSyncService` own provider filters, replay, deduplication, and ordering. The runtime publishes
   only after this handler completes its mirror and state updates. Consumers subscribe to that
   internal event instead of duplicating provider lifecycle and race handling.
6. **Reduction calls go through the terminal owner.** The dispute handlers call `ReductionManager.schedule`, `tryReduce`, and `completeWithGenesis` directly and accept the disposed results (`undefined` completion, `false` completion) without installing or submitting anything; a direct final-dispute reduction settles a pending leave once through the staged reduction application ([`REQ-DISPUTE-PIPE-3-PHE3SQ` (Deterministic reduction)](../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-3-phe3sq)).
7. **The evidence comparison is dispute policy, owned by DisputeManager.** After a successful audit
   `onDisputeCommitted` asks `disputeManager.shouldAddOwnEvidence(forkId, dispute)`
   ([#L612-L616](../../../../../../src/eventHandlers/EventHandler.ts#L612-L616)) and uploads its own dispute only on
   `true`. The handler keeps no comparison state: it only tells the owner when a kept answer loses
   its premise — `onDisputeKilled` calls `forgetEvidenceComparison(forkId)`
   ([#L831](../../../../../../src/eventHandlers/EventHandler.ts#L831)), and `onDisputeReducedResultCommitted`
   calls it when the window is reduced ([#L709](../../../../../../src/eventHandlers/EventHandler.ts#L709)). The memo, its
   rules, and its tests belong to [DisputeManager](../disputeManager/DisputeManager.ts.md) (decision 12)
   ([`REQ-DISPUTE-PIPE-6-6FZB9M` (Minimal intervention and convergence)](../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-6-6fzb9m)).
8. **Reduced-result validation is chain-only.** `validateDisputeReductionAndChallenge`
   recomputes the committed reduction with `ReductionManager.computeReduction`, the chain's reducer
   ([#L950-L954](../../../../../../src/eventHandlers/EventHandler.ts#L950-L954)), and challenges a disagreement
   ([#L971-L973](../../../../../../src/eventHandlers/EventHandler.ts#L971-L973)). The local diamond has no sync guarantee, so a
   local-first recomputation would not lower chain reads on average.
9. **Dispute decisions apply only to the current fork.** After the authoritative kill-period read,
   `handleDisputeCommitted` returns when the runtime's fork is no longer the dispute's fork
   ([#L528-L529](../../../../../../src/eventHandlers/EventHandler.ts#L528-L529)); after a failed audit it returns before reading the stored fraud proof
   when the fork changed during the audit ([#L566-L568](../../../../../../src/eventHandlers/EventHandler.ts#L566-L568)). The expired branch awaits its
   full audit before it records the dispute and schedules the reduction (decision 11). Why: an
   old-fork kill or persist would act on state the runtime already replaced, and an unawaited
   audit could race the scheduled reduction
   ([`REQ-DISPUTE-PIPE-4-3YVDSA` (Atomic recovery)](../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-4-3yvdsa)).
10. **Only participants and pending participants handle disputes.** Right after the relevance check,
    `handleDisputeCommitted` continues only when `isCommittedParticipantStatus(status)` holds
    ([#L397-L409](../../../../../../src/eventHandlers/EventHandler.ts#L397-L409)): data availability is guaranteed to them. Any other observer (a
    spectator) aborts its runtime on every dispute event of its fork, new, final or expired, before the
    final and expired branches and before `validateDispute`, so it stores no dispute, builds no counter
    (including the dispute strategy's stored merges, which start only from that audit) and follows no
    reduction. One check covers all three branches (engineer decision, 2026-10-04: "abort on every
    dispute"; what a spectator should do during a dispute is an open question)
    ([`REQ-DISPUTE-PIPE-2-MJRJV1` (Ordered complete verification)](../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-2-mjrjv1)).
11. **An expired kill period still gets a full audit, never a kill.** When the authoritative read
    says the window exists and its kill period expired, `handleDisputeCommitted` runs the same
    `validateDispute` as the auditable branch, logs an invalid verdict
    (`Expired dispute is invalid, but can no longer be killed`) and sends no kill, then stores the
    dispute confirmation and schedules the reduction at the kill-period end ([#L530-L557](../../../../../../src/eventHandlers/EventHandler.ts#L530-L557)). There is no persist-without-audit
    path. Why: the audit's replay stores every block, snapshot and state of the dispute's tail by
    hash, so a peer that recovers the commit only after the kill period (it was offline, or its
    delivery was lost) still holds the dispute head the reduction reads; a kill after the kill period
    is refused on chain, so the verdict can only be logged. An audit that throws (an internal failure
    or missing chain data) escapes the handler like any other audit error
    ([`REQ-DISPUTE-PIPE-2-MJRJV1` (Ordered complete verification)](../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-2-mjrjv1)).

## Assumptions, dependencies, trust boundaries, and limits

- Operates inside the participant runtime; untrusted input arrives only through the documented ingress paths.
- The kept evidence comparison is only as fresh as the kill and reduced-result events this handler forwards to DisputeManager; both calls run before the handler's first await.

## Specification adherence

- Chain-only dispute intake with dedup and exact binding ([`REQ-DISPUTE-PIPE-1-HRBFP7` (Bound intake)](../../../../specification/disputes/dispute-processing.md#req-dispute-pipe-1-hrbfp7)); adopt-or-challenge on foreign reductions.
- A challenge is only built from a chain-computed disagreement.

## Specification contradictions

None demonstrated.

## Missing behavior

Counter-dispute after a kill is currently disabled in code in favor of event-driven replacement (open sequencing question); atomic kill+replacement multicall (TODO).

# Terminal leave contribution

`StateSnapshotUpdated` accepts an otherwise unknown snapshot when it proves removal for a runtime with a pending terminal leave. It lets reduction converge instead of aborting, then rechecks leave completion after snapshot and reduced-fork event processing. The removal alone proves the signer is in neither on-chain set, so the branch assigns `SYNCED` without a pending-set read: the contract refuses a JOIN while the fork carries a dispute window, a same-fork snapshot post must consume every pending JOIN, and a reduction consumes the JOINs up to its window's expiry, so no posted snapshot can drop a signer whose JOIN is still pending ([`REQ-LIF-10-QR8NQ9.T1.P6`](../../../../specification/settlement/lifecycle.md#req-lif-10-qr8nq9.t1.p6)). This contributes to [`REQ-TJOIN-7-NNGTAY` (Terminal channel leave)](../../../../specification/peer-communication/targeted-channel-join.md#req-tjoin-7-nngtay) and [`REQ-LIF-10-QR8NQ9` (Terminal runtime departure)](../../../../specification/settlement/lifecycle.md#req-lif-10-qr8nq9).
